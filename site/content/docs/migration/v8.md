# Migration Guide v8

LiteBus 8.0 puts an execution identity on every mediation: the calling principal and the tenant the work belongs to, resolved once and read from the execution context. Tenancy becomes a declared pipeline position like authorization and audit, stamped onto durable envelopes and restored when a reaction runs. Authorization gains composable named policies with a permission port, and each assembly of a modular monolith contributes its own LiteBus configuration through application modules instead of one central registration call.

All audit code moves to the `LiteBus.Auditing` package family, the `RequireHandler` boolean becomes an acknowledgement call, and HTTP refusals map through a catalog instead of the mediation outcome, so most breaks surface as compile errors or as a changed status code a test asserts on.

Four rollout changes need attention. Tenant-scoped idempotency keys change their stored format, and claims made before the upgrade are not recognized after it. A guard denial that carries no mapped code answers 400 where v7 answered 403. Immediate dispatch with handler-level immediacy markers but no per-handler delivery fails composition, and Entity Framework Core storage fails startup when the scoped context is not registered. There are no database schema changes: no PostgreSQL version moves and no Entity Framework Core migration.

## Upgrade Checklist

1. Update LiteBus package references to 8.0.0 and rebuild. A `net10.0` application keeps its target framework; LiteBus 8 also ships a `net11.0` build for applications on .NET 11.
2. Reference `LiteBus.Auditing.Abstractions` where messages declare audit positions and `LiteBus.Auditing` where the application composes, add `using LiteBus.Auditing.Abstractions;` to every file that names an audit type, and move audit configuration to `registry.Modules.AddAuditing(auditing => auditing.ForCommands()...)`. See [Audit Code Moved to the Auditing Packages](#audit-code-moved-to-the-auditing-packages).
3. Replace `dispatch.RequireHandler = false` with `dispatch.AllowEnvelopesWithoutHandler(reason)`, stating why envelopes may reach no handler.
4. Register the context with `AddDbContextFactory<TContext>` (which also registers the scoped context) wherever the Entity Framework Core stores configure `UseDbContext<TContext>`, and point `UseDbContext` at the context the handlers resolve through `ITransactionalOutbox<X>`. A startup task and a resolve-time guard fail with the missing call named.
5. Where a handler class carries `[DispatchImmediately]` with immediate dispatch enabled, call `EnablePerHandlerDelivery()` or move the attribute to the event type.
6. Review every `Verdict.Deny` and `Validity.Invalid` code. A denial whose code has no catalog mapping answers 400 where v7 answered 403, and a `validation.*` code answers 422 where v7 answered 400. Map product codes in a refusal catalog or adopt the dotted codes the default catalog covers.
7. Replace `IOutbox` injected into command handlers with `ITransactionalOutbox<TContext>`. LB1025 names each handler.
8. Give each reaction its own subscriber name in `<module>.<event>.<reaction>` form. LB1027 names each shared value.
9. Replace LB1007 and LB1017 suppressions in contracts assemblies with `[assembly: MessageContractsRegisteredIn("RegisteringAssembly")]`.
10. Split definition classes that declare more than one concern. LB1028 suggests the split names. This is an informational note, so schedule it rather than blocking the upgrade on it.
11. Prefer `AuditDeclaration.Audited(action, category:, targetKind:)` over `with` chains that end in `WithTargetFrom`, which needed parentheses to compile.
12. Extend custom outbox stores to honor `OutboxLeaseRequest.MaxPerTenant`, and custom `IModuleRegistry` implementations with `Find<T>()`. Custom execution contexts compile unchanged: `IExecutionContext.Identity` has a default.
13. Deploy the idempotency key change when no repeat crossing the upgrade would double-apply. Tenant-scoped claims stored before the upgrade are not recognized after it.
14. Adopt execution identity, tenancy declarations, authorization policies, ambient tenant propagation, and application modules as capabilities, each behind its own opt-in. See [New Capabilities](#new-capabilities).
15. Run the test suite. New LB1025 through LB1028 diagnostics appear on code that was clean in v7, and tests asserting HTTP status codes or problem types observe the catalog mapping.

## Major Changes in v8

In v7, the pipeline decided whether work happens, but the caller traveled however each application carried it: a caller property copied onto every command and query, a tenant that existed only as envelope metadata, and a tenancy check each product wrote itself in its own authorization guard, with nothing failing composition when a message never decided. Authorization carried a policy name and left the engine to the application. Registration lived in one central `AddLiteBus` call, so analyzers that see one compilation at a time reported contracts in assemblies that only held them.

In v8, the mediator resolves one identity per mediation and exposes it as `IExecutionContext.Identity`, so guards, handlers, audit actor resolution, and reactions read the caller from the pipeline instead of from a property every message carries. Tenancy is a declaration with three positions, a guard, and composition coverage, and the ambient tenant propagates onto envelopes and back into reactions. Authorization policies compose from combinators with one evaluation order, and application modules let each assembly configure the composition it belongs to, which also gives the contract analyzers a way to see registrations across assemblies. Every break in that vocabulary is a compile error or a startup failure rather than a silent behavior change, which is deliberate. A second tenant's message dropped without a signal, or an immediacy marker ignored without an error, is the failure the checks replace.

## Audit Code Moved to the Auditing Packages

Every audit type leaves `LiteBus.Messaging.Abstractions` and `LiteBus.Messaging` for the auditing package family. Messaging keeps the concerns that decide how a mediation ends; auditing observes how it ended, so it lives in its own packages and reaches the pipeline through completion handlers and generic declarations.

`LiteBus.Auditing.Abstractions`, namespace `LiteBus.Auditing.Abstractions`, holds `AuditActor`, `AuditDeclaration`, `AuditedDeclaration`, `AuditExemptDeclaration`, `AuditedAttribute`, `AuditExemptAttribute`, `AuditOutcome`, `AuditReasonMissingException`, `AuditRecord`, `IAuditActorResolver`, `IAuditDefinition<TMessage>`, `IAuditOutcomeMapper`, `IAuditRecordWriter`, `IAuditScope`, `IAuditTrail`, the audit catalogue, and the `Audited` and `NotAudited` declaration extensions. `LiteBus.Auditing` holds the record writer, `DefaultAuditOutcomeMapper`, `AuditTrailDiagnosticCheck` and the auditing module. A message assembly references `LiteBus.Auditing.Abstractions`, and the composition root references `LiteBus.Auditing`:

```csharp
// Before (7.x)
using LiteBus.Messaging.Abstractions;

services.AddLiteBus(liteBus =>
{
    liteBus.AddMessaging(messaging => messaging.UseAuditTrail<PostgresAuditTrail>());
    liteBus.AddCommands(commands => commands.RegisterFromAssembly(assembly).EnableAuditing());
});

// After (8.0)
using LiteBus.Auditing;
using LiteBus.Auditing.Abstractions;

services.AddLiteBus(liteBus =>
{
    liteBus.AddMessaging(_ => { });
    liteBus.AddCommands(commands => commands.RegisterFromAssembly(assembly));
    liteBus.Modules.AddAuditing(auditing => auditing
        .ForCommands()
        .UseTrail<PostgresAuditTrail>());
});
```

No audit type is renamed. An application that aliased the framework type to dodge a collision drops the alias only when nothing else in scope defines the same name; an application with its own `AuditRecord` or `AuditOutcome` keeps the alias and points it at the new namespace, for example `using LiteBusAuditRecord = LiteBus.Auditing.Abstractions.AuditRecord;`. Analyzer metadata names and the `litebus_required_declarations` matching follow the move, so LB1018 and LB1020 keep working without configuration changes.

## Envelopes Without a Handler Need an Acknowledgement

`InProcessOutboxDispatchOptionsBuilder.RequireHandler` is replaced by `AllowEnvelopesWithoutHandler(string reason)`. The boolean read as a tuning flag, but turning it off marked every message published without effect when the handler assembly was not scanned, while the backlog read zero. The call states why publishing to zero handlers is intended, and the reason stays visible: a startup task logs it at Warning (EventId 2201), and `LiteBusCompositionSummary.RelaxedSafeguards` lists it on the startup line.

```csharp
// Before
outbox.UseInProcessDispatch(dispatch => dispatch.RequireHandler = false);

// After
outbox.UseInProcessDispatch(dispatch => dispatch.AllowEnvelopesWithoutHandler(
    "Leaf service with no local subscribers yet; envelopes intentionally complete."));
```

`InProcessOutboxDispatchOptions.RequireHandler` stays as a get-only property, and `MissingHandlerReason` carries the acknowledgement. Code that only read the option compiles unchanged. A null or whitespace reason throws `ArgumentException`, because an acknowledgement that says nothing is the boolean again.

## Immediate Dispatch Without Per-Handler Delivery Fails Composition

In v7, `EnableImmediateDispatch` without `EnablePerHandlerDelivery` produced event-level immediacy, and a `[DispatchImmediately]` marker on a handler class was ignored without an error: the projection it was meant to refresh waited for the processor poll, and the screen read after the command intermittently showed stale data. In v8, composition fails with `LiteBusConfigurationException` when immediate dispatch is enabled, per-handler delivery is off, and any registered handler class carries `[DispatchImmediately]`. The message names the handler types and says to call `EnablePerHandlerDelivery()`.

```csharp
// Before: composed, and handler-level immediacy silently never applied.
outbox.EnableImmediateDispatch();

// After, when the markers sit on handler classes: give each handler its own envelope.
outbox.EnableImmediateDispatch().EnablePerHandlerDelivery();
```

When event-level immediacy is what the application wants, move the marker from the handler class to the event type instead:

```csharp
// Before: ignored without per-handler delivery.
[DispatchImmediately]
internal sealed class UpdateCashProjection : IEventHandler<CashPosted> { ... }

// After: event-level immediacy, which needs no per-handler envelopes.
[DispatchImmediately]
public sealed record CashPosted(Guid AccountId, decimal Amount) : IEvent;
```

The check runs as a composition validation, because the event axis registers its handlers after the outbox module builds. Both direct and indirect main handlers are validated, and one handler class observing several messages is named once.

An immediate-addressed envelope staged with scheduled visibility is still never immediate, which is correct, but it is no longer silent. The envelope factory logs at Debug (EventId 2013) naming the envelope id, the contract, and the handler, and adds 1 to the `litebus.outbox.immediate_dispatch.skipped_scheduled` counter on the `LiteBus.Outbox` meter, tagged with `litebus.contract.name`. The names are the public constants `ImmediateDispatchSkippedScheduledInstrumentName` and `ImmediateDispatchContractAttributeName` on `LiteBusOutboxTelemetry`, and the existing OpenTelemetry package exports the counter with no change. A handler marked immediate whose events are always enqueued with `ScheduledAfter` shows up there instead of looking like normal processor latency.

## Entity Framework Core Checks Run at Startup

In v7, a missing context registration composed cleanly and failed on the first transactional accept or enqueue, and resolving `ITransactionalOutbox<X>` for a context never passed to `UseDbContext<X>()` failed late the same way. In v8 both fail before the first write. The inbox and outbox storage modules register a startup task that resolves the configured context from a new scope and raises `DurableStorageConfigurationException` naming the missing `AddDbContextFactory<TContext>` registration, and the outbox module registers an open-generic guard so resolving the transactional outbox for an unconfigured context raises `LiteBusConfigurationException` naming the missing `UseDbContext<X>()` call.

```csharp
// Before: UseDbContext<OrdersDbContext>() with no context registration composed and failed on
// the first transactional write.

// After: register the context. The factory call also registers the scoped OrdersDbContext the
// transactional writers resolve. An application that also calls AddDbContext passes
// optionsLifetime: ServiceLifetime.Singleton so the singleton factory reads no scoped options.
services.AddDbContextFactory<OrdersDbContext>(options => ...);
```

```csharp
// Before: a handler injects ITransactionalOutbox<BillingDbContext> while the storage builder
// configures OrdersDbContext. v7 failed on the first enqueue; v8 fails at resolve time naming
// the missing call.
// After: configure the context the handlers resolve. The builder holds one context type.
outbox.UseEntityFrameworkCoreStorage(ef => ef.UseDbContext<BillingDbContext>());
```

The startup task resolves the context from an application container scope, so it observes the same registrations the writers do. LB1026 reports the `UseDbContext` mismatch at build time for the outbox side; see [New Analyzers](#new-analyzers). The complete registration, with the interceptor on the factory registration, is on the [ASP.NET Core with Entity Framework Core and Outbox](../getting-started/aspnetcore-efcore-outbox.md) page.

## A Second Add Call Configures Instead of Throwing

In v7, calling `AddCommands` twice threw `LiteBusConfigurationException` for the duplicate module registration, so every assembly's handlers, contracts, and recurring jobs were configured in one central call. In v8, every `Add*` registration extension checks `IModuleRegistry.Find<TModule>()` first: when the module exists, the action runs on that module's builder instead of registering a second module, so two calls configure one composition.

```csharp
// Before: the second call threw for the duplicate module registration.
// After: both calls configure the one command module.
liteBus.AddCommands(commands => commands.RegisterFromAssembly(typeof(OrdersModule).Assembly));
liteBus.AddCommands(commands => commands.RegisterFromAssembly(typeof(BillingModule).Assembly));
```

That is what application modules build on: each assembly implements `IApplicationModule.Configure(ILiteBusBuilder)` with the same `Add*` calls the host uses, and the host registers them with `AddApplicationModule<TModule>()` or discovers them with `AddApplicationModulesFromAssembly(assembly)`.

`AddAuthorizationPolicies` merges the same way: each call adds its policies, conditions and ports to one policy set. A policy name registered twice still fails composition, and so does a second `UsePermissionLookup` or `UseSignInInstantSource` with a different type.

```csharp
using LiteBus.Runtime;
using LiteBus.Runtime.Abstractions;

public sealed class LedgerModule : IApplicationModule
{
    public void Configure(ILiteBusBuilder liteBus)
    {
        liteBus.AddCommands(commands => commands.RegisterFromAssembly(typeof(LedgerModule).Assembly));
        liteBus.AddOutbox(outbox => outbox.Contracts.Register<EntryPosted>("ledger.entry-posted"));
    }
}

// In the host composition.
liteBus.AddApplicationModule<LedgerModule>();
```

A configuration call after `BuildOrder` froze the registry throws as in v7. Code that caught the duplicate-module exception to detect a double registration changes behavior: the second call now succeeds and merges. See [Application Modules](../architecture/application-modules.md).

## HTTP Refusals Map Through a Catalog

In v7, `MediationResultHttpExtensions.ToHttpResult` mapped by outcome: an idempotency refusal kept its own status, any other denial answered 403, and a validation failure answered 400. In v8 the refusal code decides through an `IRefusalProblemCatalog`, so one client handler reads every refusal the same way. The default catalog answers a missing declaration, an authorization denial, and a missing tenant with 403; a caller that is not signed in with 401; a validation failure with 422; a concurrency conflict with 409; and anything unmapped with 400. The problem type is a stable `urn:litebus:` value derived from the code, with dots replaced by colons.

That changes what two refusals answer:

| Refusal | v7 | v8 |
| --- | --- | --- |
| Denial with no code, or with a code no mapping covers (such as `NOT_PERMITTED`) | 403 | 400 |
| Single validation failure with a `validation.*` code | 400 | 422 |

Unchanged: both idempotency refusals (409 and 422 with the same titles and types), validation failures with no code or several failures (400 with the same title and the `urn:litebus:mediation:invalid` type), and mapped authorization and declaration denials (403 with the type now derived from the code, such as `urn:litebus:authorization:forbidden`). Three codes are new in v8: `authorization.not-signed-in` answers 401, `tenancy.required` answers 403, and `concurrency.conflict` answers 409.

An Invalid decision carries the single failure's code, or null when the stage collected several, so only a lone `Validity.Invalid(message, member, "validation.amount")` takes the 422 path. Give every guard denial a code under a mapped prefix, and map the product's own codes on a catalog built from the defaults:

```csharp
// Before: v7 answered every custom denial with 403 from the outcome alone.
Verdict.Deny("not permitted", code: "NOT_PERMITTED");

// After: map the product vocabulary once, and register the catalog in request services.
var catalog = RefusalProblemCatalog.CreateDefault();
catalog.Map("orders.*", StatusCodes.Status403Forbidden, "Request denied");
services.AddSingleton<IRefusalProblemCatalog>(catalog);
```

`ToHttpResult` also accepts the catalog per call as an optional last argument, and falls back to `RefusalProblemCatalog.Default` when request services hold none. An exact mapping wins over a prefix pattern, and the longest prefix wins when several patterns cover one code. Do not map on `RefusalProblemCatalog.Default` itself: it is shared by the process, so build with `CreateDefault()` and register that instance instead. Client tests asserting on status codes, titles, or problem types need the new values.

## Tenant-Scoped Idempotency Keys Changed Format

In v7, the idempotency key resolver read the tenant from the trace tenant entry in the mediation items and joined tenant, scope, and key with colons. In v8 it reads the tenant from the execution identity the mediator resolved, falling back to the trace entry the ASP.NET Core idempotency filter still writes, and joins the tenant with a slash:

```csharp
// Before: tenant:scope:key.
"acme:MyApp.Commands.ApplyPaymentCommand:pay-1"

// After: tenant/scope:key.
"acme/MyApp.Commands.ApplyPaymentCommand:pay-1"
```

Unscoped keys keep the `scope:key` form and are unaffected. Segments escape `/` as well as `\` and `:` now, so the join stays unambiguous.

The stored key is the claim identity, so a tenant-scoped claim applied before the upgrade is not recognized after it: a repeat crossing the upgrade is treated as a new request and runs the handler again. Claims are transient by design, expiring after the store's claim timeout, so the mismatch drains on its own. Deploy when no repeat crossing the upgrade window would double-apply, and prefer a quiet window for commands that replay a stored result, because the stored answer is keyed the same way. Stores are unchanged: the resolver computes the new key and the rows follow.

## Composition Refuses What Could Not Work

Three registrations that composed in v7 fail in v8, each naming the fix:

- Immediate dispatch without per-handler delivery while a registered handler class carries `[DispatchImmediately]` fails composition with `LiteBusConfigurationException`. See [Immediate Dispatch Without Per-Handler Delivery Fails Composition](#immediate-dispatch-without-per-handler-delivery-fails-composition).
- An Entity Framework Core store whose configured context does not resolve from a new scope fails startup with `DurableStorageConfigurationException`, and resolving `ITransactionalOutbox<X>` for an unconfigured context fails with `LiteBusConfigurationException`. See [Entity Framework Core Checks Run at Startup](#entity-framework-core-checks-run-at-startup).
- A message whose authorization declaration names a policy that no `AddAuthorizationPolicies` call registered fails composition with `LiteBusConfigurationException`, naming each unknown policy and the messages that use it. In v7 the typo surfaced as a denial on the first request.

`catch (LiteBusConfigurationException)` keeps working and still catches all of them, including `DurableStorageConfigurationException`, which derives from it.

## Interfaces That Gained Members

These are infrastructure contracts implemented by LiteBus itself. Applications that only implement handlers are unaffected. Custom implementations, including test doubles, must add the members. Defaults are noted where a custom implementation compiles unchanged.

| Interface | Added members | Notes |
| --- | --- | --- |
| `IExecutionContext` | `Identity` | Has a default returning `ExecutionIdentity.Anonymous`, so custom contexts compile unchanged but observe no caller or tenant until they override it. |
| `IExecutionContext` | `MessageType`, `Parent` | Both have defaults returning `null`, so custom contexts compile unchanged. Nesting rules and `MessagePolicy.SentBy<TParent>()` read the chain through them. |
| `IRefusalProblemCatalog` | `TryResolve(code, out map)` | Has a default that delegates to `Resolve` and cannot tell a fallback apart. Override it to report unmapped codes. |
| `IMessageCatalog` | `MissingDeclaration(valueType, scope)` | Has a default computed from enumeration. |
| `ICheckpointPolicy` | `IsTimeBased` | New contract in 8.0. Defaults to `false`. |
| `MessageCompletionContext` | `Identity` | Defaults to `ExecutionIdentity.Anonymous`. The pipeline sets it from the mediation's execution context. |
| `IModuleRegistry` | `Find<T>()` | Has no default. A custom registry must implement it; the shipped registry finds the registered module of the exact type, including composite children. |
| `OutboxLeaseRequest` | `MaxPerTenant` | Null by default, meaning no cap. A custom outbox store honors it to keep per-tenant fairness. |
| `OutboxProcessorOptions` | `MaxLeasedPerTenant` | Null by default. The processor passes it to the store as `MaxPerTenant`. |
| `CommandMediationSettings`, `QueryMediationSettings`, `EventMediationSettings`, `MessageMediationRequest<TMessage, TMessageResult>` | `Identity` | Null by default, meaning resolve from the enclosing mediation or the registered provider. |
| `AuthorizationGuard<TMessage>` | `CurrentIdentity` | Protected static. Guards read the caller from here instead of from a property every message carries. |
| `InProcessOutboxDispatchOptions` | `MissingHandlerReason` | Null while a handler is required. Carries the acknowledgement otherwise. |
| `LiteBusCompositionSummary` | `RelaxedSafeguards`, `RecordRelaxedSafeguard(string)` | Lists the safeguards the application turned off on purpose, each with its reason. |
| `MartenAuditRecord` | `Segment`, `Sequence`, `PreviousHash`, `Hash`, `HashScheme` | Null and zero for records written without the hash chain, so documents written in v7 read unchanged. A chained record with no `HashScheme` verifies as `sha256-v1`. |
| `MediationResultHttpExtensions.ToHttpResult` | Optional `catalog` parameter | Source-compatible. Null resolves from request services with the default catalog as fallback. |
| `OutboxEnvelopeFactory` | Optional `logger` parameter | Source-compatible. Direct constructions that omit it discard the scheduled-immediate diagnostic. |

## Package Changes

No package is renamed, removed, split, or added. A v7 application keeps its existing references and gains the v8 capabilities through the packages it already holds: tenancy and authorization policies ship in `LiteBus.Messaging` with their contracts in `LiteBus.Messaging.Abstractions`, the refusal catalog and execution identity provider ship in `LiteBus.Extensions.AspNetCore`, and the hash chain and tenant sessions ship in `LiteBus.Commands.Storage.Marten`. The aggregate `LiteBus` package is unchanged. The full inventory is in [Dependency Graph](../architecture/dependency-graph.md).

No NuGet dependency version moves for a `net10.0` application: the 7.2 floors carry over unchanged. Every package now also targets `net11.0`, and that build raises the Microsoft dependencies (EF Core, `Microsoft.Extensions.*`, `Microsoft.AspNetCore.OpenApi` and `System.Security.Cryptography.Pkcs`) to 11.0.0, the release .NET 11 ships with. An application on .NET 11 that uses the Entity Framework Core stores needs a provider built for EF Core 11.

## New Analyzers

In v7 the analyzer range ends at LB1024 (LB1002 and LB1006 are reserved and never shipped). v8 adds LB1025 through LB1028:

| Rule | Condition | Default |
| --- | --- | --- |
| LB1025 | A command handler whose public constructor takes `IOutbox`, in a compilation that references a transactional outbox storage package | Warning |
| LB1026 | A type injecting `ITransactionalOutbox<X>` for a context no `UseDbContext<X>()` call in the compilation configures | Warning |
| LB1027 | Two handlers of different messages sharing one `[SubscriberName]` value | Warning |
| LB1028 | A definition class implementing two or more `IMessageDefinition<TMessage, TValue>` value types | Info |

LB1025 reports the wrong injection at the constructor parameter:

```csharp
// Before: the outbox row commits in its own transaction, apart from the domain write.
public PlaceOrderHandler(IOutbox outbox) { ... }

// After: the row stages in the same DbContext transaction and commits with it.
public PlaceOrderHandler(ITransactionalOutbox<OrdersDbContext> outbox) { ... }
```

The rule reports only when the compilation references a transactional storage package (Entity Framework Core, PostgreSQL, or Marten), because without one there is no transactional injection to switch to. Only public constructors are inspected: a private test-seam constructor is never called by the container. LB1026 runs only when the compilation holds at least one `UseDbContext<TContext>()` call, because the configuring call may otherwise live in another assembly; the fix is the missing call. See [Transactional Outbox Wiring](../catalog/analyzers/transactional-outbox-wiring.md), [Subscriber Names](../catalog/analyzers/subscriber-names.md), and [Definition Concerns](../catalog/analyzers/definition-concerns.md).

LB1026 and LB1027 join the build-only rules: they gather facts as each file is analyzed and report once at compilation end, so editors show them in the error list after a build rather than as underlines while editing. LB1025 and LB1028 report per type as usual. See [Analyzers](../reference/analyzers.md).

## Cross-Assembly Contracts Name Their Registering Assembly

In v7, LB1007 and LB1017 matched registrations only inside the analyzed compilation. A modular monolith that keeps published contracts in a small assembly and registers them where the owning module composes suppressed both rules in every contracts project and lost the check. In v8, the contracts assembly carries `[assembly: MessageContractsRegisteredIn("RegisteringAssembly")]`, and both rules trust the named assembly for the types declared there:

```csharp
// Before: every contracts project suppressed the check it could not satisfy.
#pragma warning disable LB1017 // Registered by the Ledger module assembly.

// After: the check moves to the compilation that registers the contracts.
using LiteBus.Messaging.Abstractions;

[assembly: MessageContractsRegisteredIn("Ledger")]
```

The named assembly's own compilation reports any contract of the attributed assembly that it does not register, without a source location, so the error list names the type rather than underlining a file. The attribute allows multiples for contracts registered by more than one assembly, and names compare without regard to case. Prefer it over suppression: a suppression hides the next missing registration too. See [Contract Registration](../catalog/analyzers/contract-registration.md).

## One Definition Class per Concern

The guide and every example now recommend one definition class per value type: `PlaceOrderCommandAuthorizationDefinition` beside `PlaceOrderCommandAuditDefinition`, rather than one `PlaceOrderCommandDefinition` mixing both. Authorization, audit, tenancy, and idempotency are unrelated decisions, and the registry already keys definitions by value type, so the split costs nothing at runtime: each definition contributes its own type-keyed value, and only a second declaration of the same value for the same message is refused.

```csharp
// Before: one class implementing two unrelated definition contracts.
internal sealed class PlaceOrderCommandDefinition
    : IAuthorizationDefinition<PlaceOrderCommand>, IAuditDefinition<PlaceOrderCommand>
{
    public AuthorizationDeclaration Authorization => AuthorizationDeclaration.Authorized("orders.place");
    public AuditDeclaration Audit => AuditDeclaration.Audited("orders.place-order");
}

// After: each decision readable and reviewable on its own.
internal sealed class PlaceOrderCommandAuthorizationDefinition : IAuthorizationDefinition<PlaceOrderCommand>
{
    public AuthorizationDeclaration Authorization => AuthorizationDeclaration.Authorized("orders.place");
}

internal sealed class PlaceOrderCommandAuditDefinition : IAuditDefinition<PlaceOrderCommand>
{
    public AuditDeclaration Audit => AuditDeclaration.Audited("orders.place-order");
}
```

The registry still accepts the combined class, so nothing breaks; LB1028 is an informational note suggesting the split, naming the concerns and the first split class name. Open generic definitions and definitions in referenced assemblies are never reported, because no split class name can be suggested there. See [Definition Concerns](../catalog/analyzers/definition-concerns.md).

## Subscriber Names Follow One Vocabulary

Per-handler outbox rows record the subscriber name, so the recommended pattern is `<module>.<event>.<reaction>` in kebab segments matching the contract name prefix, such as `ledger.entry-posted.cash-projection`. The mechanics are unchanged: names compare ordinally, dispatch matches a recorded value against both the subscriber name and the handler's full type name, and LB1027 warns when two handlers of different events share one name, which makes rows hard to read in operations tooling and makes renaming one handler change the other's recorded identity:

```csharp
// Before: two reactions share one recorded identity.
[SubscriberName("cash.projection")]
internal sealed class UpdateCashProjection : IEventHandler<EntryPosted> { ... }

[SubscriberName("cash.projection")]
internal sealed class UpdateCashForecast : IEventHandler<EntryReversed> { ... }

// After: each reaction owns its name.
[SubscriberName("ledger.entry-posted.cash-projection")]
internal sealed class UpdateCashProjection : IEventHandler<EntryPosted> { ... }

[SubscriberName("ledger.entry-reversed.cash-forecast")]
internal sealed class UpdateCashForecast : IEventHandler<EntryReversed> { ... }
```

Retire a name in stages: add the new name, deploy, let the processor drain the envelopes recorded under the old one, then remove the old handler. Handlers of the same message may share a name deliberately; the rule only compares across message types. See [Subscriber Names](../catalog/analyzers/subscriber-names.md).

## The Audited Factory Takes Its Facts as Arguments

`AuditDeclaration.Audited` takes the optional category, target kind, and reason requirement as arguments, matching `IMessageDeclarations.Audited(action, category, targetKind, reasonRequired)`. The `with` form still compiles, but a `with` expression cannot take a member access without parentheses, so the natural chain was a syntax error that hid every semantic error behind parse errors:

```csharp
// Before: the with expression needs parentheses before the selector chain.
public AuditDeclaration Audit =>
    (AuditDeclaration.Audited("orders.cancel-order") with
    {
        Category = "money",
        TargetKind = "order",
    }).WithTargetFrom<CancelOrderCommand>(command => command.OrderId.ToString());

// After: the facts are arguments, and the selector chains directly.
public AuditDeclaration Audit =>
    AuditDeclaration.Audited("orders.cancel-order", category: "money", targetKind: "order")
        .WithTargetFrom<CancelOrderCommand>(command => command.OrderId.ToString());
```

Use the argument form in new declarations. `AuditedDeclaration` itself is unchanged apart from its namespace move, so existing `with` refinements keep compiling.

## Behavior Changes Without Code Breaks

Nothing here breaks compilation. Each item changes what happens at runtime for code that compiled in v7.

Mediation:

- The in-process inbox and outbox dispatchers restore the envelope tenant into the mediation identity, so a reaction runs in the tenant of the fact it reacts to. Guards, authorization conditions, and audit attribution observe the tenant on the execution identity instead of only in the mediation items.
- When the application registered no `IAuditActorResolver`, the audit record writer attributes the record from the principal on the execution identity: the `ClaimTypes.NameIdentifier` claim, else the `sub` claim, as `AuditActor.User(id)` with `DisplayName` from `ClaimTypes.Name`. A handler-scoped actor and an explicit resolver win as before, and a mediation with no principal still records a null actor.
- `AuditRecord.TenantId` falls back to the execution identity tenant when the trace items carry none, so tenant-filtered audit queries keep working for mediations that never stamped trace metadata.
- The mediator creates the dispatch scope before the execution context, because identity resolution reads the registered provider from that scope. A custom `IMessageDispatchScopeFactory` observes the scope created earlier relative to context creation; the disposal order is unchanged.
- Nested mediations inherit the enclosing identity unless their settings carry an explicit one, so a handler that sends a guarded command runs it as the same caller without consulting the provider again.

Durable processors:

- Immediate-addressed envelopes staged with scheduled visibility are reported through a Debug log and the `litebus.outbox.immediate_dispatch.skipped_scheduled` counter instead of passing silently. The envelopes still wait for the processor as before.
- Allowing envelopes without a handler logs a Warning at startup and lists the acknowledgement on the composition summary. The dispatch behavior is unchanged.
- Outbox lease calls carry `MaxPerTenant` from `OutboxProcessorOptions.MaxLeasedPerTenant`. The default is null, so batches lease exactly as in v7 until the cap is set.

Stores:

- Every outbox store honors the per-tenant lease cap, including the capped relational path that claims each selected row with its own guarded update. Uncapped leases run the v7 statements unchanged.
- Tenant-scoped idempotency claims resolve under the new `tenant/scope:key` format from the execution identity tenant. Unscoped claims are byte-identical to v7.

Hosting and diagnostics:

- The `LiteBus.Outbox` meter gains the `litebus.outbox.immediate_dispatch.skipped_scheduled` counter. The OpenTelemetry package exports it with no change.
- `LiteBusCompositionSummary` gains the `RelaxedSafeguards` list, so the startup line names what the application turned off on purpose.

## New Capabilities

Nothing here is required to upgrade. Each item is a v8 capability a v7 application gains by adopting it, with the page that documents it.

### Execution Identity on Every Mediation

`ExecutionIdentity` carries the calling principal and the tenant, and the mediator resolves one per mediation: the identity passed on the mediation settings, the identity of an enclosing mediation, the registered `IExecutionIdentityProvider`, and finally `ExecutionIdentity.Anonymous`. It is exposed as `IExecutionContext.Identity`, so messages carry no caller property:

```csharp
// Before: every command and query carried its caller, copied by each endpoint.
public sealed record CloseAccountCommand(string AccountId, Caller Caller) : ICommand;

// After: the pipeline resolves the caller once, and guards read it from the context.
public sealed record CloseAccountCommand(string AccountId) : ICommand;
```

Set the identity on the settings when the caller is known only at the call site, such as a job running on behalf of one tenant:

```csharp
await _commands.SendAsync(
    command,
    new CommandMediationSettings { Identity = ExecutionIdentity.ForTenant(workspaceId) },
    cancellationToken);
```

ASP.NET Core hosts register the provider that reads `HttpContext.User` with one call, naming the tenant claim when it is not `tenant_id`:

```csharp
services.AddLiteBusExecutionIdentity(options =>
{
    options.TenantClaimType = "tenant_id";
});
```

A principal is never persisted: durable dispatchers restore the tenant only. See [The Execution Context](../concepts/execution-context.md) and [ASP.NET Core Execution Identity](../integrations/aspnetcore-execution-identity.md).

Removing a caller property from a durable command or event contract is wire-compatible for JSON-serialized contracts. A payload written before the upgrade still carries the property, and the deserializer ignores a member the type no longer has. A payload written after the upgrade simply lacks it. No contract version bump is needed, and no drain beyond the idempotency claim window: the handler reads the caller from `IExecutionContext.Identity`, which the dispatcher restores as the envelope's tenant with no principal. A contract that uses a serializer configured to reject unknown members, such as `JsonUnmappedMemberHandling.Disallow`, keeps the property until in-flight envelopes drain.

### Tenancy Positions and the Tenancy Guard

`TenancyDeclaration` states whether a message runs inside a tenant, across tenants for a stated reason, or outside any tenant, declared on a definition class, with attributes, or through `IMessageDefinition<TMessage>.Describe`:

```csharp
internal sealed class PostManualEntryCommandTenancyDefinition : ITenancyDefinition<PostManualEntryCommand>
{
    public TenancyDeclaration Tenancy => TenancyDeclaration.Required();
}
```

`[TenantRequired]`, `[CrossTenant("retention job")]`, and `[NoTenant("sign-in")]` are the attribute forms. `UseTenancy()` registers the open-generic guard for every message, and `RequireDeclaration<TenancyDeclaration>()` fails composition for a message that states no position, so a missing tenant check fails startup rather than leaking data between customers:

```csharp
registry.AddMessaging(messaging => messaging
    .UseTenancy()
    .RequireDeclaration<TenancyDeclaration>());
```

A message requiring a tenant and mediated without one is denied with `tenancy.required`, which answers 403 through the default refusal catalog. Cross-tenant and tenantless positions allow, and an undeclared message is allowed until the declaration is required. See [Tenancy](../concepts/tenancy.md) and [Security and Tenancy](../operations/security-and-tenancy.md).

### Ambient Tenant Propagation

`UseAmbientTenant()` on the outbox and inbox module builders stamps the ambient execution identity tenant onto envelopes whose items carry `TenantScope.Unscoped`. An explicit `TenantScope.Isolated` on the item always wins, and outside a mediation the envelope is identical to one enqueued without the option:

```csharp
liteBus.AddOutbox(outbox => outbox.UseAmbientTenant());
```

Staged domain events stamp the ambient tenant the same way when the option is on. The precedence reads beside `UseAmbientTrace`: an explicit item tenant beats the ambient value, and the ambient value beats unscoped. The in-process dispatchers restore the stored tenant into the reaction's identity, so propagation round-trips without application code. See [Tenancy](../concepts/tenancy.md).

### Composable Authorization Policies

`AddAuthorizationPolicies` registers named policies built from combinators, conditions every message evaluates, and the permission lookup, with one fixed evaluation order: conditions in registration order, then the named policy, with the first deny winning.

```csharp
registry.AddMessaging(messaging => messaging.AddAuthorizationPolicies(policies => policies
    .Add("vaults.open", MessagePolicy.All(MessagePolicy.SignedIn(), MessagePolicy.Permission("vaults.open")))
    .AddCondition<BusinessHoursCondition>()
    .UsePermissionLookup<RolePermissionLookup>()));
```

Messages name their policy with the existing authorization declarations: `[Authorized("vaults.open")]`, `IAuthorizationDefinition<TMessage>`, or `AuthorizationDeclaration.Authorized("vaults.open")`. The combinators are `SignedIn`, `Permission`, `Claim`, `RecentSignIn` (against the `auth_time` claim), `System` (no calling principal), `Self` (the message's subject equals the principal), `All`, `Any`, `When`, `Allow`, and `Deny`. An unknown policy name denies with `authorization.unknown-policy` rather than passing a message whose rule is missing, and a permission check with no lookup registered denies with `authorization.permission-lookup-missing`. Adopting the guard obliges every message to state an authorization position: an undeclared message denies with `declaration.missing`, and an exempt one allows. See [Authorization Policies](../concepts/authorization-policies.md).

### Application Modules

Each assembly implements `IApplicationModule.Configure(ILiteBusBuilder)` with the handlers, contracts, and recurring jobs it owns, and the host registers modules explicitly or discovers them from an assembly in type-name order. See [A Second Add Call Configures Instead of Throwing](#a-second-add-call-configures-instead-of-throwing) and [Application Modules](../architecture/application-modules.md). Custom declaration checks that do not fit `RequireDeclaration` belong in `ValidateComposition(Action<IMessageCatalog>)`, which runs the application's own rule over every registered message after every module is built.

### Per-Tenant Outbox Fairness

`OutboxProcessorOptions.MaxLeasedPerTenant` caps how many envelopes of one tenant a single lease returns, so one busy tenant cannot fill every batch while others wait. Unscoped envelopes count as one tenant, and envelopes past the cap stay pending for a later call in the store's usual order. Every outbox store honors it, and the shared contract tests prove it. Leave it null for the v7 behavior.

### Tamper-Evident Audit Trail

The `LiteBus.Auditing` package family records every audited mediation with a sequence number and a hash linked to its predecessor, on Marten, PostgreSQL or EF Core. Every piece is replaceable: the stored document, the segments, the canonical form, the hash scheme, the checkpoint policy, the signers, the publishers and the checkpoint sources.

```csharp
services.AddLiteBus(liteBus => liteBus.AddAuditing(auditing => auditing
    .UseMartenStore()
    .UseHashChain(chain => chain
        .CheckpointWhen(CheckpointPolicies.EveryRecords(100))
        .PublishCheckpointsTo<LogCheckpointPublisher>())));
```

By default, success records commit with the business change and are linked after commit, so the trail never records a change that rolled back. Checkpoints are stored before they are published, and a background retrier publishes them, so a failed publish is retried rather than lost. `IAuditChain` verifies a segment by pages against every registered checkpoint source, lists segments, expires a segment for retention, and erases a segment or tenant without publishing an anchor. See [Auditing](../concepts/auditing.md#hash-chained-audit-storage).

### Marten Tenant Sessions

`UseMartenTenantSessions()` registers a singleton `MartenTenantSessionFactory` that opens lightweight sessions for the ambient tenant, so handlers work on tenant-filtered documents without resolving the tenant themselves:

```csharp
commands.UseMartenTenantSessions();

public sealed class GetLedgerHandler : IQueryHandler<GetLedger, Ledger>
{
    private readonly MartenTenantSessionFactory _sessions;

    public GetLedgerHandler(MartenTenantSessionFactory sessions) => _sessions = sessions;
}
```

The application must configure Marten for conjoined tenancy (`AllDocumentsAreMultiTenanted` with a multi-tenancy source). Without it, opening a tenant session fails in Marten rather than filtering silently. Outside a mediation, or when the mediation runs outside any tenant, the factory opens a default session. See [Marten Unit of Work, Idempotency, and Audit](../integrations/commands-marten.md).

### Marten Concurrency Refusals

`MartenConcurrencyRefusalClassifier`, registered with `UseFaultRefusalClassifier<MartenConcurrencyRefusalClassifier>()`, maps a Marten concurrency fault and event-stream version conflicts to a denial with `concurrency.conflict`, beside the PostgreSQL constraint classifier. Through the default refusal catalog it answers 409, so a lost optimistic-concurrency race reads as a conflict rather than a failure. Cancellation is never classified, as with every classifier.

## Removed and Renamed Identifiers

Search application code for these v7 identifiers:

- `AuditActor`, `AuditDeclaration`, `AuditedDeclaration`, `AuditExemptDeclaration`, `AuditedAttribute`, `AuditExemptAttribute`, `AuditOutcome`, `AuditReasonMissingException`, `AuditRecord`, `IAuditActorResolver`, `IAuditDefinition`, `IAuditOutcomeMapper`, `IAuditRecordWriter`, `IAuditScope`, `IAuditTrail` in `LiteBus.Messaging.Abstractions` (in v8: `LiteBus.Messaging.Abstractions.Auditing`)

- `dispatch.RequireHandler = false` calls (in v8: `dispatch.AllowEnvelopesWithoutHandler(reason)`)
- `EnableImmediateDispatch` without `EnablePerHandlerDelivery` beside handler-level `[DispatchImmediately]` (in v8: fails composition)
- `UseDbContext<TContext>` with no context registration (in v8: fails startup; add `AddDbContextFactory<TContext>`)
- `ITransactionalOutbox<X>` resolved for an unconfigured `X` (in v8: throws naming `UseDbContext<X>()`)
- `IOutbox` injected into command handlers (in v8: LB1025; inject `ITransactionalOutbox<TContext>`)
- `tenant:scope:key` idempotency key expectations (in v8: `tenant/scope:key`)
- Code-less `Verdict.Deny(reason)` and unmapped denial codes (in v8: answer 400 through the refusal catalog)
- `urn:litebus:mediation:denied` and `urn:litebus:mediation:invalid` expectations for coded refusals (in v8: the type derives from the code)
- Second `Add*` calls expected to throw (in v8: they configure the one module)
- One definition class implementing two definition contracts (in v8: LB1028 suggests the split)
- One `[SubscriberName]` value on handlers of different messages (in v8: LB1027; use `<module>.<event>.<reaction>`)
- LB1007 and LB1017 suppressions in contracts assemblies (in v8: `[assembly: MessageContractsRegisteredIn("...")]`)
- `AuditDeclaration.Audited("...") with { ... }.WithTargetFrom(...)` chains (in v8: pass `category:`, `targetKind:`, and `reasonRequired:` to `Audited`)

Use `rg` or the IDE symbol search across application, test, deployment, and documentation repositories. Copied samples and migration scripts often retain old package names after the main project compiles.
