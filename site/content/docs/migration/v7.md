# Migration Guide v7

LiteBus 7.0 separates deciding whether work happens from doing the work. Mediation gains four decision stages that run in a fixed order (guards, validators, shortcuts, pre-handlers), plus a completion stage that observes every ending. Validation reports verdicts instead of throwing, and auditing, message metadata, and in-process idempotency build on those stages.

The synchronous handler layer, `IExecutionContext.Abort`, and the untyped `IMessageHandler.Handle` dispatch are removed, so most breaks surface as compile errors.

Four runtime changes need attention during rollout. The PostgreSQL outbox schema moves to version 2 and upgrades automatically at startup. Kafka and SQS route and content-type metadata move to shared header names with no fallback. AMQP ingress scopes its idempotency key to the queue. Rows encrypted through a contextual payload encryptor must drain before deployment, because v7 binds the context that v6 never wrote.

## Upgrade Checklist

1. Update LiteBus package references to 7.0.0 and rebuild. The target framework stays `net10.0`.
2. Convert validators to return `Validity`, or derive them from `ThrowingCommandValidator` / `ThrowingQueryValidator` to get the build passing first, then convert module by module afterwards.
3. Replace synchronous pre-handlers and post-handlers with the asynchronous contracts, rename the `IAsyncMessagePreHandler` / `IAsyncMessagePostHandler` aliases, and rename `IAsyncMessageErrorHandler` to `IMessageErrorHandler`.
4. Replace `IExecutionContext.Abort` with a guard, a shortcut, or `SuppressPostHandlers`, whichever the call meant, and delete hand-written `object IMessageHandler.Handle(object)` implementations.
5. Rename `ParallelFaultMode` to `HandlerFaultMode` (and `AggregateAll` to `ContinueAndAggregate`), rename `IPreHandlerDescriptor` to `IPreStageHandlerDescriptor` with its collections, and update custom mediation strategies to the `LiteBus.Messaging` namespace with `RunAsyncPreStages` and the new error-runner signature.
6. Set `HookFailurePolicy` explicitly where the service relied on dead-lettering after a hook failure, and update processor-hook `using` directives to `LiteBus.Messaging.Abstractions.Processing`.
7. Extend custom stores, work signals, registries, descriptors, execution contexts, and host adapters with the members listed under [Interfaces That Gained Members](#interfaces-that-gained-members).
8. For Kafka and SQS, upgrade publishers and consumers of each queue or topic together. Version 7.0 readers do not see the old `Route` / `ContentType` names. On Kafka, resolve `ITransportPublisher` instead of the bare producer and set `SocketTimeoutMs` / `MessageSendMaxRetries` where `MessageTimeoutMs` set those in v6. Set `Mandatory = false` on direct `ITransportPublisher` calls that relied on the v6 default. Do not share one Kafka `IConsumer<string, byte[]>` across consumers or dispose it externally. Each `KafkaConsumer` owns its client. Await `WaitUntilStoppedAsync` to observe a terminal Kafka or SQS loop failure, because `StopAsync` no longer throws it.
9. Drain AMQP ingress queues before redeploying when a duplicate delivery matters. The broker-scoped idempotency key is now scoped to the queue, and the `litebus-message-id` header applies only with `TrustApplicationHeaders`. Catch `InvalidOperationException` instead of `AmqpTransportConfigurationException` for a second `AmqpConsumer.StartAsync`.
10. Drain the inbox and outbox before deploying when payload encryption uses an `IContextualPayloadEncryptor`. Version 6.0 encrypted rows without the context, which v7 cannot decrypt. Let every pending row reach a terminal state first.
11. Let the PostgreSQL outbox upgrade from version 1 to version 2 at startup, or run the v2 upgrade script through the application migration process when schema initialization is disabled. Generate an Entity Framework Core migration for the `handler` column. Create the idempotency and recurring-lease tables only when adopting those packages.
12. Give saga purges a predicate or a `Take` limit, and handle `OutboxManagementException` from retention purges without a configured retention period.
13. Catch the derived composition exception where code distinguished failure categories, enable the analyzers that fit the codebase, and expect build-only rules in the error list after a build rather than as underlines while editing.
14. Run the test suite. A validator that threw in v6 and returns a verdict in v7 appears as a behavior difference in tests that asserted on the exception type. A test double stubbed once per test behaves the same way. `TestQueryMediator.NextResult` is consumed once per call in v7.

## Major Changes in v7

In v6, every pre-handler ran through one stage ordered by a priority number the author had to remember. Validators were pre-handlers that threw, so malformed input produced a fault that looked like a database timeout, and error handlers could not distinguish the two. Stopping the pipeline meant calling `Abort`, which threw an exception carrying an optional result, and synchronous and asynchronous handler contracts existed side by side with near-identical names. There was no stage that observed how a mediation ended, no vocabulary for refusing a message versus answering it, and no place to record an audit entry that covers denied and failed mediations as well as successful ones.

In v7, deciding and doing are separate contracts. Guards refuse with a `Verdict`, validators answer with a `Validity`, shortcuts answer with a `Shortcut`, and pre-handlers prepare work that is going to happen. The framework runs those four stages in that fixed order, then the main handler, post-handlers, and error handlers as in v6, then a completion stage that observes every ending exactly once. A refusal carries a reason and a code, reports `MediationOutcome.Denied` or `MediationOutcome.Invalid`, and reaches the caller as an exception or, with a refusal mapper registered, as a value. Every break in that vocabulary is a compile error rather than a silent behavior change, which is deliberate. A validator left compiling would have kept reporting malformed input as a fault.

## Validators Return a Value

`ICommandValidator<TCommand>.ValidateAsync` and `IQueryValidator<TQuery>.ValidateAsync` return `Task<Validity>` instead of `Task`, and both derive from `IMessageValidator<TMessage>` rather than from the pre-handler contract. `IEventValidator<TEvent>` is the new event-axis contract.

```csharp
// Before
public Task ValidateAsync(TransferCommand command, CancellationToken cancellationToken = default)
{
    if (command.Amount <= 0)
    {
        throw new ArgumentOutOfRangeException(nameof(command));
    }

    return Task.CompletedTask;
}

// After
public Task<Validity> ValidateAsync(TransferCommand command, CancellationToken cancellationToken = default)
{
    return Task.FromResult(command.Amount <= 0
        ? Validity.Invalid("the amount must be positive", nameof(command.Amount))
        : Validity.Valid);
}
```

Three things change with it. Validation is its own stage, running after guards and before shortcuts, so a malformed message cannot claim an idempotency key or collect a cached answer. Every validator runs and the stage collects their failures, so a caller sees all of them at once. The mediation reports `MediationOutcome.Invalid` rather than `Failed`, so an audit trail distinguishes malformed input from a database timeout, and error handlers never see it.

A validator that genuinely needs to fault, because something it depends on is unreachable, still throws. That is a fault, not a verdict about the message.

See [Validation](../concepts/validation.md) for adapting an external validation library, and [Moving a Validator That Threw](../concepts/validation.md#moving-a-validator-that-threw) for the conversion walkthrough.

### Incremental Validator Conversion

The signature change is a compile break in every validator at once, which for a codebase with a hundred of them is a single commit nobody can review. `ThrowingCommandValidator<TCommand, TException>` and `ThrowingQueryValidator<TQuery, TException>` exist so the build passes before conversion starts.

Derive from the adapter, move the v6 body across unchanged, and translate the exception once:

```csharp
public sealed class TransferCommandValidator
    : ThrowingCommandValidator<TransferCommand, ValidationException>
{
    protected override Task ValidateOrThrowAsync(
        TransferCommand command,
        CancellationToken cancellationToken)
    {
        // The v6 body, unchanged.
        var errors = new ErrorCollection();

        if (command.Amount <= 0)
        {
            errors.Add(nameof(command.Amount), "the amount must be positive");
        }

        errors.ThrowIfInvalidCommand();
        return Task.CompletedTask;
    }

    protected override Validity Describe(ValidationException exception) =>
        Validity.Invalid(exception.Errors.Select(e => new ValidationFailure(e.Message, e.Member)));
}
```

Only the exception type named in the type argument is caught. Anything else propagates and ends the mediation as a failure, which keeps a genuine fault inside a validator from being reported as a verdict about the message.

Adapted and converted validators mix freely in one mediation. The stage collects failures across both shapes, so a half-converted codebase behaves correctly rather than only once the last file merges. That is what makes the migration reviewable. Adapt everything mechanically in one pass, then convert module by module.

Two things the adapter cannot do, both worth knowing before relying on it:

- A throwing body stops at the first problem, so a message with three malformed fields still reports one failure. Recovering the collected-failures behavior needs a real conversion.
- Nothing requires removing the adapter. Treat it as temporary code with a deletion date, not a supported shape, or the codebase keeps the validation model that v7 replaces.

## Guards Refuse, Shortcuts Answer, and the Order Is Fixed

In v6, the only way to stop the pipeline was `Abort` from a pre-handler. In v7, a guard that refuses or a shortcut that answers stops the pipeline before the work, and the framework fixes the order the four pre-stage roles run in. Guards run first, then validators, then shortcuts, then pre-handlers. Priority orders handlers inside a stage and never reorders the stages, so a globally registered cache shortcut cannot answer a caller that a message-specific authorization guard would deny, and a malformed message cannot claim an idempotency key. The order states what each stage may assume about its input. A guard sees every message. A validator sees only messages the caller is allowed to send. A shortcut sees only well-formed ones. A pre-handler sees only messages that are going to be handled.

A guard implements `IMessageGuard<TMessage>` and returns a `Verdict` from `DecideAsync`, with the axis contracts `ICommandGuard<TCommand>`, `IQueryGuard<TQuery>`, and `IEventGuard<TEvent>`. Stream queries use `IQueryGuard<TQuery>`. A refusal always carries a reason, may carry a code, and reports `MediationOutcome.Denied`.

```csharp
// Before: a v6 pre-handler that stops the pipeline by aborting.
public Task PreHandleAsync(TransferCommand command, CancellationToken cancellationToken = default)
{
    if (!_policy.Allows(command))
    {
        AmbientExecutionContext.Current.Abort();
    }

    return Task.CompletedTask;
}

// After: the guard supplies a reason and a code; one mapper decides what a refused caller receives.
public Task<Verdict> DecideAsync(TransferCommand command, CancellationToken cancellationToken = default)
{
    return Task.FromResult(_policy.Allows(command)
        ? Verdict.Allow
        : Verdict.Deny("not permitted", code: "NOT_PERMITTED"));
}

public sealed class ResultRefusalMapper : ICommandRefusalMapper<ICommand, Result>
{
    public Result Map(ICommand command, Refusal refusal) => refusal.Outcome switch
    {
        MediationOutcome.Denied  => Result.Forbidden(refusal.Code, refusal.Reason),
        MediationOutcome.Invalid => Result.Invalid(refusal.Reason),
        _                         => Result.Failure(refusal.Reason)
    };
}
```

One registration against `ICommand` covers every command producing that result type, and it covers validation failures at the same time. A mapper registered against a concrete message takes precedence over one registered against a base type. Two at the same level raise `PipelineContractException` rather than resolving by assembly scanning order.

When no mapper is registered, a refusal reaches the caller as `LiteBusMessageDeniedException` (with `DeniedBy` naming the guard or shortcut) or `LiteBusMessageInvalidException` (with `RejectedBy` and every collected failure in `Failures`).

A shortcut implements `IMessageShortcut<TMessage>` or `IMessageShortcut<TMessage, TMessageResult>` and returns a `Shortcut` from `TryAnswerAsync`, with the axis contracts `ICommandShortcut<TCommand>`, `ICommandShortcut<TCommand, TCommandResult>`, `IQueryShortcut<TQuery, TQueryResult>`, `IStreamQueryShortcut<TQuery, TQueryResult>`, and `IEventShortcut<TEvent>`. Answering a message that produces a result always supplies the value, so a stream shortcut that means the caller enumerates nothing states that explicitly:

```csharp
return Shortcut<IAsyncEnumerable<Product>>.Answer(AsyncEnumerable.Empty<Product>(), "nothing to stream");
```

The untyped `Shortcut.Answer(reason)` serves messages that produce no result. `Shortcut.Deny(reason, code)` ends the mediation exactly as a guard denial does, for decisions that can only be made at the shortcut stage, such as an idempotency claim. Registering an untyped shortcut for a message that produces a result fails composition with `PipelineContractException`, and [LB1019](../reference/analyzers.md) reports it at build time.

See [Deciding Whether the Work Happens](../concepts/handler-pipeline.md#deciding-whether-the-work-happens) and [Guard Discovery and Ordering](../concepts/handler-pipeline.md#guard-discovery-and-ordering). Each word in the stage vocabulary names exactly one thing across the whole API. [Pipeline Vocabulary](../reference/glossary.md#pipeline-vocabulary) is the list, and it applies where a page and a type name disagree.

## The Completion Stage Observes Every Ending

`IMessageCompletionHandler<TMessage>`, `IMessageCompletionHandler<TMessage, TMessageResult>`, and the axis contracts `ICommandCompletionHandler`, `IQueryCompletionHandler`, and `IEventCompletionHandler` run in a `finally` on every mediation path, exactly once. Each handler receives a read-only `MessageCompletionContext` carrying the message, the outcome, the result, the exception, the reason, the code, and the elapsed duration. Post-handlers run only when the main handler succeeds and error handlers only for recoverable exceptions, so no earlier stage could observe how a message actually ended. Recording an audit entry, emitting a metric, or closing a unit of work belongs here.

The completion stage is not cancellable. Handlers receive `CancellationToken.None`, because the ending has already happened and handing the stage the token whose cancellation ended the mediation would drop exactly the records a review looks for. Unlike every other role, completion orders handlers by priority alone, with no direct-before-indirect split. Completion handlers observe an ending rather than wrapping the handler, so there is no wrapping layer for a specific handler to sit inside.

## The Synchronous Handler Layer Is Removed

In v6, `IMessagePreHandler<TMessage>` declared `object PreHandle(TMessage)` and `IMessagePostHandler<TMessage, TMessageResult>` declared `object PostHandle(TMessage, TMessageResult?)`, with `IAsyncMessagePreHandler<TMessage>`, `IAsyncMessagePostHandler<TMessage>`, and `IAsyncMessagePostHandler<TMessage, TMessageResult>` holding the `Task` members beside them. Every handler is asynchronous in v7, so the `IAsync` names are removed and the members they declared moved to `IMessagePreHandler<TMessage>` and `IMessagePostHandler<TMessage, TMessageResult>`.

| Before | After |
| --- | --- |
| `IAsyncMessagePreHandler<TMessage>` | `IMessagePreHandler<TMessage>` (interface name only) |
| `IAsyncMessagePostHandler<TMessage>` | `IMessagePostHandler<TMessage, object>` |
| `IAsyncMessagePostHandler<TMessage, TMessageResult>` | `IMessagePostHandler<TMessage, TMessageResult>` |
| Synchronous `PreHandle` / `PostHandle` | Asynchronous `PreHandleAsync` / `PostHandleAsync` |
| `IAsyncMessageErrorHandler<TMessage>` and `<TMessage, TMessageResult>` | `IMessageErrorHandler<TMessage>` and `<TMessage, TMessageResult>` (interface name only) |
| Non-generic `IMessagePreHandler` discovery marker | `IMessagePreStageHandler` (the pre stage holds four roles, so the marker cannot share the name of `IMessagePreHandler<TMessage>`, the one unnamed role in that stage) |

```csharp
// Before: a synchronous v6 pre-handler written against the messaging-level contract.
public object PreHandle(TransferCommand command)
{
    command.Normalize();
    return command;
}

// After.
public Task PreHandleAsync(TransferCommand command, CancellationToken cancellationToken = default)
{
    command.Normalize();
    return Task.CompletedTask;
}
```

The axis contracts are unchanged at the call site. `ICommandPreHandler<TCommand>`, `IQueryPostHandler<TQuery, TResult>`, `IStreamQueryPostHandler<TQuery, TQueryResult>`, and their siblings compile as they are and derive from `IMessagePreHandler<TMessage>` and `IMessagePostHandler<TMessage, TMessageResult>` directly. Only code that named an alias or a synchronous member explicitly needs a change. The non-generic `IMessagePostHandler` keeps its shared name, because the post stage holds a single role. `IAsyncMessageHandler` keeps its prefix, because there the prefix distinguishes the `Task`-returning specialization of `IMessageHandler<TMessage, TMessageResult>` from `IStreamMessageHandler`, the `IAsyncEnumerable` one.

## IExecutionContext.Abort Is Removed

`IExecutionContext.Abort` and `LiteBusExecutionAbortedException` are removed. In v6, `Abort` set `MessageResult` and threw an exception the strategies caught to end the mediation, excluding it from error handlers. A pre-handler that stopped the pipeline in v7 implements a guard contract and returns a `Verdict`, or a shortcut contract and returns a `Shortcut` (see [Guards Refuse, Shortcuts Answer, and the Order Is Fixed](#guards-refuse-shortcuts-answer-and-the-order-is-fixed)). The break is a compile error rather than a change in behavior, which is deliberate. A flag that left `Abort()` compiling would have silently started running the statements after it.

Only a guard or a shortcut can stop the pipeline before the work. Stopping means skipping the work, and once the main handler has run there is nothing left to skip. A handler that finished its work but should trigger no reactions calls `SuppressPostHandlers()`, which skips the post-handlers that have not run yet without stopping the calling handler and without changing the outcome. Use it when the work turned out to be a no-op and the reactions to it should not fire, such as an idempotent command that detects it already ran. A main handler returns its result instead of aborting with one.

## Multiple Handler Contracts per Class

`IMessageHandler` has no members. `object Handle(object message)` and its default implementation on `IMessageHandler<TMessage, TMessageResult>` are removed, which lets one class implement several closed handler contracts such as `IEventHandler<OrderRefundSucceeded>` and `IEventHandler<OrderRefundSettledOutsideProcessor>`. Those classes failed with CS8705 in v6. The mediator calls each handler through the closed contract on its descriptor. Delete any hand-written `object IMessageHandler.Handle(object)` implementation. Code that called `Handle(object)` calls the typed contract instead. See [Event Module](../concepts/events.md) for one handler serving several events.

## The Stage Runners Moved to LiteBus.Messaging

`MessageContextExtensions` is in the `LiteBus.Messaging` assembly and the `LiteBus.Messaging` namespace, rather than in `LiteBus.Messaging.Abstractions`. It is the pipeline engine. It opens ambient scopes, orders the stages, preserves stack traces, and decides what a refused caller receives. An abstractions package describes contracts, and this was never one.

Only a custom `IMessageMediationStrategy` calls these methods, and every package that implements one already references `LiteBus.Messaging`, so the fix starts with a using directive:

```csharp
using LiteBus.Messaging;            // add this
using LiteBus.Messaging.Abstractions;
```

`RunAsyncPreHandlers` is replaced by `RunAsyncPreStages`, which runs all four pre-stage roles in the fixed order and returns the `PipelineDecision` the strategy acts on. `RunAsyncPostHandlers` keeps its signature under the new namespace. `RunAsyncErrorHandlers` takes the failure and the execution context instead of dispatch info and a token, and captures the `ExceptionDispatchInfo` and opens its own ambient scope:

```csharp
// Before
await messageDependencies.RunAsyncErrorHandlers(message, result, ExceptionDispatchInfo.Capture(exception), cancellationToken);

// After
await messageDependencies.RunAsyncErrorHandlers(message, result, exception, executionContext);
```

`RunAsyncDecisionStages` exposes the guard-plus-validator prefix behind `EvaluateAsync` to a custom strategy. `ResolveRefusalResult<TMessageResult>` applies the registered refusal mapper, or raises when none covers the message. The two `RunAsyncCompletionHandlers` overloads take either a built context or the outcome, failure, reason, code, result, and duration that a strategy tracked.

## Event Fault Settings Are Renamed

`ParallelFaultMode` becomes `HandlerFaultMode`, `AggregateAll` becomes `ContinueAndAggregate`, and the `EventExecutionSettings.ParallelFaultMode` property becomes `FaultMode`:

```csharp
// Before
new EventExecutionSettings { ParallelFaultMode = ParallelFaultMode.AggregateAll }

// After
new EventExecutionSettings { FaultMode = HandlerFaultMode.ContinueAndAggregate }
```

Under `ContinueAndAggregate`, parallel event handling rethrows `OperationCanceledException` when every handler was cancelled, instead of reporting a failure and running error handlers.

## Composition Exceptions Have Categories

`LiteBusConfigurationException` is an unsealed base class with five derived types:

| Derived Type | Coverage |
| --- | --- |
| `ModuleCompositionException` | Duplicate module registration, dependency cycles, a missing required module, a descriptor the container adapter cannot translate |
| `MessageDeclarationException` | Two definitions declaring one value, a definition that declares nothing, an annotation that disagrees with its value, a required declaration nobody satisfied |
| `PipelineContractException` | A pipeline marker with no contract, an unsupported open generic shape, two refusal mappers at one level, an untyped shortcut on a result-producing message |
| `DurableStorageConfigurationException` | Durable messaging enabled without the storage, dispatch or processor registration it needs, or against a schema it cannot use |
| `AuditConfigurationException` | No `IAuditTrail` registered, `AddAuditing` with no axis selected, a failed audit convention check |

`catch (LiteBusConfigurationException)` keeps working and still catches all of them. Only code that needed to distinguish one composition mistake from another has anything to change.

`AuditReasonMissingException` is outside the hierarchy entirely and derives from `Exception`. An audited action that declares `ReasonRequired` and receives no reason is a data problem in one mediation rather than a composition error, and an application catching configuration faults at startup must not also catch a handler that never made the call. It carries the action and the message type.

## Composition Refuses What Could Not Work

Six compositions that succeeded in v6 and then misbehaved fail when the container is built in v7, with a `ModuleCompositionException`, `DurableStorageConfigurationException`, or `ArgumentException` naming what collided:

- A second `AddLiteBus` on one service collection or container builder. Compose every module inside one call.
- A second transport module in one composition. Host each broker in its own service, or keep one transport per composition.
- A service type registered both as a single binding and as collection items.
- A type that implements both `IStartupTask` and `IBackgroundService`. Split it into two types. v6 rejected such a type in `RegisterBackgroundService` only. `RegisterStartupTask` mirrors the check in v7.
- A saga composition whose `MapContract` definition id has no registered state type. Register the state type for every mapped contract, or module build fails with `DurableStorageConfigurationException`.
- Two different `IDiagnosticCheck` types registered under one probe name. v6 allowed the collision. Rename one probe, or composition fails with `ModuleCompositionException`.

## Marker-Only Types Are Reported

Every pipeline marker declares no members, so a class could implement one without implementing any contract naming a message type. Such a class produced no descriptor, was registered as a message type instead, and silently never ran. Registration raises `PipelineContractException` naming the type and the closed contracts that would fix it.

## Interfaces That Gained Members

These are infrastructure contracts implemented by LiteBus itself. Applications that only implement handlers are unaffected. Custom implementations, including test doubles, must add the members. Defaults are noted where a custom implementation compiles unchanged.

| Interface | Added members | Notes |
| --- | --- | --- |
| `IMessageDescriptor` | `Metadata`, `PreStageHandlers` / `IndirectPreStageHandlers` (renamed from `PreHandlers`), `CompletionHandlers` / `IndirectCompletionHandlers`, `RefusalMappers` / `IndirectRefusalMappers` | Registry-level shape that keeps the indirect completion split. |
| `IMessageDependencies` | `PreStageHandlers` / `IndirectPreStageHandlers` (renamed), single `CompletionHandlers` collection, `RefusalMappers` / `IndirectRefusalMappers`, `HasPreStageHandlers(PreStage)` | `IndirectCompletionHandlers` is gone, because completion orders by priority alone. `HasPreStageHandlers` has a default implementation that enumerates the descriptors. Override it only to answer from a precomputed mask. |
| `IHandlerDescriptor` | `ContractType` | The closed contract the descriptor was discovered from. |
| `IPreStageHandlerDescriptor` (renamed from `IPreHandlerDescriptor`) | `Stage`, `Dispatch` | The pre stage the handler runs in and the delegate bound at registration. `PreHandlerDescriptorBuilder` is renamed `PreStageHandlerDescriptorBuilder` to match. |
| `IExecutionContext` | `Data`, `HandledAt`, `PostHandlersSuppressed`, `SuppressPostHandlers()` | `Data` is an `IHandleContextData` store keyed by value type. Return `new HandleContextData()` from a custom implementation. `Abort` is removed. |
| `IModuleConfiguration` | `CompositionValidations`, `RegisterCompositionValidation(Action)` | A custom host adapter must run the collected validations after its module loop, or a rule spanning several modules never executes. Both shipped adapters do. |
| `IMessageReader` | `ScannedOpenGenericHandlers`, `OpenGenericClosures` | Both have defaults, so custom registries compile unchanged. |
| `IMessageWriter` | `RegisterFromScan(Type)`, `AddDeclaration(MessageDeclarationItem)` | The default `AddDeclaration` throws, so implement it when the composition uses `DeclareDefault`. |
| `ILeaseRenewable` | `ReleaseLeaseAsync(LeaseReleaseRequest, CancellationToken)` | Default returns `false`. A custom store compiles unchanged but spends an attempt on shutdown or drain until it implements the release. `InboxEnvelope.AsReleased` and `OutboxEnvelope.AsReleased` are the matching transitions. |
| `IProcessorWorkSignal` | `IAsyncDisposable` | A custom work signal must add `DisposeAsync`. Also implement `IDisposable` when the container may be disposed synchronously. Built-in signals implement both. |
| `IOutboxDiagnosticsStore`, `IOutboxManager` | `GetFailureSummaryAsync(CancellationToken)` | A custom outbox store implements it to return one `OutboxFailureSummary` per failing contract.

## Processor Hook Contracts Changed Namespace

`IProcessorEnvelope`, `IProcessorEnvelopeHook` and `ProcessorHookRunner` are in `LiteBus.Messaging.Abstractions.Processing`. Replace `using LiteBus.DurableMessaging.Abstractions.Processing;` with `using LiteBus.Messaging.Abstractions.Processing;`. The package reference is unchanged. The inbox and outbox share one hook runner instead of running identical copies.

## The Hook Failure Policy Is Nullable

`ProcessorOptions.HookFailurePolicy` is `ProcessorHookFailurePolicy?`, and `null` means the dispatcher's recommendation. A `UseProcessorOptions` call that sets only a batch size keeps the transport dispatchers' `CompleteDespiteHookFailure` in v7. In v6 it replaced that recommendation with `DeadLetter`. If the service relied on dead-lettering after a hook failure, set the policy explicitly:

```csharp
UseProcessorOptions(new OutboxProcessorOptions { HookFailurePolicy = ProcessorHookFailurePolicy.DeadLetter })
```

An explicit value always overrides the dispatcher recommendation. With no dispatcher recommendation, `null` dead-letters, as in-process dispatch does.

## Refusals and Missing Handlers Dead-Letter on First Attempt

The inbox and outbox processors dead-letter a refusal or a missing handler on its first attempt instead of spending the retry schedule on it, including when a dispatcher wraps the refusal or missing handler in its own exception type. `IsRetryableDispatchException` inspects the inner exception chain to find the wrapped cause. A guard refuses the same message identically on every attempt, and a message with no handler gains none on retry, so retrying only delayed the dead-letter entry an operator was waiting to see. `MediationExceptionFilters.IsRefusal` and `IsRetryableDispatchException` expose that classification for custom processors. `RetryOptions.IsPermanentFailure` marks an application exception as permanent for the same terminal treatment. A classifier that throws is treated as not permanent.

## Tenant Filters Mean the Same on Every Store

Tenant filters and lease requests mean the same on every store. `null` applies no tenant restriction, and an empty string matches unscoped rows only. Stored and requested values compare through `DurableTenantId.Normalize`. The Entity Framework Core and in-memory stores treated an empty string as no restriction in v6. Code that passes `string.Empty` to mean "every tenant" must pass `null` in v7. This covers processor lease requests and management query and purge filters on both axes. Every inbox and outbox store throws `IdempotencyConflictException` when a supplied message id already exists for another tenant, regardless of conflict mode. In v6 a non-strict accept returned `AlreadyAccepted` or `AlreadyEnqueued` with the foreign row, silently dropping the second tenant's message.

## Contextual Payload Encryption Binds Its Context

In v6, `IContextualPayloadEncryptor` declared contextual `EncryptAsync` and `DecryptAsync` overloads, but `InboxPayloadProtector` and `OutboxPayloadProtector` implemented only the plain `IPayloadEncryptor` pair and forwarded every call to it. An encryptor registered through `UsePayloadEncryption` therefore encrypted inbox and outbox rows without the context even when it implemented the contextual contract.

In v7 the protectors implement `IContextualPayloadEncryptor` and forward to the contextual overloads when the configured encryptor implements them, binding message id, contract name and version, tenant, and axis as authenticated metadata. `PayloadProtectionContext.TenantId` normalizes null, empty, and whitespace values to `null`, so unscoped messages authenticate identically on encrypt and decrypt. Drain the inbox and outbox before deploying v7. Let every pending row reach a terminal state, because rows encrypted without the context cannot be decrypted once the context is bound.

## Retention and Purge Guardrails

`IOutboxManager.RunRetentionPurgeAsync` throws `OutboxManagementException` when `OutboxCleanupHostOptions.Retention` is not a positive period, instead of returning 0. Callers that treated 0 as "nothing to purge" catch the exception or configure a retention period first. The management retention-purge routes report the missing policy through the management safety response rather than an HTTP 500. Inbox message queries reject a `PageSize` above `InboxMessagePageRequest.MaxPageSize` (1000) with `ArgumentOutOfRangeException`. Version 6.0 applied no cap, so page through the cursor or lower the page size. The management message-query endpoints reject `messageIds` sets larger than `MaxBulkMessageIds` (default 1000) with HTTP 400, like purge and requeue. In v6 the query paths were uncapped, so page the identifiers or raise the limit.

`SagaPurgeFilter.Take` bounds a saga purge to at most that many of the oldest matching rows, and `Take` must be positive. A saga purge with no predicate and no `Take` throws `ArgumentException`. In v6 it deleted every row. Add a predicate or a `Take` limit to intentional full purges.

## PostgreSQL Schema Changes

| Component | v6 schema | v7 schema | Application action |
| --- | --- | --- | --- |
| Inbox (`litebus_inbox_messages`) | Version 1 | Version 1, unchanged | None. |
| Outbox (`litebus_outbox_messages`) | Version 1 | Version 2: nullable `handler` column | None when schema initialization runs at startup. Otherwise run the v2 upgrade script. |
| Saga (`litebus_saga_instances`) | Version 1 | Version 1, unchanged | None. |
| Command idempotency (`litebus_idempotency_keys`) | No table | Version 1 | Created at startup when `UsePostgreSqlIdempotencyStore` is registered. |
| Recurring leases (`litebus_recurring_leases`) | No table | Version 1 | Created at startup when `UsePostgreSqlRecurringLease` is registered. |

An existing version 1 outbox table upgrades on startup when schema initialization runs. The registered schema initializer calls `EnsureAsync`, which applies the v2 upgrade script (`ADD COLUMN IF NOT EXISTS handler text NULL`) and records version 2 in `litebus_schema_versions`. `EnsureSchemaCreationOnStartup` defaults to `true` on every PostgreSQL store options type. A deployment with initialization disabled must run the v2 upgrade script through the application migration process before starting v7 binaries, or validation reports the drift. See [PostgreSQL schema management](../integrations/postgresql-schema-management.md) for the canonical SQL files and the upgrade section.

The `handler` column carries the full name of the handler one per-handler-delivery envelope is addressed to. It stays `NULL` unless `EnablePerHandlerDelivery` is enabled, so the upgrade is storage-only for services that never adopt per-handler delivery.

Entity Framework Core applications own their migrations. Generate an application migration from `GetModelBuilderConfiguration()` for the selected provider, which includes the `handler` column, and apply it before starting v7. The same migration records `lease_generation` as a concurrency token on the inbox and outbox entities. That annotation adds no DDL, but without the migration EF Core reports pending model changes. In-memory stores need no action. Marten idempotency and audit records are documents in the application's document store, not SQL tables.

## Transport and Ingress Changes

`TransportPublishRequest.Mandatory` defaults to `true`, matching `AmqpPublishRequest` and the outbox dispatcher (whose own `Mandatory` option already defaulted to `true` in v6). Only a direct `ITransportPublisher` caller that relied on `false` is affected, and it sets `Mandatory = false` explicitly. An AMQP mandatory publication the broker returns as unroutable fails with the new `AmqpMessageReturnedException` and releases its circuit-breaker permit, so a routing mistake counts as a dispatch failure rather than opening the circuit.

The Kafka transport does not register the bare `IProducer<string, byte[]>`. Resolve `ITransportPublisher`. `MessageTimeoutMs` sets only the message timeout in v7. In v6 it also set the socket timeout and disabled send retries. Keep the v6 coupling by setting the two new options beside it, each positive when set and left at the librdkafka default otherwise:

```csharp
new KafkaTransportOptions
{
    BootstrapServers = bootstrapServers,
    MessageTimeoutMs = 30_000,
    SocketTimeoutMs = 30_000,
    MessageSendMaxRetries = 0
}
```

Kafka and SQS route and content-type metadata use the shared names `litebus-route` and `content-type` instead of `Route` and `ContentType`:

| Adapter | Before | After |
| --- | --- | --- |
| Kafka record headers | `ContentType` header, with the route as the record key | `content-type` header, with the route still as the record key |
| SQS message attributes | `Route`, `ContentType` | `litebus-route`, `content-type` |

There is no fallback in either direction. A v7 reader does not see the old names, and a v6 reader does not see the new ones. Upgrade publishers and consumers of each queue or topic together, and give consumers outside LiteBus the ability to read both names during the rollout. The shared names are `TransportHeaders.Route` and `TransportHeaders.ContentType`.

The AMQP ingress broker-scoped idempotency key is scoped to the queue (`ingress:{queue}:{id}`) instead of the exchange, so two queues bound to one exchange share no key. During the redeploy of an AMQP ingress host, a redelivery of a message accepted under the old key is accepted again under the new one. Drain the queue first if a duplicate matters.

Ingress reads identity and idempotency from the `litebus-message-id` header only when `TrustApplicationHeaders` is set (default `false`). In v6 the header applied unconditionally. An application that publishes `litebus-message-id` and relies on ingress honoring it sets `TrustApplicationHeaders = true` on the ingress safety options. Ingress also ignores `litebus-visible-after` and `litebus-visible-after-delay` unless `TrustApplicationHeaders` is set. In v6 those headers applied unconditionally, so an application that schedules visibility through broker headers sets the same option.

Transport publishers are singletons in all five adapters, so a dispatched envelope shares one AMQP channel, Azure Service Bus sender link, or Kafka producer instead of opening and closing its own. Consumers are transient in all five, Azure Service Bus included, because each instance holds one subscription.

The Kafka producer is flushed once, when the container is disposed. `KafkaConsumer.StartAsync` starts the consume loop on the thread pool and returns instead of blocking until the first record arrives. The Kafka transport registers `IConsumer<string, byte[]>` as transient instead of singleton, and each `KafkaConsumer` owns its client. It closes the client on `StopAsync` and disposes it on `DisposeAsync`, so code that shares one client across consumers or disposes it externally must be changed. Kafka and SQS `StopAsync` complete without throwing when the consume loop faulted. Await `WaitUntilStoppedAsync` to observe the terminal failure.

`InMemoryTransportBroker` implements `IDisposable` and completes its destination channels. Dispose test hosts that create one. The transport outbox dispatcher fills the new `TransportPublishRequest.MessageGroupId` and `DeduplicationKey` from the envelope, and the SQS adapter sets them on queues whose URL ends in `.fifo`, so outbox dispatch publishes to SQS FIFO queues. `AmqpReceivedMessage.QueueName` and `AmqpConsumerOptions.MaxInFlightMessages` give a typed `IAmqpConsumer` subscription the same admission control as the generic consumer path.

The SQS consumer deletes poison messages (an undecodable body or malformed packed headers) instead of faulting, so poison no longer reaches the queue dead-letter queue through redrive. A transient Kafka consume error waits one second and then resumes polling instead of faulting the loop, and a transient requeue-seek failure retries with the seek backoff schedule.

A second `AmqpConsumer.StartAsync` throws `InvalidOperationException` instead of `AmqpTransportConfigurationException`, matching `IMessageConsumer` and the other four consumers. Catch `InvalidOperationException` for idempotent-start handling. The `StartAsync` token cancels startup only, so cancelling or disposing it after startup no longer affects deliveries. `StopAsync` ends the subscription and cancels in-flight handlers. Each AMQP delivery settles at most once. A handler that settles and then throws no longer triggers a second acknowledgement that closed the channel with `PRECONDITION_FAILED`.

## New Analyzers and Build-Only Rules

In v6 the analyzer range ends at LB1017 (LB1002 and LB1006 are reserved and never shipped). v7 adds LB1018 through LB1024:

| Rule | Condition | Default |
| --- | --- | --- |
| LB1018 | A command or query type that states no audit position | Disabled. Enable with `dotnet_diagnostic.LB1018.severity = warning` |
| LB1019 | A shortcut on the untyped contract for a message that produces a result | Warning |
| LB1020 | A command or query with no position on a metadata type named in `litebus_required_declarations` | Disabled until configured and enabled |
| LB1021 | A `litebus_required_declarations` name that does not resolve | Warning |
| LB1022 | A handler priority inside the `ReservedFloor` to `ReservedCeiling` window | Warning |
| LB1023 | A command handler that sends or publishes through a mediator (nested unit of work) | Disabled. Enable with `dotnet_diagnostic.LB1023.severity = warning` |

LB1001, LB1007 through LB1012, LB1017, LB1018, LB1020, and LB1021 use facts from the whole compilation, so they gather facts as each file is analyzed and report once at compilation end. `dotnet build` and CI report them as usual. LB1011 resolves `const` tag names and maps arguments to parameters. LB1003 checks base classes. A build that was clean in v6 can report new diagnostics in v7 without any code change. Each one names the declaration or registration that fixes it.

## Behavior Changes Without Code Breaks

Nothing here breaks compilation. Each item changes what happens at runtime for code that compiled in v6.

Mediation:

- Event post-handlers and error handlers receive `null` as the message result instead of the task that tracked handler completion.
- Message resolution counts the interfaces of the registered type, so a message implementing several registered interfaces can resolve to a different handler than in v6. Ties throw `AmbiguousMessageResolveException` with `Candidates` naming the registered types that tied.
- One open generic pipeline handler runs once per message regardless of registration order. When two closures of one generic handler definition reach a message through the same contract, only the direct one is kept. `LiteBusCompositionSummary.DuplicateStageCoverages` names handler types that still cover one message both directly and through a base type, so a handler that runs twice appears in the startup line.
- A main handler reached through an erased message type, such as an event published as `IEvent`, receives the mediation's cancellation token rather than reading the ambient one, and is called through the contract recorded at its registration.
- `NoHandlerFoundException` and `MultipleHandlerFoundException` name the runtime message type when the call erased it to `ICommand`, `IQuery`, or `IEvent`.
- Stream mediations release the handler's enumerator when its enumeration ends rather than when the whole mediation ends, honor the token passed to `WithCancellation` or `GetAsyncEnumerator` (not only the one passed to `StreamAsync`), and route faults through one path. Stream guards, shortcuts, and post-handlers honor the enumerator cancellation token.
- Each composition keeps its own mediation telemetry options. A second composition inherits nothing from the first one.
- `MessageMediator.Mediate` and the public pipeline extension methods throw `ArgumentNullException` naming the argument instead of `NullReferenceException`.
- Assembly scans skip types that fail to load instead of aborting the registration, in all six scans. `MessageRegistry.Handlers` returns a snapshot taken under the registry lock instead of a live view, so a concurrent registration cannot change it during enumeration.
- Mediation restores the caller ambient execution context before it returns a task or stream, and creates the dispatch scope only when a handler resolves a service, so a stream that is never enumerated holds no container scope.
- `TestQueryMediator.NextResult` is consumed once per `QueryAsync`, `StreamAsync`, or `TryQueryAsync` call. In v6 one stub answered every call until `Clear`, so a test that stubs once and queries twice observes a default result on the second call. `StreamAsync` throws `InvalidCastException` on a stub type mismatch instead of yielding an empty stream.
- `TestCommandMediator`, `TestQueryMediator`, and `TestEventMediator` recording properties return snapshots instead of the live list, so a previously captured reference no longer observes later messages.

Durable processors:

- A handler-internal `OperationCanceledException`, such as a dependency timeout, follows the normal failure path with `MaxAttempts` and `IsPermanentFailure`, instead of being recorded as lease loss and retried indefinitely.
- A dispatch cancelled by host shutdown, a drain, or a lease loss is recorded as no outcome. No attempt is consumed, no error is recorded, no visibility moves, and no dead letter is written. The outbox in-process dispatcher rethrows the caller's cancellation instead of wrapping it, and both envelope handlers recognize it even when a dispatcher wrapped it in its own exception type.
- A lease renewal that throws cancels the running dispatch and reports the lease lost, instead of appearing only after the handler finished. The lease store receives a cancellable token linked to the heartbeat.
- A failed persist for one lease-lost message is logged and counted as a persist failure instead of aborting the whole inbox or outbox pass and discarding the other envelopes' results.
- The `AfterDispatch` hook runs on the persist token on both the inbox and the outbox, so a shutdown during a saga save leaves no executed command or published event to run again. With the default `HonorShutdownTokenOnPersist = false`, a hook that never returns delays shutdown instead.
- Saga state is compared with the JSON snapshot taken when it was loaded. Reading state and then calling `Complete()` works, a dispatch that only reads state saves nothing, and a handler that changes state in place without `SetState` is still persisted. A completed saga dispatches a new correlated message with an inactive saga scope instead of suppressing it. Only a redelivery of the last applied message is suppressed. `Complete()` on a saga that was never saved creates the row already completed instead of dead-lettering a successful handler. A saga save without an applied message id keeps the existing duplicate-dispatch marker instead of erasing it.
- One hook's `AbandonDispatchScope` failure skips no other hook and leaks no saga correlation gate, and an empty message id stays out of the abandon path.
- The inbox and outbox cleanup loops report nothing when the host stops during their error backoff instead of throwing `OperationCanceledException` out of `ExecuteAsync`.
- `TransportOutboxDispatcherOptions.ResolveRoute` overrides `OutboxEnvelope.Topic`, as its documentation says. In v6 an envelope topic took precedence. An empty result fails the dispatch with `LiteBusDispatchException`. Inbox transport dispatch throws `InboxDispatchException` naming the message when the route resolver returns an empty route, matching the outbox dispatcher. An `ITenantRoutingStrategy` result that is null or whitespace fails the outbox dispatch with `LiteBusDispatchException` naming the envelope, like an empty `ResolveRoute` result. In v6 the envelope published with an empty route.
- The outbox in-process dispatch failure message carries contract-registration guidance only when the cause is a missing contract or handler, instead of on every failure including concurrency conflicts and cancellations.

Stores:

- PostgreSQL inbox and outbox batch inserts run in chunks of 1,000 rows inside the caller's transaction, so a batch above the 65,535 parameter limit no longer fails.
- Inbox and outbox requeue clear `error_type`, `first_failed_at`, and `dead_lettered_at`, matching the Entity Framework Core and in-memory stores.
- Strict replay of an identical unscoped message returns `AlreadyAccepted` or `AlreadyEnqueued` on every store instead of throwing `IdempotencyConflictException`, because stored and requested tenants are compared after normalization.
- The in-memory stores reject a non-terminal envelope passed to `PersistAsync`, like the relational stores.
- Entity Framework Core batch acceptance re-inserts rows still missing after a concurrent unique violation and rethrows other database errors with the original exception, instead of reporting invented `AlreadyAccepted` outcomes. The save-changes interceptors fail the save when two strict-idempotency envelopes share a message id, instead of keeping one and reporting both as accepted. Lease SQL escapes schema and table identifiers for each provider.

Transports and ingress:

- A cancelled AMQP connection probe releases its circuit-breaker permit instead of leaving the circuit half-open until restart. A failed AMQP consumer start releases its channel and can be retried. The consumer stayed unusable in v6, and `WaitUntilStoppedAsync` never completed.
- Disposing a transport consumer twice is safe on all five brokers and the connection manager. The Kafka, in-memory, SQS, Azure Service Bus, and AMQP consumers threw `ObjectDisposedException` in v6. `AzureServiceBusPublisher.Dispose` waits at most five seconds and does not propagate close errors.
- The in-memory consumer's `StopAsync` and `WaitUntilStoppedAsync` complete after the destination channel is closed instead of throwing `ChannelClosedException`, which ended the ingress loop in v6.
- A cancelled ingress acceptance is left unacknowledged for the broker to redeliver instead of being requeued with the cancelled token. Stopping a Kafka host commits no offset for a message that was never stored.
- SQS sends invalid UTF-8 and characters SQS rejects as base64 so the payload round-trips byte for byte, caller headers cannot replace mapper-owned attributes, and headers past the ten-attribute limit are packed into `litebus-headers` and expanded on receive. Publishing to and consuming from SQS works against AWSSDK 4, which leaves attribute collections uninitialized.
- `TransportInboxIngressConsumer` cannot recreate its admission semaphore after disposal or release a disposed one.

Hosting and diagnostics:

- Every processor and cleanup loop delay uses the injected `TimeProvider`, so tests drive the startup delay, heartbeat interval, and cleanup backoff. The first cleanup retry after a transient failure waits 5 seconds instead of a full `Interval`.
- A failing diagnostics store stops the queue-depth gauge from reporting until the next successful read, instead of exporting the last good counts, and the outbox records `litebus.outbox.diagnostics.unavailable` when no store is registered.
- The management drain endpoints enforce the options passed to `AddLiteBusManagementEndpoints`, like the other management endpoints.
- A diagnostic probe that observes its token is cancelled when the run budget expires, and a probe whose `Name` differs from its registration reports the mismatch instead of a generic failure. `DiagnosticCheckRunOptions.RunTimeout` sets an overall budget for one diagnostic run. When unset, it is the worst case of the probe count packed into `MaxParallelism` lanes at `Timeout` each. A negative `RunTimeout` throws `ArgumentOutOfRangeException` when health checks or management endpoints are registered instead of failing on every request or run.
- `GetHostedServiceForBackgroundService<T>()` works before the host has started.
- `BackgroundServiceHostWrapper.StopAsync` completes when the loop ended after the cancellation it requested, instead of reporting a failed stop. The wrapper disposes its stopping token source and logs event ID 6001 naming a service whose loop ignored shutdown.
- `LiteBusDependencyResolutionException` and `DiagnosticCheckNameMismatchException` throw `ArgumentNullException` for a null argument instead of `NullReferenceException`.
- The durable test host honors its `timeProvider` argument in the messaging and in-memory storage modules.
- The PostgreSQL `LISTEN` channel name is quoted. A data source created by `UseConnectionString` is disposed with the service provider under Microsoft dependency injection, which never disposed the prebuilt instance it was registered as in v6. The documentation already claimed it was. `UseDataSource` still leaves ownership with the application.

## New Capabilities

Nothing here is required to upgrade. Each item is a v7 capability a v6 application gains by adopting it, with the page that documents it.

### Refusals as Values

`TrySendAsync` and `TryQueryAsync` return how the mediation ended instead of raising:

```csharp
// Before: an endpoint catching an exception to produce a status code.
try
{
    await _commands.SendAsync(command, ct);
    return Results.NoContent();
}
catch (LiteBusMessageDeniedException denied)
{
    return Results.Problem(denied.Reason, statusCode: 403);
}

// After.
var result = await _commands.TrySendAsync(command, cancellationToken: ct);

return result.Outcome switch
{
    MediationOutcome.Denied  => Results.Problem(result.Reason, statusCode: 403),
    MediationOutcome.Invalid => Results.ValidationProblem(ToErrors(result.Failures)),
    _                        => Results.NoContent()
};
```

A genuine fault still throws. A database timeout is not a value a caller branches on, and a result carrying the exception could be swallowed silently. These methods return a decision as a value and still throw a fault.

`SendAsync` is unchanged, and a registered `IMessageRefusalMapper` still applies to both. Under `TrySendAsync` a mapped refusal arrives with the mapped value in `Value` and `Denied` in `Outcome`, so an application that models failure in its own result type receives both the mapped value and the outcome.

There is no `TryStreamAsync`. A stream refusal is observed when enumeration starts rather than when the method returns, so a result value would have to be produced before the decision exists.

### Evaluating Messages Without Sending

`EvaluateAsync` runs the decision stages and stops:

```csharp
var decision = await _commands.EvaluateAsync(new CloseOrganizationCommand(id), cancellationToken: ct);

if (decision.IsDenied)
{
    // hide the control
}
```

This replaces a second authorization method written beside the real one, one to authorize while doing and one for a caller that shows or hides a control. Two methods answering the same question drift, and the drift is silent and security-relevant. A button stays visible for an action the pipeline will refuse.

It runs guards and validators only. Shortcuts and pre-handlers act rather than decide, and the idempotency shortcut LiteBus ships claims a key, so evaluating a page full of controls would consume keys for commands nobody submitted.

That puts one obligation on a guard. It has to be free of effects a caller would not want from a "may I" question. A guard that loads an aggregate to decide is acceptable, and the load happens on every evaluation, so check `IExecutionContext.Data` before loading if it is expensive.

### Auditing in One Call

`AddAuditing` configures the trail, the actor resolver, the outcome mapper, and which axes produce records, in one configuration that cannot be half-made:

```csharp
registry.AddMessaging(messaging => messaging.AddAuditing(auditing => auditing
    .UseTrail<SqlAuditTrail>()
    .UseActorResolver<RequestActorResolver>()
    .ForCommands()
    .ForQueries()));
```

The granular calls exist underneath, and they are what `AddAuditing` composes: `UseAuditTrail<TAuditTrail>(lifetime)` or `UseAuditTrailInstance` for the sink, `UseAuditActorResolver`, `UseAuditOutcomeMapper`, and `EnableAuditing()` on the command, query, and event module builders (`EventModuleBuilder.EnableAuditing()` writes one record per publish rather than one per handler). Configuring a trail through `AddAuditing` and selecting no axis fails composition with `AuditConfigurationException`, because no probe can report that at runtime. Nothing is ever audited, so nothing ever fails.

Because auditing runs at the completion stage, refusals, failures, and cancellations are recorded as first-class outcomes in an `AuditRecord` carrying the action, the actor, the outcome, the target, the reason, and timing. The message itself is deliberately not on the record. It is handed to the resolver, so a payload cannot reach audit storage by default. `AuditDeclaration` is a closed hierarchy of `AuditedDeclaration` and `AuditExemptDeclaration`, declared with `[Audited]` / `[AuditExempt]`, `IAuditDefinition<TMessage>`, or `IMessageDefinition<TMessage>.Describe`. `ReasonRequired` on an audited declaration is enforced with `AuditReasonMissingException` when the handler supplied no reason through `IAuditScope.WithReason` or a `WithReasonFrom<TMessage>` selector.

An `IAuditActorResolver` supplies `AuditRecord.Actor` from the completion context, so it attributes a denied, invalid, failed, or cancelled mediation as readily as a successful one:

```csharp
internal sealed class RequestActorResolver : IAuditActorResolver
{
    public AuditActor? Resolve(MessageCompletionContext context) => context.Message switch
    {
        IActingAccountCommand acting => AuditActor.User(acting.ActingAccountId.ToString()),
        _ => AuditActor.System(ProcessNameOf(context.Message.GetType()))
    };
}
```

`IAuditScope.WithActor` overrides the resolver for a handler that knows what the rule cannot, such as an actor established by exchanging a token mid-handler. Returning `null` is legitimate and means nothing established an actor. Prefer `AuditActor.System("worker-name")` where the application knows a process acted. A scheduled job and an unattributed action are different answers, and an audit query has to be able to distinguish them. `AuditActor.Kind` and `AuditActor.Id` are required. `DisplayName` is a separate property, so the field that makes the trail hold personal data is a line a reviewer sees. The `litebus.audit.trail` probe reports `Degraded` when a trail is registered and no resolver is.

An application that needs a record of its own rather than `AuditRecord` replaces the writer with `auditing.UseRecordWriter<TWriter>()`. `IAuditRecordWriter` is the entire contract between the pipeline and auditing, so a replacement keeps the stage placement, the priority, and the axis selection, and owns building the record, including skipping a message that declares no audit position. `IAuditOutcomeMapper` lets an application that refuses by throwing record its own exception as `AuditOutcome.Denied` rather than `AuditOutcome.Failed`. Refusing through a guard needs no mapper.

`IMessageCatalog` resolves at runtime, and `AuditCatalogue.ToRows` projects every audited message into an ordered `AuditCatalogueRow` carrying the action, the message, the category, the target kind, and whether a reason is required, with `ToMarkdown` as one formatter over those rows:

```csharp
var catalog = provider.GetRequiredService<IMessageCatalog>();
File.WriteAllText("audit-catalogue.md", catalog.ToMarkdown());
```

The permission side of an authorization matrix stays with the application, projected from `MessageCatalogEntry.Metadata`, because a required permission is an application value type and only the application knows what it means. `messaging.RequireUniqueAuditActions()` and `messaging.RequireAuditActionFormat()` enforce audit conventions as startup failures, and LB1018 reports messages that state no audit position.

### Message Metadata Declarations

`IMessageDescriptor.Metadata` exposes values resolved once at registration from declaring attributes on the message type and from message definitions, so a pipeline stage reads a dictionary instead of reflecting on every dispatch. Put the definition class beside the message it describes. `IMessageDefinition<TMessage, TValue>` declares one value with the compiler checking it against its key. `IMessageDefinition<TMessage>` declares any number of values from one `Describe` method:

```csharp
internal sealed class CloseGateCommandDefinition : IMessageDefinition<CloseGateCommand>
{
    public void Describe(IMessageDeclarations declarations)
    {
        declarations.Audited("admission.close-gate", category: "admission", targetKind: "gate");
        declarations.Declare(new RequiredAuthorization(new PermittedAction.ManageGate(), Subject.Platform));
    }
}
```

`IMessageDeclarations` also carries `NotAudited(rationale)`, `Authorized(policy)`, `AuthorizationExempt(rationale)`, and `Exempt<TValue>(rationale)`, so a definition records an exemption without an attribute. `IMessageDefinition<TMessage, TValue>` remains the better choice for a message that declares exactly one thing, which is why `IAuditDefinition<TMessage>`, `IAuthorizationDefinition<TMessage>`, and `IIdempotencyDefinition<TMessage>` are built on it. Both shapes write into the same type-keyed metadata. `IMessageMetadataAccessor` reads a message type's declared metadata from application code through `ForMessage` and `TryGet`. An unregistered type raises `MessageMetadataNotFoundException` rather than answering with an empty collection, because an empty answer turns a missing registration into a permission check that silently passes.

`MessageModuleBuilder.RequireDeclaration<TValue>()` fails composition for any registered message that neither declares a value of that type nor records an exemption from it. Scope the requirement to the rule it enforces rather than leaving it axis-wide:

```csharp
// Too wide: this demands a permission declaration from every query too, and the exemptions written to satisfy
// it say nothing.
messaging.RequireDeclaration<RequiredAuthorization>();

// Scope to the axis, or better, to the marker that carries the rule.
messaging.RequireDeclaration<RequiredAuthorization, ICommand>();
messaging.RequireDeclaration<RequiredAuthorization, IActingAccountCommand>();

// Or an arbitrary selection, with the words the composition error uses.
messaging.RequireDeclaration<RetentionClass>(type => type.Namespace!.Contains("Billing"), "every billing message");
```

The scope is a type rather than a namespace deliberately. A namespace is a string a refactoring tool moves without warning, so a requirement keyed on one silently stops applying when a folder is renamed. For an authorization rule that failure is a command with no guard where the requirement applied.

A rule that holds for a whole family can be stated once with a default, and a command that declares its own value keeps it while the rest of the family inherits the default:

```csharp
registry.AddMessaging(messaging => messaging
    .DeclareDefault<IOrganizationCommand, AuthorizationDeclaration>(AuthorizationDeclaration.Authorized("organizations.manage"))
    .RequireDeclaration<AuthorizationDeclaration, IOrganizationCommand>());
```

Defaults and a scoped requirement belong together. The requirement makes the family answer for the value, and the default answers for the ones with nothing special to say. Two defaults for one scope and value type are a configuration error. `[MessageDeclaration(typeof(TValue))]` states on an attribute class which metadata value that attribute declares, which is what lets LB1020 turn "every command states the permission it requires" into a build failure. `[DeclarationExempt(typeof(TValue), rationale)]` records a deliberate gap, repeatable and aggregated into one `DeclarationExemptions` value. `MessageModuleBuilder.ValidateComposition(Action<IMessageCatalog>)` runs any other application rule over every registered message after every module is built. See [Authorization Declarations](../concepts/authorization-declarations.md).

### Declaration Guards

`DeclarationGuard<TMessage, TValue>` looks a declaration up for the message runtime type and calls one `DecideAsync(declaration, message, ...)`. An undeclared message is denied with `declaration.missing` unless `DecideUndeclaredAsync` is overridden, and a recorded exemption allows. `AuthorizationGuard<TMessage>` builds on it. An exempt message is allowed, and an authorized one calls `AuthorizeAsync(policy, message, ...)`. `AuthorizationDeclaration` states the position the way `AuditDeclaration` states the audit position: `[Authorized(policy)]`, `[AuthorizationExempt(rationale)]`, the keyed `IAuthorizationDefinition<TMessage>`, and the `Authorized` / `AuthorizationExempt` helpers on `IMessageDeclarations`. LiteBus carries the position and never evaluates the policy. `RequireDeclaration<AuthorizationDeclaration, ICommand>()` and LB1020 enforce that every message states one, and an application guard reads it through `IMessageMetadataAccessor`.

### In-Process Idempotency

`IIdempotencyDefinition<TMessage>` declares the key a repeat is recognized by, and `IIdempotencyStore` remembers which keys were applied. `CommandModuleBuilder.EnableIdempotency()` registers two shortcuts and a completion handler that claim the key before the handler runs and settle it after. The key is applied on success and released on anything else, so a transient failure does not turn the retry into a false repeat. The durable inbox and outbox already deduplicate envelopes. This solves the same problem for in-process commands with the shortcut stage plus the declaration and the storage contract.

```csharp
IdempotencyDeclaration.KeyedBy<ApplyPaymentCommand>(command => command.PaymentId.ToString())
    .WithFingerprint<ApplyPaymentCommand>(command => $"{command.Amount}:{command.Currency}");
```

`WithFingerprint` declares a request fingerprint, and an applied key claimed again with a different fingerprint is refused with `FingerprintMismatch`. An unsettled claim older than the store's claim timeout is taken over, so a crashed claimant no longer blocks its key. Both outcomes deny the command with the codes in `IdempotencyRefusalCodes` (`idempotency.in-flight`, `idempotency.fingerprint-mismatch`), and the idempotency completion handler settles only a key the mediation claimed. `IdempotencyDeclaration.ReplayResult` records the first answer so a repeated result-producing command is answered with it. Without it, a repeat raises a configuration error naming the fix rather than inventing a `default`.

`InMemoryIdempotencyStore` ships from `LiteBus.Testing.Mediation`, because a store that forgets on restart and knows only its own process cannot make a claim about the system. `LiteBus.Commands.Storage.PostgreSql` ships the durable store with `ClaimTimeout` defaulting to five minutes on the database clock. The `litebus.idempotency.store` probe reports `Unhealthy` when idempotency is enabled and no store is registered. See [PostgreSQL Idempotency Store](../integrations/commands-postgresql-idempotency-store.md).

`WithIdempotencyKey(...)` in `LiteBus.Extensions.AspNetCore` is an endpoint filter that keys the command an endpoint sends by the `Idempotency-Key` request header, configured by `IdempotencyKeyFilterOptions` (header name, required by default, 255 characters at most) and carried into the pipeline by `CommandMediationSettings.WithIdempotencyKey(HttpContext)`. `MediationResult.ToHttpResult(...)` answers an in-flight key with 409, a fingerprint mismatch with 422, other denials with 403, and invalid commands with 400. See [ASP.NET Core Idempotency Key](../integrations/aspnetcore-idempotency-key.md).

`Idempotency.FromCommandKey(suffix)` keys an outbox or inbox item by the idempotency key the in-flight command was granted, so a retried command enqueues the same rows. `OutboxEnqueueItem<TEvent>.FromAmbient` and `InboxAcceptItem<TMessage>.FromAmbient` stamp the trace of the message being handled onto what the handler writes, through `MessageTrace.FromAmbient()`. Both are explicit opt-ins, and `UseAmbientTrace()` on either axis module stamps envelopes that carry no explicit trace.

### Unit-of-Work Commit Priority

`IUnitOfWork` and `UseUnitOfWork<TUnitOfWork>()` on the command and query module builders commit the application unit of work at `HandlerPriorities.UnitOfWork` once per mediation that succeeded. A denied, invalid, shortcut-answered, or faulted mediation commits nothing. The application supplies the commit through `CommitAsync`. LiteBus never opens a transaction.

`HandlerPriorities` reserves a priority window for handlers shipped by LiteBus, so ordering against them is a documented guarantee. `ReservedFloor` (1,000,000) opens it, `ReservedCeiling` (2,000,000) closes it, and application handlers own the band below the floor, where an unannotated handler already sits, and the band at or above the ceiling. `UnitOfWork` names the position in that upper band where an application commits, which is what makes an audit record staged by the writer at `Observability` part of the transaction that applies the change it describes. LB1022 reports a handler priority inside the reserved window.

### Recurring Commands

`LiteBus.Commands.Recurring` sends a command on an interval from a background loop:

```csharp
commands.AddRecurring<ReconcileCommand>(options =>
{
    options.Interval = TimeSpan.FromMinutes(5);
});
```

`RecurringCommandHostOptions` carries `Enabled`, `Interval` (one minute by default), `StartupDelay`, `ErrorBackoff` (five minutes by default), and `Validate`, which rejects a zero `Interval` or `ErrorBackoff`. `AddRecurring` registers the command it sends. A send that loses an optimistic-concurrency race to another instance is logged at Information and the loop waits `Interval` rather than `ErrorBackoff`, governed by `IsConcurrencyConflict` (defaulting to `IsConcurrencyConflictByTypeName`).

`RequireLease` takes a named lease before each pass (`LeaseName`, defaulting to the command type's full name) and skips the pass when another instance holds it, through the `IRecurringCommandLease` contract. `LiteBus.Commands.Recurring.Storage.PostgreSql` supplies a renewable lease row in `litebus_recurring_leases`, registered with `UsePostgreSqlRecurringLease(...)` and configured by `PostgreSqlRecurringLeaseOptions` (`LeaseDuration`, 30 seconds by default, and `RenewInterval`, a third of it by default). Lease times come from the database clock, the holder renews in the background while the pass runs, a crashed holder's lease expires on its own, and no connection is held between statements, so the lease works behind a transaction-mode PgBouncer. Composition fails when `RequireLease` is set and no lease is registered. See [Recurring Commands](../integrations/recurring-commands.md) and [Paged Fan-Out](../reliable-messaging/paged-fan-out.md).

### Marten Support

`LiteBus.Commands.Storage.Marten` brings the command axis to Marten. `UseMartenUnitOfWork()` commits the scoped `IDocumentSession`. `UseMartenIdempotencyStore(...)` keeps idempotency claims as Marten documents in their own serializable sessions. `MartenAuditTrail` stages each successful audit record in the handler's session so it commits with the change, while denial and failure records are written on their own so a rolled-back session cannot lose them.

`LiteBus.Outbox.Storage.Marten` stages outbox rows on the current session with `QueueSqlCommand` through `UseMartenTransactionalOutbox()`, so the row commits in the same `SaveChangesAsync` as the documents. It suits an application whose session serves reads and writes, where the ambient-transaction route would open a write transaction for every read. `PostgreSqlOutboxSchema.CreateInsertStatement` returns the outbox insert for one envelope at the current schema version, so a unit of work that queues SQL writes the row the PostgreSQL store writes instead of hand-written column lists. See [Marten Unit of Work, Idempotency, and Audit](../integrations/commands-marten.md), [Marten outbox storage](../integrations/outbox-marten-storage.md), and [Transactional messaging writes](../reliable-messaging/transactional-writes.md).

### Per-Handler Delivery, Staged Domain Events, Ambient Trace

`OutboxModuleBuilder.EnablePerHandlerDelivery()` writes one outbox envelope per subscribed main handler of an event, recorded on the `OutboxEnvelope.Handler` column, and the in-process dispatcher publishes each envelope to that handler alone, so a failing reaction retries, dead-letters, and is replayed on its own while the others publish. Per-handler message ids and idempotency keys are derived deterministically so a retried enqueue resolves to the same rows. A handler added after the enqueue does not receive events already enqueued, and enqueueing an event with no subscribed main handler throws `NoHandlerFoundException`. Use it only with in-process dispatch. Broker dispatchers publish the full event per envelope, so per-handler envelopes would duplicate broker publication.

`OutboxModuleBuilder.StageCollectedEvents()` registers a scoped `IDomainEventCollector` and a completion handler at `HandlerPriorities.Persistence` that enqueues the events a handler collected into `ITransactionalOutbox` when the mediation succeeded, before the unit-of-work commit. `OutboxModuleBuilder.UseAmbientTrace()` and `InboxModuleBuilder.UseAmbientTrace()` stamp accepted or enqueued envelopes that carry no explicit trace with the trace of the message being handled.

### Mediation Is Observable

`LiteBus.Messaging.Extensions.OpenTelemetry` registers one span per mediation and three metrics: total duration, a count tagged by outcome and decision code, and a decision counter tagged by the stage and the handler that stopped the message. That last one is what answers "which stage denied this" without reading a stack trace. Only a `Failed` outcome sets the span error status, because a denial is a decision, and marking every refused request as an error makes a trace view useless for finding the requests that actually broke.

```csharp
services.AddOpenTelemetry()
    .WithTracing(tracing => tracing.AddLiteBusMediationInstrumentation())
    .WithMetrics(metrics => metrics.AddLiteBusMediationMetrics());
```

`LiteBusMediationTelemetry` declares the `LiteBus.Mediation` activity source and meter with public instrument names (`litebus.mediation.duration`, `litebus.mediation.count`, `litebus.mediation.stage.duration`, `litebus.mediation.decisions`). `MessageModuleBuilder.UseTelemetry(new MediationTelemetryOptions { StageSpans = true, StageMetrics = true })` enables per-stage spans and per-stage durations while investigating. Both stay disabled by default, because mediation volume is orders of magnitude above durable-processing volume.

### Composition Can Be Inspected

The host logs what it composed as one startup line, one call shows what runs for one message, and application conventions are enforced as startup failures:

```csharp
// What the host actually composed, as one startup line.
logger.LogInformation("{Summary}", provider.GetRequiredService<LiteBusCompositionSummary>());

// What runs for one message, in the order it runs.
var plan = provider.GetRequiredService<IMessageReader>().Explain(typeof(CloseOrganizationCommand));

// The application's own conventions, as startup failures.
messaging.RequireUniqueAuditActions().RequireAuditActionFormat();
```

The summary names every open generic handler and the number of messages it was closed over. That is the mitigation for the one implicit behavior worth watching. Adding a file to a scanned assembly inserts a pipeline stage into every message it fits, with no registration line in the composition code to review. `messaging.RequireExplicitOpenGenerics()` turns that into a composition failure naming each handler that breaks the rule and the registration line that fixes it, and is opt-in because picking up open generics is what an assembly scan has meant since v4. `IMessageReader.Explain` returns a `MessagePipelinePlan` with every handler that runs in the order it runs, as `MessagePipelineStep` records naming the stage, the priority, the handler, the contract, and whether it arrived indirectly or from a closed open generic. Open generic handlers may also take two type parameters, binding the message type and the result type the message declares through `IProducesResult<TMessageResult>`, so a generic post-handler, completion handler, or error handler reaches the typed contract.

### Cross-Axis Guards

The axis builders accept a handler written against a messaging-level pipeline contract, when its message type is constrained to that axis:

```csharp
// One implementation, registered per axis, rather than two near-identical classes.
internal sealed class OrganizationGuard<TMessage> : IMessageGuard<TMessage>
    where TMessage : ICommand
{ ... }

registry.AddCommands(commands => commands.Register(typeof(OrganizationGuard<>)));
```

A handler constrained to neither axis is still refused. Nothing says which axis it is for, and accepting it would silently close it over every message in whichever axis registered it. Main handler contracts are excluded, because a command handler and a query handler mean different things.

### The Execution Context Is Injectable

`IExecutionContext` is registered as a scoped dependency:

```csharp
// Before: the dependency is invisible in the type signature, and a unit test needs an ambient scope.
var occurrence = AmbientExecutionContext.Current.Data.Get<Occurrence>();

// After.
public sealed class Handler : ICommandHandler<CancelOccurrenceCommand>
{
    private readonly IExecutionContext _context;

    public Handler(IExecutionContext context) => _context = context;
}
```

`AmbientExecutionContext` is unchanged and remains the way to reach the context from code that runs outside dependency injection.

Scoped here means per mediation, not per request. The dispatch scope is created from the root `IServiceScopeFactory`, so it is a sibling of the ambient HTTP request scope rather than a child of it. A scoped `DbContext` in a handler is not the request's `DbContext`, two `SendAsync` calls in one request get two different scoped instances, and a test that seeds a scoped service from its own scope is not touching the instance the handler used. Per-mediation state belongs in `IExecutionContext.Data`, which is scoped to the message rather than to whichever scope happens to surround it. `IExecutionContext.HandledAt` is the instant the mediation started, read once from the messaging module's `TimeProvider`.

`Data` is an `IHandleContextData`, a store keyed by the CLR type of the value rather than by a string, created once per mediation. `Get<T>` throws `HandleContextDataNotFoundException` naming the type, `TryGet<T>` covers the optional case, and access is lock-guarded because parallel event handlers share one execution context. Keyed overloads cover a mediation that legitimately holds two values of one type:

```csharp
context.Data.Set(new AccountId("a-1"), debit);
context.Data.Set(new AccountId("a-2"), credit);
```

### Testing Without a Host

`MediationHarness` in `LiteBus.Testing.Mediation` runs the real pipeline over hand-supplied handler instances, with no host and no container, and reports which pre stages ran. Asserting that a guard denies meant starting the whole host in v6, which for an application with a relational store meant a database container for a test about one authorization decision. `MediationHarnessResult.StagesRun` is the part no consumer can build, because only the stage runner records it. It runs the real strategies through the real stage runner, so the fixed stage order, the validator stage's aggregation, and priority ordering all apply. What it leaves out is composition, so a registration a host would reject still has to be asserted against a host. `MessageRegistryFactory.Create()` and `MessageMediatorFactory.Create(registry, dispatchScopeFactory)` are the public seams it is built on, both `EditorBrowsable(Never)`, for a manual host composing LiteBus without a container.

`LiteBus.Testing.DurableMessaging` adds an in-memory `ITransactionalOutbox` (`AddTestTransactionalOutbox`), `ProcessorPassHelpers.DrainOutboxAsync` and `DrainInboxAsync`, a `ScriptedOutboxDispatcher` that fails chosen contracts on chosen attempts, and `StoreSchemaContract.AssertCompatible`, which reports every schema difference at once. See [Testing the outbox without a database](../reliable-messaging/transactional-writes.md).

### Turn Faults Into Refusals

`IFaultRefusalClassifier`, registered with `MessageModuleBuilder.UseFaultRefusalClassifier<TClassifier>()`, ends a mediation as a refusal when any stage raises a fault it recognizes (through `TryClassify`), including a commit fault raised in the completion stage, so `TrySendAsync` returns it as a value and error handlers do not run. `PostgreSqlConstraintRefusalClassifier` maps unique (23505) and exclusion (23P01) violations on configured constraints to denials with application codes. Cancellation is never classified, and nothing changes when no classifier is registered. See [Turning Faults Into Refusals](../concepts/handler-pipeline.md#turning-faults-into-refusals).

`TransportOutboxDispatcherOptions.TenantRoutingStrategy` and `OutboxModuleBuilder.UseContractResolver(IMessageContractResolver)` make the dispatcher's tenant routing and the envelope factory's contract resolver configurable. Both constructor parameters existed in v6, but no builder could fill them. `IOutboxManager.GetFailureSummaryAsync` reports, per contract, the `Failed` and `DeadLettered` counts with the most recent error and time, so a health probe distinguishes a failing message from a slow backlog. See [Message States and Alerting](../operations/message-states.md).

## Verification Checklist

- Every project targets .NET 10 and references one LiteBus version.
- `dotnet restore` reports no v6 LiteBus package in the transitive graph.
- Every validator returns `Validity` or derives from a throwing adapter, and tests assert `Invalid` / `Denied` where they asserted thrown exceptions.
- No synchronous pre-handler or post-handler remains. No `IAsyncMessagePreHandler`, `IAsyncMessagePostHandler`, or `IAsyncMessageErrorHandler` reference remains.
- No `Abort`, `LiteBusExecutionAbortedException`, or `Handle(object)` reference remains.
- Custom mediation strategies call `RunAsyncPreStages` and the new error-runner signature from the `LiteBus.Messaging` namespace.
- `HookFailurePolicy` is explicit where the service relied on dead-lettering after a hook failure.
- Custom stores, signals, registries, descriptors, contexts, and host adapters implement the new members.
- Kafka publishers and consumers upgraded together. No bare `IProducer<string, byte[]>` resolution. SQS and Kafka external consumers read both header names during rollout.
- AMQP ingress queues drained before redeploy where duplicates matter. `TrustApplicationHeaders` is set where `litebus-message-id` is relied on.
- PostgreSQL outbox metadata records schema version 2. Entity Framework Core migrations applied. Idempotency and recurring-lease tables exist only where adopted.
- Saga purges carry a predicate or `Take`. Retention purges handle a missing policy.
- A smoke message completes through each configured inbox, outbox, and transport route, and a guard denial dead-letters on first attempt in each durable axis.
- Diagnostics, management authorization, and OpenTelemetry registration use the v7 host adapters, including mediation instruments where adopted.
- Unit, integration, package, and documentation checks pass.
