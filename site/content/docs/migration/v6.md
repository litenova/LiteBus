# Migration Guide v6

LiteBus 6.0 upgrades the released v5.x line to a .NET 10 mediator and durable messaging runtime. No v6 database schema has been released before 6.0.0. A database found during this upgrade is therefore a v5 database, an application-owned schema, or test data. It is not an older v6 schema.

The PostgreSQL inbox, outbox, and saga schemas all start at version **1** in v6. Their version 1 create scripts contain the complete 6.0 table shape. LiteBus does not ship or run an automatic v5-to-v6 table conversion because the inbox identity, payload storage, idempotency scope, lease fencing, and terminal state fields changed together.

## Why v6 Is a Major Upgrade

v5 combined message intent, module registration, storage, and host execution through broad APIs. That made common examples short, but it also hid which store, dispatcher, host loop, and external SDK an application actually used. v6 separates those roles and validates the completed module graph before building services.

| Decision | v6 result | Reason |
| --- | --- | --- |
| Target .NET 10 only | Every package targets `net10.0` | The runtime, hosting, and analyzer code use one supported BCL and async surface instead of carrying multi-target branches. |
| Replace flat durable registration | Storage, dispatch, ingress, and processors register inside `AddInbox` or `AddOutbox` | The parent module owns its children, so dependency order is validated without marker services or callback-order rules. |
| Replace scalar writer options | `InboxAcceptItem` and `OutboxEnqueueItem` carry explicit metadata value objects | Identity, idempotency, visibility, tracing, tenancy, and routing can evolve independently without adding overloads or nullable option bags. |
| Split packages by concern | One store, broker, host, or telemetry concern per package | A PostgreSQL-only service does not receive RabbitMQ, Kafka, AWS, Azure, or EF Core transitively. |
| Replace sequential durable loops | Pipelined processors with leases, renewal, retries, and terminal persistence | Concurrency and shutdown behavior use one processor model, including stale-lease fencing. |
| Start v6 schemas at version 1 | Final 6.0 columns and indexes live in each v1 create script | Preview-only migration history has no released consumer and would misidentify v5 metadata as an older v6 database. |
| Replace direct host wiring | Modules declare startup tasks, background services, and diagnostic checks in a host manifest | Core and adapter packages remain independent of `Microsoft.Extensions.Hosting`. |

## Recommended Upgrade Order

Use a staged deployment. Do not deploy v6 binaries against active v5 durable tables.

1. Move the application to the .NET 10 SDK and update direct LiteBus package references.
2. Compile the mediator-only path first: commands, queries, events, handlers, error handlers, and module registration.
3. Replace v5 inbox and outbox writer calls with v6 items and metadata.
4. Compose one storage adapter and one dispatcher for each durable axis. Add ingress only where the service consumes broker messages.
5. Stop v5 durable writers and processors, then drain or export remaining rows.
6. Create v6 version 1 tables or run a reviewed application-owned data migration into new tables.
7. Start one v6 instance with schema validation and processors disabled. Verify contracts, row counts, indexes, diagnostics, and broker connectivity.
8. Enable processors, confirm the backlog drains, then roll out the remaining instances.

The database step is intentionally after the code compiles. It prevents an application rollback from loading v6 rows through v5 store code.

## Package Reference Changes

Semantic mediator package IDs remain stable. Durable storage and hosting packages changed because their v5 names did not state the role they performed.

| v5 package | v6 package or action | Why |
| --- | --- | --- |
| `LiteBus.Commands.*` | Same package family | Command contracts and pipelines remain a distinct semantic module. |
| `LiteBus.Queries.*` | Same package family | Query contracts and pipelines remain a distinct semantic module. |
| `LiteBus.Events.*` | Same package family | Event contracts and pipelines remain a distinct semantic module. |
| `LiteBus.Extensions.Microsoft.DependencyInjection` | Keep for the semantic aggregate, or reference per-module DI packages | The aggregate contains mediator modules only. Durable and broker adapters remain opt-in. |
| `LiteBus.PostgreSql` | `LiteBus.Storage.PostgreSql` | Shared PostgreSQL code is storage infrastructure, not a feature module. |
| `LiteBus.Inbox.PostgreSql` | `LiteBus.Inbox.Storage.PostgreSql` | The package implements inbox persistence only. |
| `LiteBus.Outbox.PostgreSql` | `LiteBus.Outbox.Storage.PostgreSql` | The package implements outbox persistence only. |
| `LiteBus.Inbox.Extensions.Microsoft.Hosting` | `LiteBus.Runtime.Extensions.Microsoft.Hosting` plus `inbox.EnableInboxProcessor()` | Processor work is declared by the inbox module and executed by the shared host bridge. |
| `LiteBus.Outbox.Extensions.Microsoft.Hosting` | `LiteBus.Runtime.Extensions.Microsoft.Hosting` plus `outbox.EnableOutboxProcessor()` | The outbox follows the same manifest path. |
| `LiteBus.Inbox.PostgreSql.Extensions.Microsoft.Hosting` | No direct replacement | PostgreSQL schema initialization is selected inside `UsePostgreSqlStorage`. |
| `LiteBus.Outbox.PostgreSql.Extensions.Microsoft.Hosting` | No direct replacement | PostgreSQL schema initialization is selected inside `UsePostgreSqlStorage`. |

Add only the integration package used by the service. For example, an outbox that publishes to Kafka needs `LiteBus.Outbox.Dispatch.Kafka` and `LiteBus.Transport.Kafka`; it does not need inbox ingress or another broker SDK.

## Target Framework and Build

Update application projects:

```xml
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <Nullable>enable</Nullable>
</PropertyGroup>
```

Use the .NET SDK selected by the repository or application `global.json`. Restore after all LiteBus package references use the same 6.0 version. Mixed v5 and v6 LiteBus packages are unsupported because contract assemblies, module builders, and durable envelopes changed as one release.

## Module Composition

### v5

v5 registered modules and durable infrastructure as independent top-level entries:

```csharp
services.AddLiteBus(modules =>
{
    modules.AddMessageModule(messaging =>
        messaging.RegisterFromAssembly(applicationAssembly));
    modules.AddCommandModule(commands =>
        commands.RegisterFromAssembly(applicationAssembly));

    modules.AddCommandInboxModule();
    modules.AddPostgreSqlCommandInboxStore(postgres =>
        postgres.UseDataSource(dataSource));
    modules.AddCommandInboxProcessorHosting();
});
```

The registry could not express that the storage and processor belonged to the same inbox composition. Registration order and marker checks filled that gap.

### v6

v6 composes the same service through the inbox parent:

```csharp
services.AddLiteBus(liteBus =>
{
    liteBus.AddMessaging(_ => { });
    liteBus.AddCommands(commands =>
        commands.RegisterFromAssembly(applicationAssembly));

    liteBus.AddInbox(inbox =>
    {
        inbox.Contracts.Register<ShipOrder>("orders.ship", version: 1);
        inbox.UsePostgreSqlStorage(postgres =>
            postgres.UseDataSource(dataSource));
        inbox.UseInProcessDispatch();
        inbox.EnableInboxProcessor();
    });
});
```

`AddLiteBus` now receives `Action<ILiteBusBuilder>`. Package-owned extensions add standard modules. `liteBus.Modules` remains available for custom `IModule` registration, but application code should not bypass the inbox or outbox parent when adding storage, dispatch, ingress, saga, or processor children.

### Composition Mapping

| v5 | v6 |
| --- | --- |
| `AddMessageModule(...)` | `AddMessaging(...)` |
| `AddCommandModule(...)` | `AddCommands(...)` |
| `AddQueryModule(...)` | `AddQueries(...)` |
| `AddEventModule(...)` | `AddEvents(...)` |
| `AddCommandInboxModule(...)` | `AddInbox(...)` |
| `AddOutboxModule(...)` | `AddOutbox(...)` |
| `AddPostgreSqlCommandInboxStore(...)` | `inbox.UsePostgreSqlStorage(...)` |
| `AddPostgreSqlOutboxStore(...)` | `outbox.UsePostgreSqlStorage(...)` |
| `AddCommandInboxProcessorHosting(...)` | `inbox.EnableInboxProcessor(...)` |
| `AddOutboxProcessorHosting(...)` | `outbox.EnableOutboxProcessor(...)` |

Storage no longer implies dispatch. Select `UseInProcessDispatch`, a broker dispatch package, or a custom `IInboxDispatcher` / `IOutboxDispatcher` explicitly.

## Inbox Writer Migration

### API Mapping

| v5 | v6 |
| --- | --- |
| `ICommandScheduler` | `IInbox` |
| `ScheduleAsync(command, options, cancellationToken)` | `AcceptAsync(item, cancellationToken)` |
| `CommandScheduleOptions` | `InboxAcceptMetadata` on `InboxAcceptItem<TMessage>` |
| `CommandReceipt<TCommand>` | `InboxReceipt<TMessage>` |
| `IIdempotentCommand.IdempotencyKey` | `Idempotency.Keyed` metadata |
| `CommandId` | `MessageIdentity.Supplied` |
| `VisibleAfter` | `MessageVisibility.At` or `MessageVisibility.After` |

v5 example:

```csharp
var receipt = await scheduler.ScheduleAsync(
    command,
    new CommandScheduleOptions
    {
        CommandId = requestId,
        IdempotencyKey = $"ship:{orderId}",
        VisibleAfter = clock.GetUtcNow().AddMinutes(5),
        CorrelationId = correlationId,
        TenantId = tenantId
    },
    cancellationToken);
```

v6 example:

```csharp
var item = InboxAcceptItem<ShipOrder>.From(command) with
{
    Metadata = InboxAcceptMetadata.Immediate with
    {
        Identity = new MessageIdentity.Supplied(requestId),
        Idempotency = new Idempotency.Keyed($"ship:{orderId}"),
        Visibility = new MessageVisibility.After(TimeSpan.FromMinutes(5)),
        Trace = new MessageTrace.Correlated(correlationId),
        Tenant = new TenantScope.Isolated(tenantId)
    }
};

var receipt = await inbox.AcceptAsync(item, cancellationToken);
```

The metadata variants make absence explicit. `MessageIdentity.Generated`, `Idempotency.None`, `MessageVisibility.Immediate`, `MessageTrace.None`, and `TenantScope.Unscoped` replace nullable fields whose interaction was easy to misread.

`IIdempotentCommand` is removed. Keeping idempotency outside the payload lets one command contract be accepted with different retry scopes at different edges. It also prevents a transport adapter from trusting a payload property before the payload has passed validation.

Result-bearing commands still execute through `ICommandMediator`. Do not put `ICommand<TResult>` messages into the inbox because the deferred processor cannot return `TResult` to the original caller.

## Outbox Writer Migration

### API Mapping

| v5 | v6 |
| --- | --- |
| `IOutboxWriter` | `IOutbox` |
| `AddAsync(event, options, cancellationToken)` | `EnqueueAsync(item, cancellationToken)` |
| `OutboxOptions` | `OutboxEnqueueMetadata` on `OutboxEnqueueItem<TEvent>` |
| `OutboxReceipt<TEvent>` | `OutboxReceipt<TEvent>` with v6 outcome semantics |
| `Topic` | `PublicationTarget.Topic` |
| `MessageId` | `MessageIdentity.Supplied` |

v5 example:

```csharp
var receipt = await outboxWriter.AddAsync(
    orderSubmitted,
    new OutboxOptions
    {
        MessageId = eventId,
        Topic = "orders.submitted",
        CorrelationId = correlationId,
        TenantId = tenantId
    },
    cancellationToken);
```

v6 example:

```csharp
var item = OutboxEnqueueItem<OrderSubmitted>.From(orderSubmitted) with
{
    Metadata = OutboxEnqueueMetadata.Immediate with
    {
        Identity = new MessageIdentity.Supplied(eventId),
        Idempotency = new Idempotency.Keyed($"order-submitted:{orderId}"),
        Trace = new MessageTrace.Correlated(correlationId),
        Tenant = new TenantScope.Isolated(tenantId),
        Target = new PublicationTarget.Topic("orders.submitted")
    }
};

var receipt = await outbox.EnqueueAsync(item, cancellationToken);
```

The typed item returns a typed receipt. Heterogeneous batches use `IReadOnlyList<OutboxEnqueueItem>` and the non-generic `EnqueueBatchAsync` overload. Parallel lists and the development-only homogeneous batch overload are not part of 6.0.

For writes that must commit with application state, use the v6 transactional writer for the selected store. PostgreSQL supports an ambient transaction provider. EF Core supports `IDbContextFactory<TContext>`, store-bound writers, and the save-changes interceptor described in [Transactional messaging writes](../reliable-messaging/transactional-writes.md).

## Contracts and Serialization

Stable contract names and versions remain the durable compatibility boundary:

```csharp
inbox.Contracts.Register<ShipOrder>("orders.ship", version: 1);
outbox.Contracts.Register<OrderSubmitted>("orders.submitted", version: 1);
```

Keep a v5 contract name and version when the CLR type and serialized payload still mean the same thing. Register a new contract version when fields or interpretation changed. Table schema version and message contract version are independent.

The PostgreSQL payload column changes from `jsonb` in v5 to opaque `text` in v6. LiteBus treats serialized JSON, encrypted text, and future codecs as payload bytes owned by the serializer and protection pipeline. PostgreSQL must not normalize, reject, or inspect ciphertext as JSON.

## Mediator and Handler Changes

The semantic entry points remain `SendAsync`, `QueryAsync`, and `PublishAsync`. Update these surrounding contracts:

| v5 | v6 | Reason |
| --- | --- | --- |
| `IEventPublisher` | `IEventMediator.PublishAsync` | One in-process event API avoids two names for the same handler pipeline. |
| `IRegistrableCommandConstruct`, `IRegistrableQueryConstruct`, `IRegistrableEventConstruct` | Removed | Builders register actual message and handler types directly. |
| Synchronous `IMessageErrorHandler.HandleError` and scalar async overloads | `HandleErrorAsync(MessageErrorContext<TMessage, TResult>, cancellationToken)` | One context carries the exception, prior result, handled outcome, and optional fallback result. |
| `IMessageMediator.MediateAsync<TMessage, TResult>` | `IMessageMediator.Mediate<TMessage, TResult>` | Task-returning strategies use `Task` or `Task<TResult>` as `TResult`; the removed API could create `Task<Task>`. |
| Multiple semantic `Multiple*HandlerFoundException` types | `MultipleHandlerFoundException` | Handler ambiguity has one runtime meaning across commands, queries, and events. |

Error contexts start with `MessageErrorOutcome.Unhandled`. Set `Outcome` to `Handled` only after recovery. A result-bearing handler must also set `HandledResult`.

## Processor and Hosting Changes

v6 ships one pipelined processor per durable axis. Sequential v5 loops and their host-specific wrappers are removed.

- `InboxProcessorOptions` and `OutboxProcessorOptions` configure batch size, concurrency, leases, retries, and tenant filters.
- `ProcessorHostOptions` configures host lifecycle timing only.
- `EnableInboxProcessor` and `EnableOutboxProcessor` declare the background loops.
- `LiteBus.Runtime.Extensions.Microsoft.Hosting` or the Autofac hosting bridge executes the manifest.
- Startup tasks run before background services. PostgreSQL schema initialization uses this path.
- Unexpected background loop faults stop the Generic Host instead of leaving the application alive without durable processing.

Do not register LiteBus processor types as `IHostedService` directly. Direct registration skips startup ordering, diagnostics, and shared shutdown behavior.

## Transport and Ingress Changes

v5 had no shared multi-broker transport platform. v6 requires a root transport plus the feature adapter that uses it:

```csharp
services.AddLiteBus(liteBus =>
{
    liteBus.AddKafkaTransport(options =>
    {
        options.BootstrapServers = configuration["Kafka:BootstrapServers"]!;
    });

    liteBus.AddOutbox(outbox =>
    {
        outbox.UsePostgreSqlStorage(postgres =>
            postgres.UseDataSource(dataSource));
        outbox.UseKafkaDispatch(dispatch =>
            dispatch.DefaultTopic = "orders.events");
        outbox.EnableOutboxProcessor();
    });
});
```

The root module owns the SDK client, connectivity probe, publisher circuit registry, and wire conventions. Dispatch owns outbound routing. Inbox ingress owns broker intake, safety limits, and acknowledgement policy. Keeping those layers separate prevents an outbound-only service from installing a consumer.

Canonical transport headers live on `TransportHeaders`. The AMQP-only header alias and the PascalCase SQS correlation fallback used during v6 development are removed before 6.0. Producers and consumers must use `correlation-id`.

## Diagnostics, Telemetry, and Management

v6 registers diagnostics through `IDiagnosticCheck` and the host manifest. ASP.NET Core health checks and management endpoints adapt those checks at the host boundary.

Register telemetry per axis:

```csharp
services.AddOpenTelemetry()
    .WithTracing(tracing => tracing.AddLiteBusTransportTracing())
    .WithMetrics(metrics =>
    {
        metrics.AddLiteBusInboxMetrics();
        metrics.AddLiteBusOutboxMetrics();
        metrics.AddLiteBusTransportMetrics();
    });
```

The aggregate OpenTelemetry package and AMQP-only circuit breaker meter names are removed. Use the inbox, outbox, and transport packages that match the running service.

Management endpoints require authorization by default. Configure the documented policy before mapping endpoints. Do not copy v5 health-check registrations that instantiate store or processor services directly.

## PostgreSQL Database Migration

### Release Facts

| Component | v5 released schema | v6 schema |
| --- | --- | --- |
| Inbox | Version 2, default table `litebus_inbox_commands` | Version 1, default table `litebus_inbox_messages` |
| Outbox | Version 2, default table `litebus_outbox_messages` | Version 1, same default table name but a different physical contract |
| Saga | Not shipped | Version 1, default table `litebus_saga_instances` |

The lower v6 number does not mean the v5 table is newer. Version metadata is scoped to the schema contract of a major release. v6 restarts at 1 because no v6 schema has been released.

`PostgreSqlInboxSchema.SqlFiles`, `PostgreSqlOutboxSchema.SqlFiles`, and `PostgreSqlSagaSchema.SqlFiles` expose only the v1 create and index files. There are no v2 or v3 v6 migration files.

### Why Automatic Conversion Is Unsafe

The physical differences require application decisions:

| Area | v5 | v6 decision required |
| --- | --- | --- |
| Inbox key | `command_id` | Rename or copy to `message_id`. |
| Payload | `jsonb` | Convert to opaque `text` without changing the contract payload. |
| Idempotency | Inbox key unique across the table | Normalize unscoped tenants and enforce `(tenant_id, idempotency_key)`. Outbox also gains idempotency. |
| Leases | Owner and expiry only | Clear active leases and initialize `lease_generation` to 0. |
| Terminal history | Latest error only | Decide how to populate completed, published, attempted, first-failed, and dead-letter timestamps. |
| Error data | `last_error` | Optionally map `error_type`; do not invent exception types from free text. |
| Tracing | Optional `trace_context` added by v5 schema version 2 | Preserve valid JSON trace text or set it to `NULL`. |
| Saga | No v5 table | Create a new v6 table. |

LiteBus cannot know whether a `Processing` or `Publishing` row was committed before the old process stopped, whether completed rows are audit records, or whether tenant normalization creates an idempotency collision. An automatic script could duplicate side effects or discard evidence.

### Path A: Drain and Recreate

Use this path when pending durable messages can be processed before the upgrade.

1. Stop traffic that writes to the v5 inbox and outbox.
2. Keep v5 processors running until no `Pending`, `Processing`, `Publishing`, or retryable `Failed` rows remain.
3. Export dead-letter and completed or published rows required for audit.
4. Stop every v5 instance and take a database backup.
5. Rename or remove the v5 tables through the application's migration process.
6. Create the v6 tables from each package's v1 script or call the schema helper from a deploy job.
7. Run `EnsureAsync` once to validate the physical shape and record v6 schema version 1. This also replaces a stale v5 metadata row after its old table has been removed.
8. Start v6 with processors disabled, run `ValidateAsync`, then enable processing.

The inbox default table name changed, so the v5 and v6 inbox tables can coexist during verification. The outbox default name did not change; use a temporary v6 name or rename the v5 table before creating the replacement.

### Path B: Preserve Rows in New Tables

Use this path when pending or dead-letter rows must survive the deployment.

1. Quiesce v5 writers and processors. Do not copy a moving lease set.
2. Create new v6 tables under temporary names from the v1 scripts.
3. Detect duplicate `(normalized tenant, idempotency key)` groups before inserting.
4. Copy identifiers, contract names, contract versions, payloads, routing, trace data, and business timestamps with an explicit mapping reviewed by the application owner.
5. Convert `payload jsonb` to its text representation. Test deserialization with the exact v6 serializer and contract registry.
6. Map `command_id` to inbox `message_id`.
7. Normalize a null or blank tenant to `''`, which is the v6 unscoped tenant value used for idempotency.
8. Clear `lease_owner` and `lease_expires_at`, set `lease_generation` to `0`, and decide whether in-flight rows return to `Pending`.
9. Populate new terminal and error timestamps only from evidence the v5 application recorded elsewhere. Leave unknown values null.
10. Compare row counts by status and contract, then run a deserialize-only verification for every retained contract version.
11. Point v6 store options at the new tables or swap names in one controlled database migration.
12. Run the schema helper once so metadata records version 1, then validate before enabling processors.

The numeric status values remain aligned for pending, active, terminal, failed, and dead-letter states. That does not make blind copying safe. An active v5 lease has no v6 generation fence, so it must not remain active after the cutover.

### Metadata Table

v5 and v6 both use `litebus_schema_versions`, but their version numbers describe different major-release contracts. Do not interpret a v5 inbox or outbox version 2 row as a v6 migration source.

When a v5 table still exists, the v6 schema helper rejects its column set with `PostgreSqlSchemaDriftException`. When the v5 table has been removed and the v6 table is created, the helper records version 1 for the configured component, schema, and table.

If a DBA creates the v6 table without calling the helper, remove or update only the matching stale metadata row as part of the reviewed migration. Do not drop a shared metadata table that also tracks another LiteBus table.

### Entity Framework Core

The v6 EF Core stores are new application-owned adapters. Generate an application migration from `GetModelBuilderConfiguration()` for the selected provider. Do not point the v6 EF store at a v5 PostgreSQL table and rely on model auto-creation.

For PostgreSQL, the v6 model uses opaque payload text, JSON trace context, tenant-scoped idempotency, chronological indexes, and `lease_generation`. SQLite stores durable timestamps as UTC ticks. MySQL uses provider-specific skip-locked lease SQL and named chronological indexes.

## Store and Adapter Authors

Custom v5 stores require a full interface migration:

- Split append, lease, state persistence, dead letter, retention, diagnostics, query, and purge roles.
- Return `InboxAppendResult` or `OutboxAppendResult` for every append in source order.
- Return `AlreadyAccepted` or `AlreadyEnqueued` when message identity or tenant-scoped idempotency resolves an existing row.
- Apply lease generations to renewal and terminal writes. A stale generation must fail even when the owner string matches.
- Use the database clock for relational eligibility, expiry, and renewal.
- Preserve caller cancellation on all async operations.
- Implement the published storage contract tests before replacing the built-in adapter.

Custom transports implement the v6 publisher and consumer contracts and can run `LiteBus.Transport.Testing`. Broker exceptions should be mapped at the adapter boundary, and acknowledgement must occur only after inbox acceptance succeeds.

## Testing Package Changes

v6 splits test support by concern:

| Need | Package |
| --- | --- |
| Shared clock and base helpers | `LiteBus.Testing` |
| Command, query, and event mediators | `LiteBus.Testing.Mediation` |
| Transport doubles | `LiteBus.Testing.Transport` |
| Inbox, outbox, and processor doubles | `LiteBus.Testing.DurableMessaging` |
| Host lifecycle helpers | `LiteBus.Testing.Hosting` |
| Third-party store conformance | `LiteBus.Storage.Testing` |
| Third-party transport conformance | `LiteBus.Transport.Testing` |

The framework-neutral base package does not pull an assertion library, Newtonsoft.Json, a broker SDK, or Generic Host dependencies into every test project.

## What Remains Stable

- `ICommand<TResult>`, `IQuery<TResult>`, and `IEvent`
- `ICommandMediator.SendAsync`
- `IQueryMediator.QueryAsync`
- `IEventMediator.PublishAsync`
- Stable message contract names and positive contract versions
- At-least-once durable processing semantics
- Granular opt-in packages for semantic modules

## Verification Checklist

- Every project targets .NET 10 and references one LiteBus version.
- `dotnet restore` reports no v5 LiteBus package in the transitive graph.
- `AddLiteBus` uses `ILiteBusBuilder` extensions.
- Every durable axis selects storage, dispatch, and processor behavior explicitly.
- Every broker adapter has one matching root transport module.
- Every persisted message type has a stable contract registration.
- Inbox and outbox calls use typed items for metadata and canonical heterogeneous batch APIs.
- v5 processors are stopped before database cutover.
- PostgreSQL inbox, outbox, and saga metadata records v6 schema version 1.
- No v2 or v3 v6 SQL migration is referenced by deployment code.
- Schema validation passes before processors start.
- Pending and failed row counts match the approved migration record.
- A smoke message completes through each configured inbox, outbox, and transport route.
- Diagnostics, management authorization, and OpenTelemetry registration use the v6 host adapters.
- Unit, integration, package, and documentation checks pass.

Run the application build and its migration tests after each phase. For the LiteBus repository itself:

```bash
dotnet build LiteBus.slnx --configuration Release
dotnet test LiteBus.slnx --configuration Release --no-build
pwsh ./scripts/Test-Documentation.ps1
```
