# Changelog

This file records the notable changes in each LiteBus release.

## v7.0.0

This is a major release for .NET 10, and this section describes the change from v6.0.2. The release adds a completion stage to the mediation pipeline, 4 named decision stages that decide whether work runs, declarative message metadata, and an audit trail and in-process idempotency built on those 3. Most of the breaking change is in the pre stage. Guards, validators, shortcuts, and pre-handlers are now 4 contracts that the framework distinguishes before it invokes them, so they run in a fixed order. The declaration model is general, not only an auditing feature. An application declares its own metadata, reads it back through an accessor, enforces it at compile time and at composition time, and positions its unit-of-work commit against the framework writers through a named priority band. In-process mediation is observable, a caller can receive a refusal as a value instead of catching it, and a caller can ask whether a message would be permitted without performing it.

The outbox schema moves to version 2 with a nullable handler column for per-handler delivery, and an existing table upgrades automatically where schema initialization is enabled. The inbox and saga schemas are unchanged, and the PostgreSQL idempotency and recurring-lease tables are new.

Transport metadata changes in 3 places, listed under Breaking. Kafka and SQS use the shared `litebus-route` and `content-type` header names, and AMQP ingress scopes its broker idempotency key to the queue. If a contextual payload encryptor is configured, drain the inbox and outbox before upgrading, because v6 encrypted those rows without the context that v7 authenticates.

### Added

- `LiteBus.Outbox.Storage.Marten` stages outbox rows on the current Marten `IDocumentSession` with `QueueSqlCommand`, so the row commits in the same `SaveChangesAsync` as the documents. Register it with `UsePostgreSqlStorage(postgres => postgres.UseMartenTransactionalOutbox())`. It suits an application whose session serves reads and writes, where the ambient-transaction route would open a write transaction for every read. It resolves `ReturnExisting` and `Strict` idempotency with one read before staging.
- `PostgreSqlOutboxSchema.CreateInsertStatement` returns the outbox insert for one envelope at the current schema version, so a unit of work that queues SQL writes the same row the PostgreSQL store writes, instead of maintaining hand-written column lists.
- `RetryOptions.IsPermanentFailure` marks an application exception as permanent. When it returns true, the inbox and outbox processors dead-letter the message on that attempt instead of spending the retry schedule on a failure that no retry can fix. A classifier that throws counts as not permanent.
- `IOutboxManager.GetFailureSummaryAsync` reports the `Failed` and `DeadLettered` counts per contract, with the most recent error and time, so a health probe can tell a failing message from a slow backlog.
- `LiteBusMessageDeniedException.DeniedBy` and `LiteBusMessageInvalidException.RejectedBy` name the guard or validator that refused the message, and the exception message includes its type name. Both are set from `PipelineDecision.DecidedBy`, which records the deciding handler for a guard denial, a validation failure, and a shortcut answer.
- `TransportOutboxDispatcherOptions.TenantRoutingStrategy` and `OutboxModuleBuilder.UseContractResolver(IMessageContractResolver)` make the dispatcher's tenant routing and the envelope factory's contract resolver configurable. Both values already existed as constructor parameters, but no builder could set them.
- The transport outbox dispatcher fills `TransportPublishRequest.MessageGroupId` and `TransportPublishRequest.DeduplicationKey` from the envelope: the idempotency key, or the message id when no key is set, and the tenant id, or the contract name when no tenant is set. The SQS adapter sets them on queues whose URL ends in `.fifo`, so outbox dispatch can publish to SQS FIFO queues.
- `KafkaTransportOptions.SocketTimeoutMs` and `KafkaTransportOptions.MessageSendMaxRetries` are positive when set and stay at the librdkafka default otherwise.
- `AmqpReceivedMessage` gains `QueueName`, and `AmqpConsumerOptions.MaxInFlightMessages` gives a typed `IAmqpConsumer` subscription the same admission control as the generic consumer path.
- `DiagnosticCheckRunOptions.RunTimeout` sets an overall budget for one diagnostic run. When it is not set, it defaults to the worst case of the probe count packed into `MaxParallelism` lanes at `Timeout` each. Probes still running when it expires are cancelled and reported unhealthy. Registering health checks or management endpoints rejects a negative budget.
- `AmbiguousMessageResolveException.Candidates` names the registered types that tied. `IdempotencyConfigurationException` reports an idempotency declaration mistake.
- `SagaPurgeFilter.Take` bounds a saga purge.
- The documentation gains a [Limits and Opt-in Boundaries](site/content/docs/reference/limits.md) page, and the documentation home states what LiteBus costs and maps each question to the page that answers it.
- `ILeaseRenewable.ReleaseLeaseAsync(LeaseReleaseRequest, CancellationToken)` returns a leased message to the queue without charging the attempt that its lease consumed. The pipelined processor calls it for every dispatch it cancelled during shutdown or a drain, so a host restart no longer moves `attempt_count`. The in-memory, PostgreSQL and EF Core inbox and outbox stores implement it. The default implementation releases nothing, so a custom store still compiles and falls back to lease expiry. `OutboxEnvelope.AsReleased` and `InboxEnvelope.AsReleased` are the matching transitions. EventIds 3011 (Debug) and 3012 (Warning, release failed) record the outcome.
- `MediationExceptionFilters.IsCallerCancellation` recognizes the caller's cancellation even when a dispatcher wrapped it in its own exception type.
- `RecurringCommandHostOptions.IsConcurrencyConflict` defaults to `IsConcurrencyConflictByTypeName`. When a send loses an optimistic-concurrency race to another instance, the loop logs at Information (EventId 2104) and waits `Interval` rather than `ErrorBackoff`, because the work it wanted is already done.
- `InMemoryTransportBroker` implements `IDisposable` and completes its destination channels.
- The 2 new operator pages are [Message States and Alerting](site/content/docs/operations/message-states.md) and [Production Runbook](site/content/docs/operations/runbook.md), with a reliability page on [Ordering and Concurrency Guarantees](site/content/docs/reliable-messaging/ordering.md), and a roadmap note keeping the integrator field report on [analyzer and API gaps](site/content/docs/roadmap/integrator-feedback.md).

- A fifth pipeline stage runs completion handlers in a `finally` on every mediation path, exactly once: `IMessageCompletionHandler<TMessage>`, `IMessageCompletionHandler<TMessage, TMessageResult>`, and the axis contracts `ICommandCompletionHandler`, `IQueryCompletionHandler`, and `IEventCompletionHandler`. Each receives a read-only `MessageCompletionContext` carrying the outcome, the result, the exception, the reason, and the elapsed duration. Post-handlers run only when the main handler succeeds, and error handlers run only for recoverable exceptions, so no earlier stage could observe how a message actually ended. Recording an audit entry, emitting a metric, or closing a unit of work belongs in this stage. A mediation that throws a non-recoverable fault completes as `Failed` with the exception, and cancellation during stream enumeration completes as `Canceled`, so the unit of work does not commit and the audit records the failure.
- The completion stage is not cancellable. Handlers receive `CancellationToken.None`, because the ending has already happened. Handing the stage the token that fired would drop the records that a later review looks for.
- A pre-stage handler that may refuse a message is a guard: it implements `IMessageGuard<TMessage>` and returns a `Verdict` from `DecideAsync`. The axis contracts are `ICommandGuard<TCommand>`, `IQueryGuard<TQuery>`, and `IEventGuard<TEvent>`. A refusal always carries a reason, may carry a code, and reports `MediationOutcome.Denied`, which an audit trail records as a denial. The compiler requires the decision, so nothing after it runs by accident, and an expected control-flow path stays off the exception path.
- A validator is a pre-stage handler that answers whether a message is well-formed: `IMessageValidator<TMessage>` returns `Validity` from `ValidateAsync`. The axis contracts are `ICommandValidator<TCommand>`, `IQueryValidator<TQuery>`, and `IEventValidator<TEvent>`. Well-formedness is a different question from whether the caller may send the message. A failure therefore reports `MediationOutcome.Invalid` rather than `Denied`, and stays out of the list that a security review reads. Unlike every other decision stage, this one runs every validator and collects their failures rather than stopping at the first, because a caller fixing a malformed message should not discover its problems one round trip at a time. `ValidationFailure` carries the message, the member it applies to, and an optional code.
- The refusal mapper contract `IMessageRefusalMapper<TMessage, TMessageResult>` turns a guard refusal or a validation failure into the value the caller receives, for applications that model failure as data rather than as an exception. The axis contracts are `ICommandRefusalMapper`, `IQueryRefusalMapper`, and `IStreamQueryRefusalMapper`. One registration against `ICommand` covers every command producing that result type, and a mapper registered against a concrete message takes precedence over it. Without a mapper, a refusal reaches the caller as `LiteBusMessageDeniedException` or `LiteBusMessageInvalidException`. A stream supplied by a refusal mapper is enumerated through the same runner as a handler stream, so a fault in it reaches the error stage.
- A pre-stage handler that answers a message whose work is already done is a shortcut: it implements `IMessageShortcut<TMessage>` or `IMessageShortcut<TMessage, TMessageResult>` and returns a `Shortcut` from `TryAnswerAsync`. The axis contracts are `ICommandShortcut<TCommand>`, `ICommandShortcut<TCommand, TCommandResult>`, `IQueryShortcut<TQuery, TQueryResult>`, `IStreamQueryShortcut<TQuery, TQueryResult>`, and `IEventShortcut<TEvent>`. A cache hit or a replayed idempotent command reports `MediationOutcome.Answered`, which an audit trail records as a success because nothing was denied. A security review reads exactly that separation of an answer from a denial.
- The framework fixes the stage order: guards, then validators, then shortcuts, then pre-handlers. Priority orders handlers inside a stage and never reorders the stages. A globally registered cache shortcut therefore cannot answer a caller that a message-specific authorization guard would have denied, and a malformed message cannot claim an idempotency key. The order states what each stage may assume about its input: a guard sees every message, a validator sees only messages the caller is allowed to send, a shortcut sees only well-formed ones, and a pre-handler sees only messages that are going to be handled. Under a single pre-handler stage, that ordering rested on a priority number the author had to remember, and indirect handlers ran ahead of direct ones regardless. ASP.NET Core documents the same hazard for `UseOutputCache` after `UseAuthorization`. LiteBus owns its stages, so it makes the mistake unrepresentable instead of documenting it. `PreStage` names the 4 stages, and `IPreStageHandlerDescriptor.Stage` records which one runs a handler.
- `Shortcut<TMessageResult>` types the answer over the result type of the message, so a shortcut that answers a result-returning message must supply the value the caller receives, as the compiler requires. Answering always carries the result. A stream query that means no items answers with `AsyncEnumerable.Empty<T>()`, which states that outright rather than leaving it implied by a missing value. A denial owes the caller nothing, so one guard contract fits every message, and the value a denied caller receives comes from a refusal mapper instead.
- `MessageContextExtensions.RunAsyncPreStages` gives a custom mediation strategy the same stage order the shipped strategies use, in one call rather than 4. Running one stage without the others cannot honor the ordering guarantee. `ResolveRefusalResult<TMessageResult>` applies the registered refusal mapper, or raises when none covers the message. Both live in `LiteBus.Messaging` rather than in the abstractions package.
- `RunAsyncErrorHandlers` and `RunAsyncCompletionHandlers` each take the execution context and open their own ambient scope, so a strategy no longer has to wrap them. The error runner also captures the `ExceptionDispatchInfo` itself, which preserves the original stack when nothing recovers. The completion runner resolves a post-handler's replacement result in preference to the handler's own. Both rules were previously a strategy's job to remember. The completion runner takes the outcome, the failure, and the reason that the strategy tracked, and builds the context from them. When error handlers recover, the mediation still completes as `Failed` but carries no exception, so completion tells a recovered fault from a propagated one.
- `LiteBusMessageDeniedException` and `LiteBusMessageInvalidException` reach the caller when no refusal mapper covers the message. Both are excluded from the recoverable-exception filter, so error handlers never see a decision as a fault. `LiteBusMessageInvalidException.Failures` carries every failure the validator stage collected.
- `MediationExceptionFilters.IsRefusal` and `IsRetryableDispatchException` classify a decision apart from a fault. The inbox and outbox processors use the second to dead-letter a refusal or a missing handler on the first attempt instead of spending the retry schedule on an answer that cannot change.
- `MediationOutcome` distinguishes `Succeeded`, `Answered`, `Denied`, `Invalid`, `Failed`, and `Canceled`. Every member is reported by some path, and each names a state the message ended in rather than a mechanism the pipeline used.
- `IExecutionContext.SuppressPostHandlers()` skips the post-handlers that have not run yet. Use it when the work turned out to be a no-op and the reactions to it should not fire, for example an idempotent command that detects it already ran. It does not stop the calling handler, and it does not change the outcome.
- Message metadata is declarative: `IMessageDescriptor.Metadata` exposes values resolved once at registration, from declaring attributes on the message type and from message definitions. A pipeline stage therefore reads a dictionary instead of reflecting on every dispatch.
- A message definition is a class that lives beside the message it describes and declares one value per concern through `IMessageDefinition<TMessage, TValue>`. Declarations are keyed by value type, so one class may declare several without ambiguity, and applications may declare their own value types, which LiteBus applies without interpreting. A declaration covers the message type it names and every message assignable to it, so one definition can describe a family of messages. When several apply, the most derived declaration wins.
- `IMessageDeclarationSource` marks an attribute as a source of message metadata and states the value type it declares. Only attributes that implement it are collected, which keeps metadata bounded. It puts attributes and definitions on one key, so a definition genuinely overwrites an attribute rather than sitting beside it.
- An audit trail at the mediation boundary records each mediation: `[Audited]` and `[AuditExempt]`, or an `IAuditDefinition<TMessage>`, declare the constant half of a record, and `IAuditScope` supplies what only the handler knows. `EnableAuditing()` on the command and query module builders registers the writer, which hands an `AuditRecord` to the application's `IAuditTrail`. Refusals, failures, and cancellations are recorded as first-class outcomes, because the writer runs at the completion stage. `[AuditExempt]` records the same `DeclarationExemption` that `[DeclarationExempt(typeof(AuditDeclaration), ...)]` records, so every exemption a message carries reads from one place, whichever spelling wrote it. Its rationale is validated when the attribute is constructed.
- The trail itself is registered on the messaging module through `UseAuditTrail<TAuditTrail>(lifetime)`, `Scoped` by default, or `UseAuditTrailInstance` for a pre-created instance, beside the outcome mapper. The shared half of auditing is therefore configured in one place, while the per-axis switch stays where the decision belongs. The instance overload carries its own name because a pre-created instance is necessarily a singleton, which a second `UseAuditTrail` overload would hide at the call site.
- `AuditDeclaration` is a closed hierarchy of `AuditedDeclaration` and `AuditExemptDeclaration`, so a declaration cannot hold a combination that means nothing, such as a category on an exemption.
- `ReasonRequired` on an audited declaration is enforced. When a successful action declares it and supplies no reason, the writer raises `AuditReasonMissingException` rather than writing an incomplete record.
- `AuditTrailDiagnosticCheck` reports the `litebus.audit.trail` probe as unhealthy when auditing is enabled and no `IAuditTrail` is registered, so a missing sink surfaces before the first audited mediation. It resolves the trail through a dispatch scope rather than from the provider, so the default scoped registration passes a container that validates scopes. It reports `Healthy` with the writer name when an application replaced the record writer, since a writer LiteBus did not build need not use a trail at all.
- `IAuditOutcomeMapper` and `MessageModuleBuilder.UseAuditOutcomeMapper` let an application that refuses by throwing record its own exception as `AuditOutcome.Denied` rather than `AuditOutcome.Failed`. Refusing through a guard needs no mapper.
- `MediationExceptionData.SuppressedCompletionFaults` is the key under which a completion-handler fault is attached to the exception that was already ending the mediation. A failed audit write is therefore never silently discarded.
- `LB1018` reports command and query types that state no audit position, so an unaudited message is a recorded decision rather than an oversight. It is disabled by default. Enable it with `dotnet_diagnostic.LB1018.severity = warning`.
- `LB1019` reports a shortcut that implements the untyped shortcut contract for a message that produces a result. That contract compiles there because `ICommand<TResult>` derives from `ICommand`, and answering from it fails at runtime with `LiteBusConfigurationException`. The typed contract is a strict superset for such a message, so the rule names it, and the declaration is where the fix goes. Open generic shortcuts are not reported, and guards and validators never are, because a refusal owes the caller no result, so one contract is correct for every message on those stages.
- Registration rejects an untyped shortcut declared for a message that produces a result, so the mistake `LB1019` reports cannot reach production in a project that does not reference the analyzer package. The check runs from both directions, because a handler may be registered before or after the message it handles.
- `HandlerPriorities` reserves a priority window for handlers shipped by LiteBus, so ordering against them is a documented guarantee. `ReservedFloor` opens it and `ReservedCeiling` closes it. Application handlers own the band below the floor, where an unannotated handler already sits, and the band at or above the ceiling. `UnitOfWork` names the position in that upper band where an application commits. That position is what makes an audit record staged by the writer at `Observability` part of the transaction that applies the change it describes. Only `Persistence` and `Observability` may be reordered between releases, and only against each other. `UnitOfWork` sits at `ReservedCeiling + 100`, leaving the ceiling itself a pure boundary marker with nothing on it.
- `IExecutionContext.Data` is an `IHandleContextData`: a store keyed by the CLR type of the value rather than by a string, created once per mediation. A guard whose decision depends on loaded state hands the loaded object to the main handler instead of forcing a second round trip. That round-trip cost is what keeps authorization inside handlers rather than in the stage that owns the decision. `Items` stays for string-keyed interop. `Get<T>` throws `HandleContextDataNotFoundException` naming the type, and `TryGet<T>` covers the optional case. Access is lock-guarded because parallel event handlers share one execution context.
- `IMessageMetadataAccessor` reads a message type's declared metadata from application code, through `ForMessage` and `TryGet`. Reading a declaration previously meant injecting `IMessageRegistry`, calling `Find`, and reaching through `IMessageDescriptor.Metadata`, which made the registry's descriptor shape part of every application reading a declaration it wrote itself. An unregistered type raises `MessageMetadataNotFoundException` rather than answering with an empty collection, because an empty answer turns a missing registration into a permission check that silently passes. An unregistered runtime type that mediation resolves through a base descriptor reads that descriptor's metadata instead, exactly as if registered, and is audited under its declaration. Only a type that nothing covers raises, and an ambiguous fallback raises `AmbiguousMessageResolveException`.
- `MessageModuleBuilder.RequireDeclaration<TValue>()` fails composition for any registered message that neither declares a value of that type nor records an exemption from it. The error names every offender, grouped by the declaration each one omits. The check runs through the new `IModuleConfiguration.RegisterCompositionValidation` hook, after every module has built, because the messaging module is foundational and has no commands to inspect during its own build.
- `[DeclarationExempt(typeof(TValue), rationale)]` records that a message deliberately declares nothing for one metadata type. It is repeatable, and every instance is aggregated into one `DeclarationExemptions` value, readable through the accessor like any other declaration. The rationale is what separates a decision from an omission.
- `[MessageDeclaration(typeof(TValue))]` states, on an attribute class, which metadata value that attribute declares. `IMessageDeclarationSource.DeclarationType` is a runtime property that an analyzer cannot execute, so without a static declaration no compile-time rule can tell that `[RequiresPermission]` is how a message states its permission. Registration fails when the annotation and the property name different types.
- `LB1020` reports a command or query type that states no position on a metadata value type named in `litebus_required_declarations`, and `LB1021` reports a configured name that does not resolve. `LB1018` is the preconfigured instance of `LB1020` over `AuditDeclaration`, and shares its analysis rather than duplicating it. A written policy such as "every command states the permission it requires" becomes a build failure instead of something code review has to catch.
- `ThrowingValidator<TMessage, TException>`, with the axis specializations `ThrowingCommandValidator` and `ThrowingQueryValidator`, adapts a validator whose body still reports failure by throwing. It is migration scaffolding for the `Validity` signature change. Adapted and converted validators mix in one mediation because the stage collects across both, so a codebase converts module by module instead of in one commit touching every validator. Only the named exception type is caught, so a genuine fault inside a validator still ends the mediation as a failure.
- Open generic handlers may take 2 type parameters, binding the message type and the result type that the message declares through the new `IProducesResult<TMessageResult>` marker on `ICommand<T>`, `IQuery<T>` and `IStreamQuery<T>`. A generic post-handler, completion handler, or error handler reaches the typed contract instead of falling back to an `object?` it can do nothing with. Arity 2 is accepted only when the handler implements a contract taking both parameters in order, so a second parameter the handler invented is still rejected. A message declaring no result is skipped the way a constraint mismatch is.
- In-process idempotency works through 3 parts: `IIdempotencyDefinition<TMessage>` declares the key that a repeat is recognised by, `IIdempotencyStore` remembers which keys were applied, and `CommandModuleBuilder.EnableIdempotency()` registers 2 shortcuts and a completion handler that claim the key before the handler runs and settle it after. A key is applied on success and released on anything else, so a transient failure does not turn the retry into a false repeat. The durable inbox and outbox already dedupe envelopes. This is the same problem one layer in, solved with the shortcut stage plus the declaration and the storage contract. `IdempotencyDeclaration.ReplayResult` records the first answer so a repeated result-producing command can be answered with it. Without it, a repeat raises a configuration error naming the fix rather than inventing a `default`. `InMemoryIdempotencyStore` ships from `LiteBus.Testing.Mediation`, because a store that forgets on restart and knows only its own process cannot make a claim about the system. A grant carries a claim token that the completion handler settles with, so a late settle after a takeover is a no-op. The stored key defaults to the message full type name, escapes its segments, and prefixes the mediation tenant when one is set. A blank explicit scope is rejected with `IdempotencyConfigurationException`.
- The `litebus.idempotency.store` diagnostic probe reports `Unhealthy` when idempotency is enabled and no `IIdempotencyStore` is registered. The `litebus.audit.trail` probe reports `trailIsSingleton`, resolved by comparing the trail across 2 dispatch scopes.
- `IHandlerDescriptor.ContractType` records the closed contract a descriptor was discovered from, and `PipelineDispatch` carries the delegate bound to it at registration.
- An audit record says who acted. `AuditRecord.Actor` carries an `AuditActor` with a required `Id` and `Kind` and optional `DisplayName` and `OnBehalfOf`, supplied by an `IAuditActorResolver` that the application registers through `UseAuditActorResolver`. `AuditActor.User(id)` and `For(kind, id)` take no display name. Write `AuditActor.User(id) with { DisplayName = name }`, which keeps personal data out of the trail unless the application deliberately puts it there. `Kind` stays a string, because the set of things that can act belongs to the application. The resolver receives the completion context, so it reads the actor off the message and runs on every path, which attributes a denied command. A pre-stage handler cannot do that, because a guard that denies stops the pipeline before any pre-handler runs, and a denied command is the case a trail exists for. A handler that knows more than the resolver overrides it with `IAuditScope.WithActor`. Returning null is legitimate and means nothing established an actor, which is a different answer from a named process. The message itself is deliberately not on the record. It is handed to the resolver, so a payload cannot reach audit storage by default. The `litebus.audit.trail` probe reports a missing resolver as `Degraded` and carries `actorResolverRegistered`.
- `MessageModuleBuilder.AddAuditing` configures the whole audit feature in one call through `AuditingBuilder`: the trail, the actor resolver, the outcome mapper, and which axes produce records. Without it, the trail on the messaging builder and the per-axis switch on the command and query builders can be registered without each other, and the mismatch surfaces only from a diagnostic probe. Configuring a trail and selecting no axis now raises `AuditConfigurationException` at composition. No probe can report that combination at runtime, because nothing is ever audited and so nothing ever fails. The per-axis `EnableAuditing()` calls remain, and are what this call composes.
- `EventModuleBuilder.EnableAuditing()` enables auditing on the event axis, the same way commands and queries do. A domain fact is frequently the thing a review most wants recorded. The writer stores one record per publish, not per handler, because the mediation is the unit being audited. A record per subscriber would turn one fact into as many entries as there happen to be reactions.
- `IMessageDefinition<TMessage>` declares every value for a message from one `Describe(IMessageDeclarations)` method, with `Declare<TValue>`, `Audited`, `NotAudited` and `Exempt<TValue>` on the collection. The keyed `IMessageDefinition<TMessage, TValue>` remains, and is the better choice for a single declaration because the compiler checks it. Past one value the keyed shape is no longer the better choice, because the second and every later value has to be written as an explicit interface implementation naming the message type and the value type again, which repeats the type name 3 times to say one thing. Both shapes write into the same type-keyed bag, so a codebase uses whichever fits each message.
- Declaration requirements can be scoped. `RequireDeclaration<TValue, TScope>()` covers every message assignable to a marker, and `RequireDeclaration<TValue>(predicate, description)` covers an arbitrary selection with the words the error uses. The unscoped form applies to commands, queries and events alike, so requiring a permission of commands also demands one from every query and produces exemptions that say nothing. Those empty exemptions train a team to treat a rationale as paperwork. The scope is a type rather than a namespace on purpose: a namespace is a string that a refactoring tool moves without telling anyone, and for an authorization rule that failure is an unguarded command that used to be guarded. The composition error names the scope alongside every offender.
- `MessageModuleBuilder.ValidateComposition(Action<IMessageCatalog>)` runs an application rule over every registered message after every module has built. `IMessageCatalog` enumerates `MessageCatalogEntry` values carrying the message type, its resolved metadata, and its `AuditedDeclaration`, with an `Audited()` filter. The underlying hook takes an `IModuleConfiguration`, which only an `IModule` implementation receives. That is too much surrounding code for a 5-line assertion. `RequireUniqueAuditActions()` and `RequireAuditActionFormat(pattern)` ship as built-ins over it, because every audited application needs both, and getting either wrong corrupts the trail rather than breaking the build.
- `ICommandMediator.TrySendAsync` and `IQueryMediator.TryQueryAsync` return `MediationResult` and `MediationResult<TResult>` instead of raising a refusal. A denial and a validation failure are routine endings that the pipeline already models as decisions internally, and converting them to exceptions at the boundary left an HTTP endpoint catching one to produce a 403. A genuine fault still throws, because a database timeout is not something a boundary should branch on, and a result carrying the exception would invite one to be swallowed. Where a refusal mapper is registered, the mapped value arrives alongside the denied outcome, so an application sees both its own shape and the framework's classification.
- `ICommandMediator.EvaluateAsync` and `IQueryMediator.EvaluateAsync` answer whether a message would be permitted and well-formed, without performing it, returning a `MediationDecision`. This removes the second authorization method an application otherwise writes: one to authorize while doing, and one for a caller that shows or hides a control. The 2 methods answering the same question drift, and the drift is silent and affects security, because a button stays visible for an action the pipeline will refuse. It runs guards and validators only, because a shortcut and a pre-handler act rather than decide. The shipped idempotency shortcut claims a key, so evaluating a page full of controls would claim keys for commands nobody submitted. `MessageContextExtensions.RunAsyncDecisionStages` exposes the same prefix to a custom mediation strategy.
- In-process mediation is observable. `LiteBusMediationTelemetry` declares the `LiteBus.Mediation` activity source and meter with public instrument names: `litebus.mediation.duration`, `litebus.mediation.count`, `litebus.mediation.stage.duration` and `litebus.mediation.decisions`. Each mediation produces one span named `mediate {MessageType}`, tagged with the message, the outcome and the decision code. The decisions counter is tagged with the stage and the deciding handler, which turns "which stage denied this" from a stack trace into a filter. Only a `Failed` outcome sets the span error status, because a denial is a decision, and colouring every refused request red makes a trace view useless for finding the requests that actually broke. The inbox, the outbox, the transport and each broker adapter all published instruments while the library's primary job published none. `MessageModuleBuilder.UseTelemetry(MediationTelemetryOptions)` decides what is recorded. Spans and metrics are on, and per-stage spans and per-stage metrics are opt-in because mediation volume is orders of magnitude above durable-processing volume. The new `LiteBus.Messaging.Extensions.OpenTelemetry` package registers the source and the meter with `AddLiteBusMediationInstrumentation()` and `AddLiteBusMediationMetrics()`.
- `IMessageReader.Explain(Type)` returns a `MessagePipelinePlan`: the message, the result type it declares, and every handler that will run in the order it will run, as `MessagePipelineStep` records naming the stage, the priority, the handler, the contract, and whether it arrived indirectly or from a closed open generic. With 100 messages, open generic guards, an audit writer and a commit, answering "what runs for this command" previously meant reading the registry in a debugger. It reproduces the pipeline's own ordering rules, including that completion orders by priority alone across the direct and indirect split. It reads from the registry rather than computing at compile time, because the registry is the only thing that knows about closed open generics, base-type registrations and priority ties.
- `LiteBusCompositionSummary` reports what the host actually composed: message counts per axis, every open generic handler with the number of messages it was closed over, the audit trail and its lifetime, whether an actor resolver is registered, the declaration policies enforced, and how many application composition checks run. Resolve it and log `ToString()` once at startup. The open generic line matters most, because adding one file to a scanned assembly inserts a pipeline stage into every message it fits, and nothing in the composition code shows it.
- `IMessageWriter.RegisterFromScan(Type)` records that a type arrived through an assembly scan rather than being named. The record surfaces as `IMessageReader.ScannedOpenGenericHandlers` and `IMessageReader.OpenGenericClosures`. `MessageModuleBuilder.RequireExplicitOpenGenerics()` then fails composition, naming each scanned open generic and the registration line that fixes it. It is opt-in rather than the default, because picking up open generic handlers is what an assembly scan has meant since v4, and turning that off changes what a scan is rather than fixing a defect.
- `IHandleContextData` gained keyed overloads of `Set`, `Get`, `TryGet`, `Contains` and `Remove`. One value per type cannot express a command that names 2 accounts, which is the identity-map case the store's own worked example implies. Keys are compared with `object.Equals`, so an identifier value object is usable directly. The unkeyed slot is a distinct slot rather than a reserved key value, so neither can clear the other. `HandleContextDataNotFoundException` now carries the `Key` alongside the `DataType`.
- `Shortcut` and `Shortcut<TMessageResult>` carry a `Code` alongside their reason, and `MessageCompletionContext` exposes `Code`. `Code` means the same thing on all 3 decision shapes and on `Verdict`: something a later stage can switch on, where the reason is prose written for a person. Without it, a completion handler counting why messages were answered had to match on English text, and a metric could not tell a cache hit from an idempotent replay.
- `AuditReasonMissingException` is raised when an audited action declares `ReasonRequired` and the handler supplied no reason. It carries the action and the message type.
- Family defaults declare one value for a family of messages: `MessageModuleBuilder.DeclareDefault<TScope, TValue>(value)` declares a value for every message assignable to a marker, and `IMessageWriter.AddDeclaration(MessageDeclarationItem)` records a declaration without a definition class. "Everything under organizations requires ManageOrganization unless it says otherwise" is a rule worth stating once. Declaring it on each of 100 commands states it 100 times and gives it 100 places to drift. Nothing new decides precedence: a declaration still resolves to the one written closest to the message, so a command carrying its own value keeps it and the family inherits the default. That is the rule a definition written for a base type has always followed. The scope is a type rather than a namespace, for the same reason a scoped requirement is: a namespace is a string that a refactoring tool moves without telling anyone, and for an authorization default that failure is a command that used to be guarded and now is not. Declaring 2 defaults for one scope and value type is a configuration error, and the writer's default `AddDeclaration` throws rather than accepting the call and dropping it, because a silently dropped default is an unguarded command that looks configured.
- An application can own the audit record shape. `AuditingBuilder.UseRecordWriter<TWriter>(lifetime)` and `UseRecordWriterInstance`, over `MessageModuleBuilder.UseAuditRecordWriter`, replace the writer that turns a completed mediation into a record. `AuditRecord` is a handoff to `IAuditTrail` rather than a persistence schema, so a different set of fields needs a different `IAuditRecordWriter`, which is the entire contract between the pipeline and auditing. A replacement keeps the completion-stage placement, the `Observability` priority and the per-axis selection, and replaces exactly the record building. Everything the built-in writer uses is public, including the audit position through `IMessageRegistry`, `AuditReasonMissingException`, `IAuditScope`, `AmbientExecutionContext`, and `IAuditOutcomeMapper`. Skipping a message that declares no audit position is part of the contract, because without it every message on the selected axes produces a record. There is deliberately no generic `AuditRecord<T>` or `IAuditTrail<TRecord>`: a type parameter there spreads through the writer, 3 axis completion handlers, the probe, the builder and `AddAuditing`, so every application wanting the default would take on complexity that only a few need, and it gains nothing a writer cannot already do. The fixed shape maps onto NIST SP 800-53 AU-3, PCI DSS Requirement 10 and the DMTF CADF event model.
- `LiteBusCompositionSummary.AuditRecordWriter` names a writer that replaced the built-in one, and the startup line reports it. Replacing the writer replaces the whole of record building, and nothing else in the composition would say so. Without the line, a misregistration looks exactly like auditing working.
- The audit catalogue is derived rather than maintained. `IMessageCatalog` is registered as a Singleton so it resolves at runtime and not only inside a composition check. `AuditCatalogue.ToRows` projects every audited message into an `AuditCatalogueRow` carrying the action, the message, the category, the target kind, and whether a reason is required. `ToMarkdown` is one formatter over those rows. Rows are the primary surface, because what a compliance process consumes differs per team, and a library emitting only Markdown would serve one team and obstruct the rest. Rows are ordered by action so 2 runs produce the same document. The other half of an authorization matrix stays the application's: a required permission is an application value type, projected from `MessageCatalogEntry.Metadata` alongside these rows, because only the application knows what its own declarations mean.
- `MediationHarness` in `LiteBus.Testing.Mediation` runs the shipped pipeline over hand-supplied handler instances, with no host and no container, and reports which pre stages ran. Asserting that a guard denies previously meant booting the whole host, which for an application with a relational store meant a database container for a test about one authorization decision. `MediationHarnessResult.StagesRun` is the part no consumer can build, because only the stage runner knows it. That is the assertion a test of the behavior wants, since the point of the library is that behavior moved into named stages. It runs the real strategies through the real stage runner, so the fixed stage order, the validator stage's aggregation, and priority ordering all apply. What it leaves out is composition, so a registration that a host would reject still has to be asserted against a host. `MessageRegistryFactory.Create()` and `MessageMediatorFactory.Create(registry, dispatchScopeFactory)` are the public seams it is built on, both `EditorBrowsable(Never)`, for a manual host composing LiteBus without a container.
- `AuthorizationDeclaration` lets a message state its authorization position the way `AuditDeclaration` states its audit position: `[Authorized(policy)]`, `[AuthorizationExempt(rationale)]`, the keyed `IAuthorizationDefinition<TMessage>`, and the `Authorized` and `AuthorizationExempt` helpers on `IMessageDeclarations`. LiteBus carries the position and never evaluates the policy. `RequireDeclaration<AuthorizationDeclaration, ICommand>()` and LB1020 enforce that every message states one, and an application guard reads it through `IMessageMetadataAccessor`.
- `LiteBus.Commands.Storage.PostgreSql` ships a PostgreSQL `IIdempotencyStore`, registered with `commands.UsePostgreSqlIdempotencyStore(...)`, with a versioned schema, a startup initializer, and the `idempotency.postgresql.schema` probe. Claims record a request fingerprint and a claim token fencing the grant. A concurrent claim of a key still in flight answers `InFlight`. An unsettled claim older than `PostgreSqlIdempotencyStoreOptions.ClaimTimeout` (5 minutes by default and validated positive, measured on the database clock) is taken over with a new token.
- Recurring commands can run single-flight across replicas. `RecurringCommandHostOptions.RequireLease` takes a named lease before each pass (`LeaseName`, defaulting to the command type's full name) and skips the pass when another instance holds it, through the new `IRecurringCommandLease` contract. `TryAcquireAsync` returns an `IRecurringCommandLeaseHandle` whose `LeaseLost` token fires when the lease is taken or renewals fail. The loop then ends the busy period, releases the handle, cancels the in-flight send, and waits `ErrorBackoff`. It logs the loss at Warning (EventId 2106). `LiteBus.Commands.Recurring.Storage.PostgreSql` supplies a renewable lease row in `litebus_recurring_leases`, registered with `UsePostgreSqlRecurringLease(...)` and configured by `PostgreSqlRecurringLeaseOptions` (`LeaseDuration`, 30 seconds by default, and `RenewInterval`, a third of it by default). An explicit `RenewInterval` at or above `LeaseDuration` fails validation, and a held lease is never re-taken, including by the same holder. Lease times come from the database clock, the holder renews in the background while the pass runs, and a crashed holder's lease expires on its own. No connection is held between statements, so the lease works behind a transaction-mode PgBouncer. The schema is versioned and created at host startup, with the `recurring.postgresql.schema` probe. Composition fails when `RequireLease` is set and no lease is registered.
- `OutboxEnqueueItem<TEvent>.FromAmbient` and `InboxAcceptItem<TMessage>.FromAmbient` stamp the trace of the message being handled onto what the handler writes, through `MessageTrace.FromAmbient()`. They are explicit opt-ins. Nothing reads ambient trace unless they are called.
- `Idempotency.FromCommandKey(suffix)` keys an outbox or inbox item by the idempotency key the in-flight command was granted, so a retried command enqueues the same rows. `ClaimedIdempotencyKey` is public in `LiteBus.Messaging.Abstractions`, so other code can read the granted key.
- `LiteBus.Testing.DurableMessaging` adds an in-memory `ITransactionalOutbox` (`AddTestTransactionalOutbox`) and `ITransactionalInbox` (`AddTestTransactionalInbox`), `ProcessorPassHelpers.DrainOutboxAsync` and `DrainInboxAsync`, a `ScriptedOutboxDispatcher` that fails chosen contracts on chosen attempts, and `StoreSchemaContract.AssertCompatible`, which reports every schema difference at once. `TestOutboxStore` accepts store options and a `TimeProvider`.
- `LiteBusCompositionSummary.DuplicateStageCoverages` names every handler type that covers one message's pre-stage, post, error, or completion entries both directly and through a base type, so a handler that will run twice shows up in the startup line.
- Command idempotency covers the cases an HTTP API needs. `IdempotencyClaimOutcome` reports `InFlight` and `FingerprintMismatch`. `IdempotencyDeclaration.WithFingerprint` declares a request fingerprint, and an applied key claimed again with a different fingerprint is refused. An unsettled claim older than the store's claim timeout is taken over, so a crashed claimant does not block its key. Both outcomes deny the command with the codes in `IdempotencyRefusalCodes` (`idempotency.in-flight`, `idempotency.fingerprint-mismatch`). An unrecognized claim outcome throws `PipelineContractException` instead of running the handler without a recorded claim. `InMemoryIdempotencyStore` implements the same semantics with a `TimeProvider`.
- `WithIdempotencyKey(...)` in `LiteBus.Extensions.AspNetCore` is an endpoint filter that keys the command an endpoint sends by the `Idempotency-Key` request header. It is configured by `IdempotencyKeyFilterOptions` (header name, required by default, 255 characters at most, optional `TenantResolver` scoping keys per tenant) and carried into the pipeline by `IdempotencyKeyGuard` and `CommandMediationSettings.WithIdempotencyKey(HttpContext)`. `MediationResult.ToHttpResult(...)` answers an in-flight key with 409, a fingerprint mismatch with 422, other denials with 403, and invalid commands with 400.
- `IUnitOfWork` and `UseUnitOfWork<TUnitOfWork>()` on the command and query module builders commit the application's unit of work at `HandlerPriorities.UnitOfWork`, once per mediation that succeeded. A denied, invalid, shortcut-answered or faulted mediation commits nothing. The application supplies the commit. LiteBus never opens a transaction.
- `LiteBus.Commands.Storage.Marten` brings the command axis to Marten. `UseMartenUnitOfWork()` commits the scoped `IDocumentSession`, `UseMartenIdempotencyStore(...)` keeps idempotency claims as Marten documents in their own serializable sessions, and `MartenAuditTrail` stages each successful audit record in the handler's session so it commits with the change. Denial and failure records are written on their own, so a rolled-back session cannot lose them.
- `IFaultRefusalClassifier`, registered with `MessageModuleBuilder.UseFaultRefusalClassifier<TClassifier>()`, ends a mediation as a refusal when any stage raises a fault it recognizes, including a commit fault raised in the completion stage. `TrySendAsync` then returns it as a value, and error handlers do not run. `PostgreSqlConstraintRefusalClassifier` maps unique (23505) and exclusion (23P01) violations on configured constraints to denials with application codes. Cancellation is never classified, and nothing changes when no classifier is registered.
- `IExecutionContext.HandledAt` is the instant the mediation started, read once from the messaging module's `TimeProvider`.
- `Shortcut.Deny(reason, code)` and `Shortcut<TMessageResult>.Deny(reason, code)` let a shortcut deny a message when the decision can only be made at the shortcut stage, for example an idempotency claim. The mediation ends exactly as a guard denial does: `TrySendAsync` returns `Denied`, `SendAsync` throws `LiteBusMessageDeniedException` naming the shortcut in `DeniedBy`, completion handlers and the audit record observe the denial, error handlers do not run, and refusal mappers apply.
- `OutboxModuleBuilder.EnablePerHandlerDelivery()` writes one outbox envelope per subscribed main handler of an event, recorded on the new `OutboxEnvelope.Handler` column. The in-process dispatcher publishes each envelope to that handler alone, so a failing reaction retries, dead-letters and is replayed on its own while the others publish. Per-handler message ids and idempotency keys are derived deterministically, so a retried enqueue resolves to the same rows. A handler added after the enqueue does not receive events already enqueued. A single enqueue persists the whole fan-out atomically in one batch call, `CreateBatchAsync` fans out per handler as well, strict resubmission compares handler addressing, and the Entity Framework Core save-changes interceptor keeps staged handler addressing. Composing per-handler delivery with a transport dispatcher throws unless `AllowPerHandlerDeliveryWithTransportDispatch` acknowledges the duplicate broker publication.
- `OutboxModuleBuilder.StageCollectedEvents()` registers a scoped `IDomainEventCollector` and a completion handler at `HandlerPriorities.Persistence`. When the mediation succeeded, the handler enqueues the events a handler collected into `ITransactionalOutbox`, before the unit-of-work commit. With `EnableSaveChangesInterceptor`, the Entity Framework Core adapter supplies the non-generic `ITransactionalOutbox` from the ambient transaction.
- `OutboxModuleBuilder.UseAmbientTrace()` stamps enqueued envelopes that carry no explicit trace with the trace of the message being handled.
- `InboxModuleBuilder.UseAmbientTrace()` stamps accepted envelopes that carry no explicit trace with the trace of the message being handled, through `MessageTrace.FromAmbient()`.
- `AuditedDeclaration.WithTargetFrom<TMessage>(...)` and `WithReasonFrom<TMessage>(...)` read the audit target and reason off the message, so a definition declares them once instead of every handler supplying them. A value the handler supplies through `IAuditScope` still wins.
- `DeclarationGuard<TMessage, TValue>` looks a declaration up for the message's runtime type and calls one `DecideAsync(declaration, message, ...)`. An undeclared message is denied with `declaration.missing` unless `DecideUndeclaredAsync` is overridden, and a recorded exemption allows. `AuthorizationGuard<TMessage>` builds on it: an exempt message is allowed, and an authorized one calls `AuthorizeAsync(policy, message, ...)`.
- Analyzers `LB1023` (a command handler sends or publishes through a mediator, nesting a second unit of work) and `LB1024` (a command handler injects an external side-effect type such as `HttpClient`, configured with `litebus.LB1024.forbidden_types`) are Warnings in `LiteBus.Handlers`, and both are disabled by default. `LB1024` inspects public constructors only.
- `RetryBackoff.Schedule` and `RetryOptions.Delays` state the retry ladder directly: one delay per attempt. `Fixed` and `Exponential` derive every delay from `InitialDelay` under the `MaxDelay` cap, which cannot express a window that starts inside a minute and still reaches days. Exponential from one minute reaches roughly 4 hours by the ninth attempt, and stretching the tail to a week pushes the first retries hours apart, which is the opposite of what a receiver with a brief outage needs. A retry window is a customer-visible guarantee for partner-facing delivery, so it is stated rather than approximated. An attempt past the end of the ladder repeats the last entry, and `MaxDelay` does not clamp the entries, so a declared tail is never silently shortened. `RetryOptions.Validate()` runs when the module builds and when a processor is constructed directly, so an empty or negative ladder fails at boot rather than on the first failure.
- `MessageModuleBuilder.UseSerializer<TMessageSerializer>(lifetime)` and `UseSerializerInstance` state the wire format of persisted messages at the composition root. The default is `SystemTextJsonMessageSerializer` with `JsonSerializerDefaults.Web`, which is camel case. The only other way to change it is to replace the container registration after `AddLiteBus`, which no analyzer sees and no startup check reports. Forgetting it renames every property of every durable message on the wire and breaks every consumer, with nothing failing at boot.
- `IdempotencyDeclaration.KeyedByContext()` and `SuppliedIdempotencyKey` cover a key that cannot be projected from the message. A processor webhook carries a raw body and a signature and nothing else, deliberately, so that nothing unverified reaches a decision. Its deduplication key is the provider's event id, known only after the signature is checked and the body parsed. That is a lookup, and a lookup needs services. A guard does that work and hands the key forward through `IExecutionContext.Data`. The pre stage runs guards before shortcuts, and the key is read once and reused by both the shortcut that claims it and the completion handler that settles it, so verification happens once per mediation. It is deliberately not a container-resolved provider: each stage resolves the key independently, so a provider would do the work twice and, if not perfectly deterministic, write a different key at each stage. A message declared this way that reaches the shortcut with no key raises `IdempotencyConfigurationException` naming the message type, because a generated fallback would make every delivery look distinct.
- `LiteBus.Commands.Recurring` sends one command on a fixed interval for the life of the host, registered through `CommandModuleBuilder.AddRecurring` with either a command factory or, for a parameterless command, timing alone. It replaces the hosted service most CQRS applications write once per background job: create a scope, resolve the mediator, send one command, sleep, back off on failure, and never let an exception escape the loop. `AddRecurring` registers the command it sends, and `RecurringCommandHostOptions.Validate` rejects a zero or negative `Interval` or `ErrorBackoff`, which would spin the loop without pause. The loop takes a snapshot of its validated timing values at start, so changing the options later does not affect a running loop. A result implementing `IRecurringWorkReport` can report that work remains, which skips the interval and turns a large backlog into one busy period instead of one batch per interval. There is no cron expression and no missed-run catch-up. By default the loop runs on every host instance concurrently, which suits a command that drains work by leasing rows, where the store arbitrates. `RequireLease` with a registered `IRecurringCommandLease` runs each pass on at most one instance instead.
- `LB1022` warns when `[HandlerPriority]` falls inside the range LiteBus reserves for its own handlers. A value between `HandlerPriorities.ReservedFloor` and `ReservedCeiling` orders the handler against the persistence and audit writers rather than against the application handlers it was meant to be ordered against. That position can move between releases. Types implementing no handler interface are skipped.
- `InProcessOutboxDispatchOptions.RequireHandler`, configured through `UseInProcessDispatch(dispatch => ...)`, controls whether a dispatched message with no handler fails the attempt. It defaults to `true`.
- `CommandModuleBuilder.RegisterChildModule` is the seam feature packages compose through. A capability layered on the command axis registers inside `AddCommands` rather than as a second top-level module the caller must remember to add. `CommandModule` is an `ICompositeModule`.

### Changed

- Dependencies move to their current versions, including `AWSSDK.SQS` 4, `Microsoft.Extensions.*` 10.0.13 and OpenTelemetry 1.20. EF Core and Npgsql stay on 9.x because `Pomelo.EntityFrameworkCore.MySql` has no EF Core 10 provider. Roslyn stays on 4.8.0 as the compiler the shipped analyzer is built against, and `SQLitePCLRaw` stays on 2.1.x to match the EF Core 9 SQLite provider.
- `LiteBusTransportTelemetry` exposes the 2 circuit-breaker counter names as public constants. The emitted names are unchanged.
- Transport publishers are singletons in all 5 adapters. A dispatched envelope therefore no longer opens and closes its own AMQP channel, Azure Service Bus sender link or Kafka producer flush. Consumers are transient in all 5, Azure Service Bus included, because each instance holds one subscription. The Kafka producer is flushed once, when the container is disposed.
- Saga state is compared with the JSON snapshot taken when it was loaded. Reading state and then calling `Complete()` now works. A dispatch that only reads state saves nothing, and a handler that changes state in place without `SetState` is still persisted.
- The `AfterDispatch` hook runs on the persist token on both the inbox and the outbox. A shutdown during a saga save therefore no longer leaves an executed command or a published event to run again. With the default `HonorShutdownTokenOnPersist = false`, a hook that never returns delays shutdown instead.
- A failed persist for one lease-lost message is logged and counted as a persist failure instead of aborting the whole inbox or outbox pass and discarding the other envelopes' results.
- Every processor and cleanup loop delay goes through the injected `TimeProvider`, so tests can drive the startup delay, heartbeat interval and cleanup backoff. After a transient failure, the first cleanup retry waits 5 seconds instead of a full `Interval`.
- PostgreSQL inbox and outbox `AddBatchAsync` insert in chunks of 1,000 rows inside the caller's transaction, so a batch above the 65,535 parameter limit no longer fails. Inbox and outbox requeue clear `error_type`, `first_failed_at` and `dead_lettered_at`, matching the EF Core and in-memory stores.
- Event post-handlers and error handlers receive `null` as the message result instead of the task that tracked handler completion.
- Message resolution counts the interfaces of the registered type. A message implementing several registered interfaces can therefore resolve to a different handler than before.
- `TransportOutboxDispatcherOptions.ResolveRoute` takes precedence over `OutboxEnvelope.Topic`, as its documentation says, and an empty result fails the dispatch with `LiteBusDispatchException`. An empty tenant routing strategy result fails the same way.
- A failing diagnostics store stops the queue-depth gauge from reporting until the next successful read, instead of exporting the last good counts. The outbox records `litebus.outbox.diagnostics.unavailable` when no store is registered.
- PostgreSQL modules register every store and the work signal through singleton factories that resolve a container-owned `PostgreSqlDataSourceOwner<TModule>`. A data source created by `UseConnectionString` is now disposed with the service provider under Microsoft dependency injection. The container never disposed the prebuilt instance it was registered as before, although the documentation already claimed it was. `UseDataSource` still leaves ownership with the application.
- `IProcessorWorkSignal` extends `IAsyncDisposable`, so the dedicated LISTEN connection of a PostgreSQL work signal is disposed by the container that created it. `PostgreSqlWorkSignal` disposal is idempotent and no longer races a listener startup. A wait after disposal falls back to the poll interval.
- The outbox in-process dispatch failure message carries contract-registration guidance only when the cause is a missing contract or handler. It no longer appears on every failure, including concurrency conflicts and cancellations.
- `MediationExceptionFilters.IsRetryableDispatchException` inspects the inner exception chain. A refusal or missing handler wrapped by a dispatcher is therefore dead-lettered on its first attempt instead of spending the retry schedule.

- Every module builder recognizes guard, validator, shortcut, and refusal mapper contracts, completion handler contracts, and message definitions as registrable constructs, so `RegisterFromAssembly` discovers them.
- The completion stage orders handlers by priority alone. Every other role runs handlers registered for the message type before handlers registered for a base type, but completion handlers observe an ending rather than wrapping the handler, so there is no nesting for a specific handler to sit inside. The split would have put the framework's broadly registered audit writer beyond the reach of an application's priority. That order decides whether a record lands inside the transaction, which is not something registration breadth should decide.
- The registry skips an untyped open generic shortcut for a message that declares a result. A closed registration of that pair is still a configuration error, because the author named the message. An open generic applies to every message it fits, and a result-producing message is not one of them, so it is skipped the way a constraint mismatch is.
- `AsyncBroadcastMediationStrategy` observes cancellations so it can report them to the completion stage. It honors a guard or shortcut decision by publishing to no handlers, and reports no result to completion handlers rather than the task that tracked its handlers. Cancellation still propagates as before.
- A decision on a stream query no longer runs post-handlers. Stopping the pipeline means the work did not happen, so the reactions to it do not fire. The caller still receives whatever stream the shortcut or the refusal mapper supplied.
- Every dispatchable handler contract is declared in one place. `PipelineContracts` holds one row per contract naming its family, its invoker, and, for a pre-stage contract, its stage and aggregation policy. Dispatch, all 4 descriptor builders, and the stage runner read from it. A new pre-stage role therefore takes one row rather than edits in 9 files, and post-handlers, completion handlers, and refusal mappers are declared the same way rather than hand-wired beside the table. The run order is read from the `PreStage` ordinals rather than from a hand-written call sequence, which makes the order the enum documents the order that executes.
- The stream mediation strategy routes every fault through one place instead of 6, and enumerates the handler's stream and a post-handler's replacement through one loop instead of 2. It is a third shorter. One timing changes with it: the handler's enumerator is released when its enumeration ends rather than when the whole mediation does, so it is now disposed before post-handlers run rather than after. A post-handler receives the `IAsyncEnumerable` and would enumerate it afresh, so nothing observes this beyond the resource being held for less time.
- The inbox and outbox share one processor hook runner. They ran identical copies, and each built a fresh envelope adapter in all 5 hook phases, so a single dispatch allocated 5 of them per axis. The adapter is now built once per dispatch.
- A pre stage that holds no handler is skipped without enumerating the shared descriptor collection. `IMessageDependencies.HasPreStageHandlers` answers from a mask computed once when dependencies are resolved, so a message with no guard, validator, or shortcut costs nothing for those stages. The default implementation on the interface enumerates, and is correct for custom implementations, so nothing outside LiteBus has to change.
- Registering a type that carries a pipeline marker but names no message type is reported with `LiteBusConfigurationException` instead of being accepted. Every marker is memberless, so such a type produced no descriptor, fell through to message-type registration, and then silently never ran.
- Pre-handlers, post-handlers, and completion handlers are invoked through the closed contract recorded in their descriptor at registration, using a delegate built while the descriptor is built. The previous dispatch searched a handler's interfaces for a method by name on every invocation and called it reflectively. That search is how a class implementing pipeline contracts for several message types could have the wrong method selected. Choosing the contract from registration metadata makes that class of bug structurally impossible, and building the delegate at registration keeps reflection out of the dispatch path.
- Registration reports 2 definitions that declare the same value type for one message, or 2 declarations covering one message where neither is more derived than the other, instead of resolving them by assembly scanning order.
- `LiteBusConfigurationException` gains derived types so a composition failure can be caught by category: `ModuleCompositionException`, `MessageDeclarationException`, `PipelineContractException`, `DurableStorageConfigurationException` and `AuditConfigurationException`. It was the one type for every composition failure, so nothing could be caught selectively. The base is no longer sealed and stays catchable as the category. Every throw site in the library now uses a derived type.
- The command, query and event module builders accept a pipeline handler written against the messaging-level contract when its message type is, or is constrained to be, assignable to that axis. Without that, a cross-cutting guard would be written once per axis, so a fix to authorization would have to land in every copy. A handler constrained to neither axis is still refused, because nothing says which axis it is for, and accepting it would silently close it over every message in whichever axis happened to register it. Main handler contracts are excluded: a command handler and a query handler mean different things.
- `IExecutionContext` is registered as a scoped dependency, so a handler declares it as a constructor parameter and the dependency appears in the type signature. Every documented way of reading mediation state went through the `AsyncLocal` static, which hides a dependency and forces an ambient scope in a unit test. `AmbientExecutionContext` remains the way to reach the context from code that runs outside dependency injection.
- `IAuditOutcomeMapper.MapFailureCode` returns the refusal's own `Code` for a `Denied` or `Invalid` outcome before falling back to the exception type name. A guard that supplied a code chose it deliberately, and it survives either shape of refusal. An exception-derived code is present when a refusal raises, and absent when a mapper returns a value instead. A shortcut's code is deliberately excluded, because an answered mediation reports `Succeeded`, and its code would otherwise land in the field a review reads as the reason something did not work.
- Outbox in-process dispatch requires a handler by default. `EventMediationSettings.ThrowIfNoHandlerFound` defaults to `false`, and the v6 dispatcher published with it as-is, so an event with no registered handler was leased, dispatched and marked `Published` without ever leaving the process. If the assembly holding the handlers is not scanned by `AddEvents`, that is total data loss with no exception, no dead letter, and a backlog reading of zero. A silent no-op is a defensible default for an immediate publish, where the caller can see there are no subscribers. A durable dispatch has no such caller, and the outbox promise is that a committed message reached somewhere. The inbox axis cannot fail this way, because command mediation requires exactly one handler. Set `RequireHandler = false` to allow publishing to zero handlers where that is deliberate.
- The operational columns are written and readable. `last_attempted_at`, `first_failed_at`, `dead_lettered_at`, `last_lease_owner` and `error_type` were created by the DDL, validated by the schema check at boot, and mapped by the EF Core model. An operator dashboard querying them read nulls, because 4 of the 5 were written by nothing and read by nothing. They are now on `InboxEnvelope` and `OutboxEnvelope`, written by every store adapter on every terminal transition, and returned by `IInboxManager.QueryAsync` and `IOutboxManager.QueryAsync`. A dead-letter listing therefore no longer needs a second statement against the library's own table. `FirstFailedAt` is set once and is not moved by later failures, so it keeps answering how long a message struggled. `AsRequeued` clears the failure record and resets the attempt count.
- `TestQueryMediator.NextResult` is consumed once per query, stream, or tried query. `StreamAsync` throws `InvalidCastException` on a stub type mismatch instead of yielding an empty stream.

### Fixed

- The management message query endpoints (`GET .../inbox/messages` and `GET .../outbox/messages`) treat `pageSize` as optional and default it to 50 (`InboxMessageQueryBinding.DefaultPageSize`, `OutboxMessageQueryBinding.DefaultPageSize`). A request without it was rejected with an empty 400 response.

- A lease renewal that throws now cancels the running dispatch and reports the lease lost, instead of surfacing only after the handler finished. The lease store receives a cancellable token linked to the heartbeat.
- Mediation restores the caller ambient execution context before it returns a task or stream, and creates the dispatch scope only when a handler resolves a service. A stream that is never enumerated therefore holds no container scope.
- A command implementing `ICommand<TCommandResult>` sent through the non-generic `SendAsync(ICommand)` or `TrySendAsync(ICommand)` runs the result-bearing pipeline. Post-, error- and completion handlers therefore receive the result instead of `null` (#128).

- The EF Core save-changes interceptors fail the save when 2 strict-idempotency envelopes share a message id, instead of keeping one and reporting both as accepted.

- An AMQP mandatory publication that the broker returns as unroutable fails with `AmqpMessageReturnedException` and releases its circuit-breaker permit. A routing mistake therefore no longer counts as broker failure and opens the circuit.
- A cancelled AMQP connection probe releases its circuit-breaker permit instead of leaving the circuit half-open until restart.

LB1003 reports `ITransactionalInbox`, `ITransactionalOutbox` and `ITransactionalOutbox<TContext>`, ignores ordinary method parameters, and reports inherited properties like inherited fields. LB1011 recognises target-typed `new() { Tags = ... }`. LB1015 checks the interceptor call on the same axis. LB1013 and LB1016 require the Entity Framework Core `DbContext`.

That cost 20 to 40 seconds per analyzer on a 3,400-file project. These rules now gather facts from symbol and syntax-node actions and report at compilation end. LB1001, LB1007 through LB1012, LB1017, LB1018, LB1020 and LB1021 report the same diagnostics on build, and no longer appear as live squiggles. See [Build-Only Rules](https://litebus.io/docs/reference/analyzers#build-only-rules).

The dispatcher now rethrows the caller's cancellation, and both envelope handlers treat it as no outcome.

The Confluent `Consume` call blocks, so the loop ran inline and `StartAsync` did not return until the first record arrived. The ingress host hid this by starting consumers from a background loop. Behaviour after startup is unchanged.

- `TransportInboxIngressConsumer` could recreate its admission semaphore after disposal and release a disposed one.

A `Register` call on another builder therefore no longer silences them. `LB1004` covers `ITransactionalInbox<TContext>` and untyped `InboxAcceptItem` acceptance, resolving untyped items through `MessageType = typeof(X)` when present and matching arguments to parameters by name. `LB1011` resolves `const` tag names and maps arguments to parameters. `LB1003` walks base classes and names every API family it flags.

A handler such as `Guard<T> where T : ICommand` was also closed over `ICommand` once any handler named that interface, and that closure applied to commands registered after it but not before. The guard therefore ran twice for some commands and once for others. When 2 closures of one generic handler definition reach a message through the same contract, only the direct one is kept. A different handler type over a base type still runs indirectly. A new closure links to all committed messages, so indirect coverage no longer depends on registration order.

Tracked terminal persist saves one row at a time, so one lost race skips only that row.

### Breaking

- Tenant filters and lease requests mean the same on every store: `null` applies no tenant restriction, and an empty string matches unscoped rows only. The EF Core and in-memory stores previously treated an empty string as no restriction. The PostgreSQL outbox lease, query, and purge paths treat a blank filter as unscoped, matching the inbox store.
- `IOutboxDiagnosticsStore` and `IOutboxManager` gain `GetFailureSummaryAsync`. A custom outbox store implements it.
- A second `AddLiteBus` on one service collection or container builder throws `ModuleCompositionException`. Each container hosts one LiteBus composition.
- A second transport module in one composition throws `ModuleCompositionException` naming both modules. Both modules register the single `ITransportPublisher` binding, so 2 transports in one composition could not work before either.
- Registering a service type both as a single binding and as collection items throws `ModuleCompositionException`. The single-binding and collection views used to disagree silently.
- `RegisterStartupTask` throws `ArgumentException` for a type that implements `IBackgroundService`, mirroring the existing rejection in `RegisterBackgroundService`.
- `ProcessorOptions.HookFailurePolicy` is `ProcessorHookFailurePolicy?`. `null`, the default, means the dispatcher's recommendation, otherwise `DeadLetter`. A `UseProcessorOptions` call that sets only a batch size no longer replaces the transport dispatchers' `CompleteDespiteHookFailure` with `DeadLetter`. Set the policy explicitly to keep that behavior.
- `IProcessorEnvelope` and `IProcessorEnvelopeHook` moved from `LiteBus.DurableMessaging.Abstractions.Processing` to `LiteBus.Messaging.Abstractions.Processing`.
- `IOutboxManager.RunRetentionPurgeAsync` throws `OutboxManagementException` when `OutboxCleanupHostOptions.Retention` is not a positive period. It previously returned 0.
- A saga purge with no predicate and no `Take` throws `ArgumentException`.
- The AMQP ingress broker-scoped idempotency key is scoped to the queue (`ingress:{queue}:{id}`) instead of the exchange. When 2 queues bind to one exchange, they no longer share a key. Ingress reads identity and idempotency from the `litebus-message-id` header only when `TrustApplicationHeaders` is set. A redelivery that arrives while an AMQP ingress host is being redeployed can be accepted twice.
- Kafka and SQS route and content-type metadata use the shared names `litebus-route` and `content-type` instead of `Route` and `ContentType`. During a rollout, a consumer reading the old names has to read both.
- `TransportPublishRequest.Mandatory` defaults to `true`, matching `AmqpPublishRequest` and the outbox dispatcher. A direct `ITransportPublisher` caller relying on `false` has to set it.
- The Kafka transport no longer registers the bare `IProducer<string, byte[]>`. Resolve `ITransportPublisher` instead. `MessageTimeoutMs` no longer also sets the socket timeout and disables send retries.
- `LiteBus.Messaging.Extensions.ServiceProviderExtensions.GetRequiredService` is obsolete. Use the one in `LiteBus.Runtime.Abstractions.Extensions`.
- `IProcessorWorkSignal` now extends `IAsyncDisposable`. A custom work signal must implement `DisposeAsync`. It should also implement `IDisposable` when the container may be disposed synchronously.

- `IExecutionContext.Abort` and `LiteBusExecutionAbortedException` are removed. A pre-handler that stopped the pipeline now implements a guard contract and returns a `Verdict`, or a shortcut contract and returns a `Shortcut`. The break is a compile error rather than a change in behavior, which is deliberate. A flag that left `Abort()` compiling would have silently started running the statements after it.
- `ICommandValidator<TCommand>` and `IQueryValidator<TQuery>` return `Task<Validity>` from `ValidateAsync` instead of `Task`, and derive from `IMessageValidator<TMessage>` rather than from the pre-handler contract. A validator that reported a failure by throwing now returns `Validity.Invalid(...)` instead. The break is a compile error rather than a change in behavior, for the same reason the `Abort()` removal is. A validator left compiling would have gone on reporting malformed input as a fault. An adapter over an external validation library changes one line, returning the failures instead of raising. A codebase with too many validators to convert in one commit derives them from `ThrowingCommandValidator` or `ThrowingQueryValidator` to get the build passing first and convert module by module.
- `IExecutionContext` gained `Data`. It is an infrastructure contract implemented by LiteBus itself. Applications that only implement handlers are unaffected, and a custom implementation or test double returns `new HandleContextData()` from `Data`.
- `IModuleConfiguration` gained `CompositionValidations` and `RegisterCompositionValidation`. A custom host adapter must run the collected validations after its module loop. Otherwise a rule spanning several modules never executes.
- The non-generic pre-stage marker is renamed `IMessagePreStageHandler`. It is the discovery marker for the whole pre stage, which now holds 4 roles, so it can no longer share a name with `IMessagePreHandler<TMessage>`, the one role in that stage LiteBus does not name. The post and completion stages hold a single role each, and keep the shared name.
- `IAsyncMessageErrorHandler<TMessage>` and `IAsyncMessageErrorHandler<TMessage, TMessageResult>` are renamed `IMessageErrorHandler<TMessage>` and `IMessageErrorHandler<TMessage, TMessageResult>`. The prefix named nothing there: no synchronous error handler exists, and the contract derives straight from the `IMessageErrorHandler` marker. Every stage now follows one rule: a marker shares its name with its role when the stage holds a single role. The main handler keeps `IAsyncMessageHandler`, where the prefix does name something. It is the `Task`-returning specialization of `IMessageHandler<TMessage, TMessageResult>`, alongside `IStreamMessageHandler` for the `IAsyncEnumerable` one.
- `IMessageDescriptor` and `IMessageDependencies` gained `RefusalMappers` and `IndirectRefusalMappers`. Custom implementations, including test doubles, must add them. `IMessageDependencies.HasPreStageHandlers` ships with a default implementation, so it needs no change unless a custom implementation wants the faster answer.
- A refusal or a missing handler now dead-letters on its first attempt in the inbox and outbox processors, instead of consuming the retry schedule. Both fail identically on every attempt, so retrying only delayed the dead-letter entry an operator was waiting to see.
- Only a guard or a shortcut can stop the pipeline. Stopping means skipping the work, and once the main handler has run there is nothing left to skip. A handler that previously aborted from a later stage now calls `SuppressPostHandlers()`.
- The synchronous handler layer is removed, and the asynchronous one takes over its names. In v6.0.2 `IMessagePreHandler<TMessage>` declared `object PreHandle(TMessage)` and `IMessagePostHandler<TMessage, TMessageResult>` declared `object PostHandle(TMessage, TMessageResult?)`, with `IAsyncMessagePreHandler<TMessage>`, `IAsyncMessagePostHandler<TMessage>`, and `IAsyncMessagePostHandler<TMessage, TMessageResult>` holding the `Task` members beside them. Every handler is asynchronous now, so the `IAsync` names are gone and the members they declared live on `IMessagePreHandler<TMessage>` and `IMessagePostHandler<TMessage, TMessageResult>`. A handler that implemented an `IAsync` contract changes the interface name only. A handler that implemented a synchronous one becomes asynchronous. The axis contracts such as `ICommandPreHandler<TCommand>` and `IQueryPostHandler<TQuery, TResult>` are unchanged at the call site and now derive from those directly.
- `IExecutionContext` gained `PostHandlersSuppressed` and `SuppressPostHandlers()`. Custom implementations, including test doubles, must add them.
- `IMessageDescriptor`, `IMessageDependencies`, and the handler descriptor interfaces gained members for the completion stage, message metadata, the recorded contract, and the prebuilt dispatch. Custom implementations of these interfaces must add them. They are infrastructure contracts implemented by LiteBus itself. Applications that only implement handlers are unaffected.
- `MessageContextExtensions` moves out of the `LiteBus.Messaging.Abstractions` package and namespace into `LiteBus.Messaging`, taking the stage runners with it. They open ambient scopes, order the stages, preserve stack traces, and decide what a denied caller receives, which is engine work rather than contract. Only a custom mediation strategy names the type, and every package implementing one already references `LiteBus.Messaging`. The fix is therefore a using directive.
- `IPreHandlerDescriptor` is `IPreStageHandlerDescriptor`, and the `PreHandlers` and `IndirectPreHandlers` collections on `IMessageDescriptor` and `IMessageDependencies` are `PreStageHandlers` and `IndirectPreStageHandlers`. One collection holds all 4 roles, so `ILazyHandlerCollection<IMessagePreStageHandler, IPreHandlerDescriptor>` contradicted itself on a single line.
- `IMessageHandler` has no members. `object Handle(object message)` and its default implementation on `IMessageHandler<TMessage, TMessageResult>` are removed, which is what lets one class implement several closed handler contracts such as `IEventHandler<OrderRefundSucceeded>` and `IEventHandler<OrderRefundSettledOutsideProcessor>`. Those classes failed with CS8705 before. The mediator calls each handler through the closed contract on its descriptor. Delete any hand-written `object IMessageHandler.Handle(object)` implementation. Code that called `Handle(object)` calls the typed contract instead.
- `IExecutionContext` gains `HandledAt`. Only an application that implements the interface itself is affected.
- The outbox table gains a nullable `handler` column for per-handler delivery. The PostgreSQL outbox schema is version 2, and an existing version 1 table is upgraded on startup when schema initialization is enabled. The Entity Framework Core outbox mapping includes the column, so an application that owns its EF Core migrations adds one.
- `ParallelFaultMode` is now `HandlerFaultMode`, `AggregateAll` is now `ContinueAndAggregate`, and `EventExecutionSettings.ParallelFaultMode` is now `FaultMode`. The old name described a mechanism, while the setting is a policy: whether a failing handler suppresses its siblings. It now applies to sequential execution as well. Under sequential broadcast the first handler that threw stopped every handler behind it, and the only escape was turning on parallel execution, which forces thread-safety onto handlers sharing a resource such as an ORM session. Fault isolation no longer costs a move to `Parallel`. The mode governs handlers inside one priority group and never carries across groups, because a priority difference states that the later group runs after the earlier one.
- `AsFailed` and `AsDeadLettered` on both envelopes take a `MessageFailure` instead of a string. The 3 parts of a failure answer 3 different questions: the formatted text is what a person reads, the exception type is what a dashboard groups by, and the timestamp is what fills `first_failed_at` and `dead_lettered_at`. Storing only the formatted string forced every consumer to parse it back apart. Use `MessageFailure.From(exception, occurredAt)` for an exception, or `MessageFailure.FromError(text, occurredAt)` for a failure with a reason but no exception.
- `CommandModuleBuilder` no longer takes an `IMessageRegistry` and an `IContractWriter`, and queues registrations instead of writing them straight through. `CommandModule` is an `ICompositeModule`, so its configuration action runs during `DeclareChildren`, before the live registry exists. Applications are unaffected. Code that constructs the builder directly is not.
- `ICommandMediator` and `IQueryMediator` gained members without default implementations (`TrySendAsync`, `TryQueryAsync`, `EvaluateAsync`). A hand-written implementation of either, for example a test double, has to implement them.
- Payloads written by v6 under an `IContextualPayloadEncryptor` were encrypted without the context, so v7 cannot decrypt them. Drain the inbox and outbox before upgrading.
- The Kafka transport registers `IConsumer<string, byte[]>` as transient instead of singleton, and `KafkaConsumer` owns its injected client. It closes the client on `StopAsync` and disposes it on `DisposeAsync`. Code that shares one client across consumers or disposes it externally must stop doing so.
- Kafka and SQS `StopAsync` complete without throwing when the consume loop faulted. Await `WaitUntilStoppedAsync` to observe the terminal failure.
- The SQS consumer deletes wire poison (an undecodable body or malformed packed headers) and continues with the next delivery, instead of faulting the loop on every delivery and every restart. Poison therefore no longer reaches the queue dead-letter queue through redrive.
- A second `AmqpConsumer.StartAsync` throws `InvalidOperationException`, matching `IMessageConsumer` and the other transports. It previously threw `AmqpTransportConfigurationException`.
- Diagnostic probe names must be unique across probe types. Registering 2 different probe types under one name fails composition with `ModuleCompositionException`.
- Management message-query endpoints reject `messageIds` identifier sets larger than `MaxBulkMessageIds` with HTTP 400, matching purge and requeue.
- Inbox message queries reject `PageSize` above 1000 (`InboxMessagePageRequest.MaxPageSize`) with `ArgumentOutOfRangeException`. The limit applies in `IInboxManager` and in every inbox store.
- Ingress ignores `litebus-visible-after` and `litebus-visible-after-delay` unless `TrustApplicationHeaders` is set. Accepted messages are immediately visible, while correlation headers are still always honored.
