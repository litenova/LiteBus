# Migration Guide v7

LiteBus 7.0 finishes the pipeline vocabulary that v6.1 started. The pre stage now holds four named roles the framework can tell apart before invoking them, which is what lets it fix the order they run in. Nothing in the persistence schemas or transport behavior changes, so no database work is involved, and almost every break is a compile error in application code. Two are not, and both are called out below: the `HandlerPriorities.UnitOfWork` value moved, and the exception raised for a missing audit reason changed type.

## Why v7 Is a Major Upgrade

v6.1 introduced guards and shortcuts as separate contracts so the framework could run every guard before any shortcut. That fixed one ordering hazard and left three loose ends: validators still reported failures by throwing, a guard could hand back its own refusal value and so do the shortcut's job on the denial path, and the vocabulary named some roles and left others named by position.

v7 closes all three. Every break in that vocabulary is a compile error rather than a silent behavior change, which is deliberate: a validator left compiling would have gone on reporting malformed input as a fault.

## Validators Return a Value

`ICommandValidator<TCommand>.ValidateAsync` and `IQueryValidator<TQuery>.ValidateAsync` return `Task<Validity>` instead of `Task`, and both now derive from `IMessageValidator<TMessage>` rather than from the pre-handler contract.

```csharp
// Before
public Task ValidateAsync(TransferCommand command, CancellationToken cancellationToken = default)
{
    if (command.Amount <= 0)
    {
        throw new ArgumentOutOfRangeException(nameof(command));
    }

    return Task.CompletedTask;
}

// After
public Task<Validity> ValidateAsync(TransferCommand command, CancellationToken cancellationToken = default)
{
    return Task.FromResult(command.Amount <= 0
        ? Validity.Invalid("the amount must be positive", nameof(command.Amount))
        : Validity.Valid);
}
```

Three things change with it. Validation is its own stage, running after guards and before shortcuts, so a malformed message can no longer claim an idempotency key or collect a cached answer. Every validator runs and the stage collects their failures, so a caller sees all of them at once. And the mediation reports `MediationOutcome.Invalid` rather than `Failed`, so an audit trail can tell malformed input apart from a database timeout, and error handlers no longer see it.

A validator that genuinely needs to fault, because something it depends on is unreachable, should still throw. That is a fault, not a verdict about the message.

See [Validation](../concepts/validation.md) for adapting an external validation library.

### Converting a Hundred Validators One at a Time

The signature change is a compile break in every validator at once, which for a codebase with a hundred of them is a single commit nobody can review. `ThrowingCommandValidator<TCommand, TException>` and `ThrowingQueryValidator<TQuery, TException>` exist so you do not have to.

Derive from the adapter, move the v6 body across unchanged, and translate the exception once:

```csharp
public sealed class TransferCommandValidator
    : ThrowingCommandValidator<TransferCommand, ValidationException>
{
    protected override Task ValidateOrThrowAsync(
        TransferCommand command,
        CancellationToken cancellationToken)
    {
        // The v6 body, unchanged.
        var errors = new ErrorCollection();

        if (command.Amount <= 0)
        {
            errors.Add(nameof(command.Amount), "the amount must be positive");
        }

        errors.ThrowIfInvalidCommand();
        return Task.CompletedTask;
    }

    protected override Validity Describe(ValidationException exception) =>
        Validity.Invalid(exception.Errors.Select(e => new ValidationFailure(e.Message, e.Member)));
}
```

Only the exception type you name is caught. Anything else propagates and ends the mediation as a failure, which keeps a genuine fault inside a validator from being reported as a verdict about the message.

Adapted and converted validators mix freely in one mediation. The stage collects failures across both shapes, so a half-converted codebase behaves correctly rather than only once the last file lands. That is what makes the migration reviewable: adapt everything mechanically in one pass, then convert module by module.

Two things the adapter cannot do for you, both worth knowing before you lean on it:

- A throwing body stops at the first problem, so a message with three malformed fields still reports one failure. Recovering the collected-failures behavior needs a real conversion.
- Nothing forces the adapter out. Treat it as scaffolding with a deletion date, not a supported shape, or the codebase keeps a validation model v7 exists to replace.

## Guards Return Only a Verdict

These types are removed:

| Removed | Replacement |
| --- | --- |
| `IMessageGuard<TMessage, TMessageResult>` | `IMessageGuard<TMessage>` plus a refusal mapper |
| `Verdict<TMessageResult>` | `Verdict`, plus a refusal mapper |
| `ICommandGuard<TCommand, TCommandResult>` | `ICommandGuard<TCommand>` plus a refusal mapper |
| `IQueryGuard<TQuery, TQueryResult>` | `IQueryGuard<TQuery>` plus a refusal mapper |
| `IStreamQueryGuard<TQuery, TQueryResult>` | `IQueryGuard<TQuery>` plus a refusal mapper |

A guard supplying its own refusal value was the guard doing the shortcut's job on the denial path, and it duplicated one mapping across every guard registered for a message. The mapping now lives in one place:

```csharp
// Before: every guard on the command repeated the shape of a refused result.
public Task<Verdict<Result>> CheckAsync(TransferCommand command, CancellationToken ct = default)
{
    return Task.FromResult(_policy.Allows(command)
        ? Verdict<Result>.Allow
        : Verdict<Result>.Deny("not permitted", Result.Forbidden("not permitted")));
}

// After: the guard supplies a reason and a code; one mapper decides what a refused caller receives.
public Task<Verdict> DecideAsync(TransferCommand command, CancellationToken ct = default)
{
    return Task.FromResult(_policy.Allows(command)
        ? Verdict.Allow
        : Verdict.Deny("not permitted", code: "NOT_PERMITTED"));
}

public sealed class ResultRefusalMapper : ICommandRefusalMapper<ICommand, Result>
{
    public Result Map(ICommand command, Refusal refusal) => refusal.Outcome switch
    {
        MediationOutcome.Denied  => Result.Forbidden(refusal.Code, refusal.Reason),
        MediationOutcome.Invalid => Result.Invalid(refusal.Reason),
        _                      => Result.Failure(refusal.Reason)
    };
}
```

One registration against `ICommand` covers every command producing that result type, and it covers validation failures at the same time. A mapper registered against a concrete message wins over one registered against a base type; two at the same level are reported as a configuration error rather than resolved by assembly scanning order.

Register nothing and a refusal reaches the caller as `LiteBusMessageDeniedException` or `LiteBusMessageInvalidException`, which is the behavior of the untyped guard in v6.1.

## Renames

| Before | After | Why |
| --- | --- | --- |
| `IMessageGuard<TMessage>.CheckAsync` | `DecideAsync` | It returns a `Verdict`. `CheckAsync` already meant a health check on `IDiagnosticCheck`, and sat beside `ValidateAsync` as a near-synonym for the two concepts the design works hardest to separate |
| `MessageOutcome` | `MediationOutcome` | It describes how a mediation ended rather than a property of the message. Completion handlers and audit outcome mappers name the type, so both need the rename |
| `MessageOutcome.ShortCircuited` | `MediationOutcome.Answered` | Its siblings all name a state the message ended in; short-circuiting names a mechanism that describes a denial just as accurately. `Answered` matches `TryAnswerAsync` and `Shortcut.Answer` |
| `IMessagePreHandler` (non-generic) | `IMessagePreStageHandler` | It is the discovery marker for the whole pre stage, which now holds four roles, so it cannot share a name with `IMessagePreHandler<TMessage>`, the one role in that stage LiteBus does not name |
| `IExecutionContext.Abort` | `IExecutionContext.SuppressPostHandlers` | Aborting did two things at once. Skipping the work is now a shortcut and refusing it is a guard, which leaves this method with the one job its name states |

`IMessagePreHandler<TMessage>` keeps its name. It is the one pre-stage role LiteBus does not name, and a catch-all named by position is more honest than one named after a single job it serves.

Each word in the table above names exactly one thing across the whole API. [Pipeline Vocabulary](../reference/glossary.md#pipeline-vocabulary) is the list, and it is the one that wins where a page and a type name disagree.

## The Stage Runners Moved to LiteBus.Messaging

`MessageContextExtensions` now lives in the `LiteBus.Messaging` assembly and the `LiteBus.Messaging` namespace, rather than in `LiteBus.Messaging.Abstractions`. It is the pipeline engine: it opens ambient scopes, orders the stages, preserves stack traces, and decides what a refused caller receives. An abstractions package describes contracts, and this was never one.

Only a custom `IMessageMediationStrategy` calls these methods, and every package that implements one already references `LiteBus.Messaging`, so the fix is a using directive:

```csharp
using LiteBus.Messaging;            // add this
using LiteBus.Messaging.Abstractions;
```

`RunAsyncPreHandlers` is replaced by `RunAsyncPreStages`, which runs all four pre-stage roles in the fixed order and returns the `PipelineDecision` the strategy acts on. The per-stage helpers that briefly existed beside it (`RunAsyncGuards`, `RunAsyncValidators`, `RunAsyncShortcuts`, `RunAsyncPreHandlers`) are gone: running one stage without the others cannot honor the ordering guarantee that the split exists to provide.

## Error Handler Contracts Lose the Async Prefix

`IAsyncMessageErrorHandler<TMessage>` and `IAsyncMessageErrorHandler<TMessage, TMessageResult>` become `IMessageErrorHandler<TMessage>` and `IMessageErrorHandler<TMessage, TMessageResult>`. The prefix named nothing: no synchronous error handler exists, and the contract derives straight from the `IMessageErrorHandler` marker.

The axis contracts `ICommandErrorHandler<TCommand>`, `IQueryErrorHandler<TQuery>`, `IEventErrorHandler<TEvent>`, and their two-parameter forms are unchanged, so only code naming the messaging-level contract directly needs a change.

`IAsyncMessageHandler` keeps its prefix, because there it does name something: it is the `Task`-returning specialization of `IMessageHandler<TMessage, TMessageResult>`, alongside `IStreamMessageHandler` for the `IAsyncEnumerable` one.

## Removed Aliases

`IAsyncMessagePreHandler<TMessage>`, `IAsyncMessagePostHandler<TMessage>`, and `IAsyncMessagePostHandler<TMessage, TMessageResult>` are gone. Every handler is asynchronous, so the distinction those names drew no longer exists.

The axis contracts are unchanged at the call site: `ICommandPreHandler<TCommand>`, `IQueryPostHandler<TQuery, TResult>`, and their siblings compile as they are, and now derive from `IMessagePreHandler<TMessage>` and `IMessagePostHandler<TMessage, TMessageResult>` directly. Only code that named an alias explicitly needs a change.

## Shortcuts Always Carry Their Result

`Shortcut<TMessageResult>.Skip()` and `Shortcut<TMessageResult>.HasResult` are removed. Answering a message that produces a result always supplies the value.

The removed overload meant "yields nothing" on a stream query and failed at runtime with `LiteBusConfigurationException` on every other result shape, so one verb carried two meanings. A stream shortcut that means the caller enumerates nothing now says so:

```csharp
// Before
return Shortcut<IAsyncEnumerable<Product>>.Skip("nothing to stream");

// After
return Shortcut<IAsyncEnumerable<Product>>.Answer(AsyncEnumerable.Empty<Product>(), "nothing to stream");
```

The untyped `Shortcut.Answer(reason)` is unchanged, for messages that produce no result.

## Marker-Only Types Are Reported

Every pipeline marker is memberless, so a class could implement one without implementing any contract naming a message type. Such a class produced no descriptor, fell through to message-type registration, and silently never ran. It now raises `LiteBusConfigurationException` at registration.

## Refusals Are Terminal in the Durable Processors

The inbox and outbox processors dead-letter a refusal or a missing handler on its first attempt instead of spending the retry schedule on it. A guard refuses the same message identically on every attempt, so retrying only delayed the dead-letter entry an operator was waiting to see.

`MediationExceptionFilters.IsRefusal` and `IsRetryableDispatchException` expose that classification for custom processors.

## Interfaces That Gained Members

`IMessageDescriptor` and `IMessageDependencies` gained `RefusalMappers` and `IndirectRefusalMappers`. These are infrastructure contracts implemented by LiteBus itself; applications that only implement handlers are unaffected. Custom implementations, including test doubles, must add them.

`IMessageDependencies.HasPreStageHandlers` also arrives, but with a default implementation that enumerates the descriptors, so a custom implementation compiles unchanged. Override it only to answer from a precomputed mask, as LiteBus does.

## The Unit-of-Work Priority Moved

`HandlerPriorities.UnitOfWork` is `ReservedCeiling + 100` instead of `ReservedCeiling`. Nothing behaves differently unless an application registered a handler at exactly `HandlerPriorities.ReservedCeiling`, in which case it now runs before the commit rather than tying with it, which is what such a handler was written to do.

Two names for one value invited a consumer to register infrastructure "just above the ceiling" and silently tie with the commit. Ties resolve by registration sequence, which is assembly scan order. The ceiling is now a boundary marker with nothing on it, and the band between it and `UnitOfWork` is where application infrastructure that has to run after every LiteBus handler and still inside the transaction belongs.

Because these are `const int` values, a consumer has to rebuild against 7.0.0 to pick the new position up. There is no runtime fallback and none is possible.

## Composition Exceptions Have Categories

`LiteBusConfigurationException` is no longer sealed and now has five derived types:

| Derived type | Covers |
| --- | --- |
| `ModuleCompositionException` | Duplicate module registration, dependency cycles, a missing required module, a descriptor the container adapter cannot translate |
| `MessageDeclarationException` | Two definitions declaring one value, a definition that declares nothing, an annotation that disagrees with its value, a required declaration nobody satisfied |
| `PipelineContractException` | A pipeline marker with no contract, an unsupported open generic shape, two refusal mappers at one level, an untyped shortcut on a result-producing message |
| `DurableStorageConfigurationException` | Durable messaging enabled without the storage, dispatch or processor registration it needs, or against a schema it cannot use |
| `AuditConfigurationException` | No `IAuditTrail` registered, `AddAuditing` with no axis selected, a failed audit convention check |

`catch (LiteBusConfigurationException)` keeps working and still catches all of them. Only code that needed to tell one composition mistake from another has anything to change.

One throw moved off the hierarchy entirely. An audited action that declares `ReasonRequired` and receives no reason now raises `AuditReasonMissingException`, which derives from `Exception`. It is a data problem in one mediation rather than a composition error, and an application catching configuration faults at startup should not also catch a handler that forgot a call.

## Auditing Is Configured In One Call

`AddAuditing` replaces the split between a trail on the messaging builder and a switch on each axis builder:

```csharp
// Before: two decisions, either of which could be made without the other.
registry.AddMessaging(messaging => messaging.UseAuditTrail<SqlAuditTrail>());
registry.AddCommands(commands => commands.EnableAuditing());
registry.AddQueries(queries => queries.EnableAuditing());

// After: one decision that cannot be half-made.
registry.AddMessaging(messaging => messaging.AddAuditing(auditing => auditing
    .UseTrail<SqlAuditTrail>()
    .UseActorResolver<RequestActorResolver>()
    .ForCommands()
    .ForQueries()));
```

The old calls still work and are what `AddAuditing` composes, so nothing has to change. Configuring a trail through `AddAuditing` and selecting no axis now fails composition, because no probe can report that at runtime: nothing is ever audited, so nothing ever fails.

`EnableAuditing()` is now available on `EventModuleBuilder` too, writing one record per publish rather than one per handler.

## Audit Records Say Who Acted

`AuditRecord.Actor` is new, and an `IAuditActorResolver` supplies it:

```csharp
internal sealed class RequestActorResolver : IAuditActorResolver
{
    public AuditActor? Resolve(MessageCompletionContext context) => context.Message switch
    {
        IActingAccountCommand acting => AuditActor.User(acting.ActingAccountId.ToString()),
        _ => AuditActor.System(ProcessNameOf(context.Message.GetType()))
    };
}

registry.AddMessaging(messaging => messaging.UseAuditActorResolver<RequestActorResolver>());
```

If you built attribution yourself in v7 preview, this replaces all of it. The pattern it replaces is a scoped holder plus a guard that allows every message and exists only to populate the holder before anything can deny, because a pre-handler never runs on the denied path and that is the path a trail exists for. The resolver runs at the completion stage, so it attributes a denied, invalid, failed or cancelled mediation as readily as a successful one. Delete the guard and the holder; keep the projection onto `AuditActor`.

`IAuditScope.WithActor` overrides the resolver for a handler that knows something the rule does not, such as an actor established by exchanging a token mid-handler.

Returning `null` is legitimate and means nothing established an actor. Prefer `AuditActor.System("worker-name")` where the application knows a process acted: a scheduled job and an unattributed action are different answers, and an audit query has to be able to tell them apart.

The `litebus.audit.trail` probe now reports `Degraded` when a trail is registered and no resolver is, because every record would be written with no actor.

## Definitions Can Describe Themselves

`IMessageDefinition<TMessage>` declares any number of values from one method:

```csharp
// Before: the type name three times to declare the second value.
internal sealed class CloseGateCommandDefinition
    : IAuditDefinition<CloseGateCommand>,
      IMessageDefinition<CloseGateCommand, RequiredAuthorization>
{
    public AuditDeclaration Audit => AuditDeclaration.Audited("admission.close-gate");

    RequiredAuthorization IMessageDefinition<CloseGateCommand, RequiredAuthorization>.Value =>
        new(new PermittedAction.ManageGate(), Subject.Platform);
}

// After.
internal sealed class CloseGateCommandDefinition : IMessageDefinition<CloseGateCommand>
{
    public void Describe(IMessageDeclarations declarations)
    {
        declarations.Audited("admission.close-gate", category: "admission", targetKind: "gate");
        declarations.Declare(new RequiredAuthorization(new PermittedAction.ManageGate(), Subject.Platform));
    }
}
```

Nothing is removed. `IMessageDefinition<TMessage, TValue>` is still the better choice for a message that declares exactly one thing, because the compiler checks the value against its key, which is why `IAuditDefinition<TMessage>` and `IIdempotencyDefinition<TMessage>` are built on it. Past one declaration it stops paying. Both shapes write into the same type-keyed metadata, so convert message by message or not at all.

`IMessageDeclarations` also carries `NotAudited(rationale)` and `Exempt<TValue>(rationale)`, so a definition can record an exemption without an attribute.

## Declaration Requirements Can Be Scoped

An unscoped `RequireDeclaration<TValue>()` applies to commands, queries and events alike, which is usually not the rule anyone meant:

```csharp
// Before: this demanded a permission declaration from every query too, and the exemptions written to satisfy
// it said nothing.
messaging.RequireDeclaration<RequiredAuthorization>();

// After: scope to the axis, or better, to the marker that carries the rule.
messaging.RequireDeclaration<RequiredAuthorization, ICommand>();
messaging.RequireDeclaration<RequiredAuthorization, IActingAccountCommand>();

// Or an arbitrary selection, with the words the composition error uses.
messaging.RequireDeclaration<RetentionClass>(type => type.Namespace!.Contains("Billing"), "every billing message");
```

The unscoped overload is unchanged, so nothing breaks. Delete the exemptions that only existed to satisfy a requirement that was too wide.

The scope is a type rather than a namespace deliberately. A namespace is a string a refactoring tool moves without telling anyone, so a requirement keyed on one silently stops applying when a folder is renamed, and for an authorization rule that failure is an unguarded command that used to be guarded.

## A Refusal Can Be A Value

`TrySendAsync` and `TryQueryAsync` hand back how the mediation ended instead of raising:

```csharp
// Before: an endpoint catching an exception to produce a status code.
try
{
    await _commands.SendAsync(command, ct);
    return Results.NoContent();
}
catch (LiteBusMessageDeniedException denied)
{
    return Results.Problem(denied.Reason, statusCode: 403);
}

// After.
var result = await _commands.TrySendAsync(command, cancellationToken: ct);

return result.Outcome switch
{
    MediationOutcome.Denied  => Results.Problem(result.Reason, statusCode: 403),
    MediationOutcome.Invalid => Results.ValidationProblem(ToErrors(result.Failures)),
    _                        => Results.NoContent()
};
```

A genuine fault still throws. A database timeout is not something a boundary should branch on, and a result carrying the exception would invite one to be swallowed, so the line is drawn where the pipeline already draws it: a decision is a value, a fault is an exception.

`SendAsync` is unchanged, and a registered `IMessageRefusalMapper` still applies to both. Under `TrySendAsync` a mapped refusal arrives with the mapped value in `Value` and `Denied` in `Outcome`, so an application that models failure in its own result type sees both halves.

There is no `TryStreamAsync`. A stream's refusal is observed when enumeration starts rather than when the method returns, so a result value would have to be produced before the decision exists.

## A Message Can Be Asked Without Being Sent

`EvaluateAsync` runs the decision stages and stops:

```csharp
var decision = await _commands.EvaluateAsync(new CloseOrganizationCommand(id), cancellationToken: ct);

if (decision.IsDenied)
{
    // hide the control
}
```

This is what replaces a second authorization method written beside the real one, one to authorize while doing and one for a caller that shows or hides a control. Two methods answering the same question drift, and the drift is silent and security-relevant: a button stays visible for an action the pipeline will refuse.

It runs guards and validators only. Shortcuts and pre-handlers act rather than decide, and the shipped idempotency shortcut claims a key, so evaluating a page full of controls would burn keys for commands nobody submitted.

That puts one obligation on a guard: it has to be free of effects a caller would not want from a "may I" question. A guard that loads an aggregate to decide is fine, and the load happens on every evaluation, so check `IExecutionContext.Data` before loading if it is expensive.

## Mediation Is Observable

Nothing to change, but there is now something to wire up:

```csharp
services.AddOpenTelemetry()
    .WithTracing(tracing => tracing.AddLiteBusMediationInstrumentation())
    .WithMetrics(metrics => metrics.AddLiteBusMediationMetrics());
```

From `LiteBus.Messaging.Extensions.OpenTelemetry`. One span per mediation and three metrics: total duration, a count tagged by outcome and decision code, and a decision counter tagged by the stage and the handler that stopped the message. That last one is what answers "which stage denied this" without reading a stack trace.

Per-stage spans and per-stage durations are off by default, because mediation volume is orders of magnitude above durable-processing volume. Turn them on while investigating with `messaging.UseTelemetry(new MediationTelemetryOptions { StageSpans = true, StageMetrics = true })`.

## The Execution Context Is Injectable

`IExecutionContext` is registered as a scoped dependency:

```csharp
// Before: the dependency is invisible in the type signature, and a unit test needs an ambient scope.
var occurrence = AmbientExecutionContext.Current.Data.Get<Occurrence>();

// After.
public sealed class Handler : ICommandHandler<CancelOccurrenceCommand>
{
    private readonly IExecutionContext _context;

    public Handler(IExecutionContext context) => _context = context;
}
```

`AmbientExecutionContext` is unchanged and remains the way to reach the context from code that runs outside dependency injection.

Scoped here means per mediation, and it is worth knowing exactly what that means, because it is not per request. The dispatch scope is created from the root `IServiceScopeFactory`, so it is a sibling of the ambient HTTP request scope rather than a child of it. A scoped `DbContext` in a handler is not the request's `DbContext`, two `SendAsync` calls in one request get two different scoped instances, and a test that seeds a scoped service from its own scope is not touching the instance the handler used. Per-mediation state belongs in `IExecutionContext.Data`, which is scoped to the message rather than to whichever scope happens to surround it.

`Data` also gained keyed overloads, for a mediation that legitimately holds two values of one type:

```csharp
context.Data.Set(new AccountId("a-1"), debit);
context.Data.Set(new AccountId("a-2"), credit);
```

## Family Defaults

A rule that holds for a whole family can be stated once:

```csharp
// Before: the same declaration on each of a hundred commands.
// After.
registry.AddMessaging(messaging => messaging
    .DeclareDefault<IOrganizationCommand, RequiredAuthorization>(
        new RequiredAuthorization(PermittedAction.ManageOrganization, Subject.Organization))
    .RequireDeclaration<RequiredAuthorization, IOrganizationCommand>());
```

Nothing to change, and nothing new decides precedence: a command that declares its own value keeps it, and the rest of the family inherits the default. That is the rule a definition written for a base type has always followed, so a codebase already using a base-type definition for this is already getting the behavior; this is a way to state it without a file.

Defaults and a scoped requirement are the pair worth having: the requirement makes the family answer for the value, the default answers for the ones with nothing special to say.

## The Audit Catalogue Is Derived

```csharp
var catalog = provider.GetRequiredService<IMessageCatalog>();
File.WriteAllText("audit-catalogue.md", catalog.ToMarkdown());
```

If you hand-built an audit catalogue or an authorization matrix during the migration, delete the audit half. `IMessageCatalog` now resolves at runtime as well as inside a composition check, and `ToRows` gives an ordered row per audited message. The permission half stays yours, projected from `MessageCatalogEntry.Metadata`, because a required permission is your value type and only you know what it means.

## Composition Can Be Inspected

Three additions, none of which require a change:

```csharp
// What the host actually composed, as one startup line.
logger.LogInformation("{Summary}", provider.GetRequiredService<LiteBusCompositionSummary>());

// What runs for one message, in the order it runs.
var plan = provider.GetRequiredService<IMessageReader>().Explain(typeof(CloseOrganizationCommand));

// The application's own conventions, as startup failures.
messaging.RequireUniqueAuditActions().RequireAuditActionFormat();
```

The summary names every open generic handler and the number of messages it was closed over. That is the mitigation for the one implicit behavior worth watching: adding a file to a scanned assembly inserts a pipeline stage into every message it fits, with no registration line in the composition code to review. `messaging.RequireExplicitOpenGenerics()` turns that into a composition failure naming each offender, and is opt-in because picking up open generics is what an assembly scan has meant since v4.

## One Guard Can Serve Both Axes

The axis builders now accept a handler written against a messaging-level pipeline contract, when its message type is constrained to that axis:

```csharp
// One implementation, registered per axis, rather than two near-identical classes.
internal sealed class AuthorizationGuard<TMessage> : IMessageGuard<TMessage>
    where TMessage : ICommand
{ ... }

registry.AddCommands(commands => commands.Register(typeof(AuthorizationGuard<>)));
```

A handler constrained to neither axis is still refused: nothing says which axis it is for, and accepting it would silently close it over every message in whichever axis registered it. Main handler contracts are excluded, because a command handler and a query handler mean different things.

## Upgrade Order

1. Update the package references to 7.0.0 and build. Everything below surfaces as a compile error.
2. Convert validators to return `Validity`, or derive them from `ThrowingCommandValidator` / `ThrowingQueryValidator` to land the build first and convert them module by module afterwards.
3. Replace typed guards with the untyped guard plus one refusal mapper per result type.
4. Rename `CheckAsync` to `DecideAsync` on guards.
5. Rename `MessageOutcome` to `MediationOutcome` in completion handlers and audit mappers, and replace its `ShortCircuited` member with `Answered`.
6. Replace `Shortcut<T>.Skip()` on stream shortcuts with an empty sequence.
7. Replace any explicit use of the removed `IAsyncMessagePreHandler` and `IAsyncMessagePostHandler` aliases, and rename `IAsyncMessageErrorHandler` to `IMessageErrorHandler`.
8. In a custom mediation strategy, add `using LiteBus.Messaging;` and call `RunAsyncPreStages` in place of `RunAsyncPreHandlers`.
9. Replace `IExecutionContext.Abort` with a guard, a shortcut, or `SuppressPostHandlers`, whichever the call actually meant.
10. Rebuild so the new `HandlerPriorities.UnitOfWork` value is picked up, and move any handler registered at exactly `HandlerPriorities.ReservedCeiling` if it was there to precede the commit.
11. Replace `catch (LiteBusConfigurationException)` with the derived type where the code needed to tell one composition mistake from another, and stop catching that type for a missing audit reason, which is now `AuditReasonMissingException`.
12. Register an `IAuditActorResolver` and delete whatever established attribution before, then check the `litebus.audit.trail` probe reports `Healthy` rather than `Degraded`.
13. Narrow any `RequireDeclaration<TValue>()` that was wider than the rule it enforced, and delete the exemptions that existed only to satisfy it.
14. Run the test suite. A validator that used to throw and is now expected to return will show up as a behavior difference in tests that asserted on the exception type.
